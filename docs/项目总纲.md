## 1. 一句话说清项目

**用两台普通 USB 摄像头，实时识别一个球形物体在三维空间中的位置，重建它的运动轨迹并预测未来位置。**

拆开是两件事：

|                        | 输入                | 输出                                           |
| ---------------------- | ------------------- | ---------------------------------------------- |
| **看见球**（单目感知） | 一路视频            | 每帧的球心像素坐标、半径（亚像素精度）         |
| **定位球**（双目几何） | 两路视频 + 标定参数 | 每帧的三维坐标 (X, Y, Z)、速度、预测的未来位置 |

关键点：**深度（Z）靠两台相机的视差算出来**，这是"双目"的全部意义。
单目也能靠"球有多大"估深度，但那依赖球径先验，且精度差一个量级。

## 2. 基本功能

### 2.1 两条技术路线并存

```
        ┌──────────────── 单目路线（已跑通、已量化）────────────────┐
        │                                                          │
  一路视频 → 检测 → 跟踪 → 单目测深 Z=fR/r → 二维轨迹 → 预测 → 可视化
        │                                                          │
        └──────────────────────────────────────────────────────────┘

        ┌──────────────── 双目路线（代码已完成，待真机验证）────────┐
        │                                                          │
  两路视频 → 各自走上面的"检测 + 跟踪" → 同步对齐 → 极线配对
           → 三角测量 → 三维轨迹 → （平滑 / 三维可视化：未做）
        │                                                          │
        └──────────────────────────────────────────────────────────┘
```

**"单目感知库 ×2 路"是设计核心**：双目不是另写一套检测，而是把同一套
`sphere_tracker/` 并行调用两次，再由 `stereo/` 把两路合成三维。
所以单目侧的每一次改进，双目自动受益。

### 2.2 单目能做什么

| 能力           | 说明                                                                 |
| -------------- | -------------------------------------------------------------------- |
| **检测**       | 四条互补线索：颜色分割 / 霍夫圆 / 背景差分 / 投票融合；可选 YOLO·SAM |
| **亚像素定位** | 径向一致性判据 + 边缘细化，半径误差 0.06 px                          |
| **跟踪**       | 卡尔曼滤波 + 机动检测 + 反弹重初始化；可应对短暂遮挡与检测失败       |
| **测深**       | 球直径先验 `Z = fR/r`；需要事先标定焦距（有专门工具）                |
| **预测**       | 已知重力约束 + 最长有效后缀拟合，预测 0.1–0.5 s 后的位置             |
| **相机自适应** | 自动探测后端 / 分辨率 / 帧率并缓存；支持手持、云台、平移拍摄         |
| **实时与离线** | 实时窗口交互；也可批处理视频导出 CSV                                 |

### 2.3 双目额外提供什么

| 能力         | 说明                                                 |
| ------------ | ---------------------------------------------------- |
| **双目标定** | 棋盘格 + `cv2` 标定，输出内外参、基线、校正映射      |
| **标定复检** | 判断装置是否被碰动过（未动 0.08 px vs 碰动 27.9 px） |
| **视频同步** | 拍手/闪光求帧偏移，自动对齐两路时间轴                |
| **极线配对** | 把右图搜索从二维降成一维，是双目实时的前提           |
| **三角测量** | 输出三维坐标，并给出交会残差作为可信度指标           |

### 2.4 明确的边界（别误期待）

- **不依赖特定颜色**是设计目标，橙色球只是已验证样例；但颜色线索仍是主力，
  所以拍摄时**曝光/白平衡/焦距必须固定**。
- **三维可视化（Plotly/Unity）尚未做**，两块主要缺口之一。
- **真机标定已跑通，且已到"可用"档**（2026-10-24 更新）：最新一次为 2026-10-24 17:34 落盘，
  基线 **123.99 mm**、整体 RMS **0.770 px**、极线 **0.584 px**、有效 39/40 对，
  判定"**可用 —— 满足三维重建要求**"（数值以 `config/stereo_calibration.json` 为准）。
  早先几次（2026-10-14 67.98 mm / 2026-10-19 64.60 mm）分别是"勉强可用"档，已被取代。
  **数字漂亮的那批仍然是合成真值**，不要混着引用。
- **相机层有三层已知根因（2026-10-18 查清，别再当"未知数"）**：
  ① 其中一台 aoni 在 MSMF 下**只认 1920×1080**（请求 640×480/1280×720 会
  "打开成功但一帧都不给"）；② 同一台**首帧要 ~23 秒**（另一台 ~2 秒）；
  ③ 设备会被置为无效（`-2147483638`），**只能物理拔插**恢复。
  所以"相机消失"多半是**我们请求了它给不了的东西**，不是相机坏了。
  工具：`cameras.py probe` / `doctor`；完整记录见 `交接文档.md` §10.15。
- **反复出现的七类错误**（弱证据撑强结论 / 修 A 引出 B / "打开成功"≠能用 /
  判据跟不上契约 / 拆函数留旧尾巴 / 假警报训练人忽略真警报 / 文档抄数值会过期）
  已归纳成表，见 `交接文档.md` **§10.16**。改完必答三问：证据是什么、
  最坏情况输出什么、判据在哪。
- 目标场景是**实验室条件**（固定机位、良好照明），不是户外或高速工业场景。

## 3. 怎么跑起来

**最省事的入口：双击项目根目录的 `启动程序.bat`（唯一的双击入口）。**
它会自动：① 找一台**真的装了 opencv** 的 Python（逐个候选真跑一次
`import cv2, numpy`，PATH 里那个没装 opencv 的 msys64 Python 会被跳过）；
② 缺依赖就问一句然后自动装（清华镜像，失败退回官方源）；
③ 启动图形界面 —— 没有 `tkinter` 就自动换成命令行界面。

图形版按"标定 → 参数 → 开始检测"三步走，还带**标定前置检查**（判断两路是否
都看得到棋盘）、相机探测、**「无关」标记**和实时运行日志。

**只想重做某一步**，就给同一个文件加一个参数，不需要记别的脚本：

    启动程序.bat cli         命令行界面（等价于原来单独的"命令行版"）
    启动程序.bat setup       相机设置（左 / 右 / 无关）
    启动程序.bat check       相机检查（编号有没有漂移）
    启动程序.bat precheck    标定前置检查
    启动程序.bat calibrate   双目标定
    启动程序.bat verify      标定复检
    启动程序.bat run         实时检测
    启动程序.bat test        回归测试

每一步跑完都会停住等按键，不会一闪而过。细节见 `用户手册.md` §2.2。

只有当你要脚本化 / 批处理时，才用下面这些原生命令。
只需要能跑 Python，不需要摄像头就能验证环境：

```powershell
# 必须用绝对路径！裸 python 会解析到 msys64 那个没装 opencv 的解释器
$PY = "$env:USERPROFILE\miniforge3\envs\myenv\python.exe"
cd D:\MY_CODING_PROGRAM\Three-dimensional-sphere-motion-trajectory-recognition

# 1) 先跑回归测试确认环境（不需要相机，约 1 分钟）
& $PY tests\selftest_synthetic.py

# 2) 接摄像头实时看效果（不写编号，启动时自动挑最优：优先外接、避开内置/红外、跳过全黑流）
& $PY apps\run_realtime.py --method fusion

#    双目第一次用先固定"左/右"角色（编号会漂移，身份不会）：
& $PY apps\tools\cameras.py identify
& $PY apps\calibrate_stereo.py --left left --right right --cols 8 --rows 5 --square 25
```

完整命令（含双目标定、离线批处理、各工具）见 `交接文档.md` §6 命令速查。
**二十四个回归测试都必须输出"全部通过"**，这是改动代码后的底线。

### 4.5 阅读时会撞上的术语

| 词                | 意思                                                                                         |
| ----------------- | -------------------------------------------------------------------------------------------- |
| **合成真值**      | 用程序渲染出来的"假视频"，每个像素的正确答案已知。用于回归测试与精度量化。**不等于真机能力** |
| **真实机 / 真机** | 真的插上摄像头、真的打印棋盘格去标定。**双目这一整条从未做过**                               |
| **极线误差**      | 立体校正后，同名点应落在同一条水平线上；偏离多少像素就是极线误差。越小越好（验收 ≤ 0.3 px）  |
| **基线 B**        | 两台相机光心之间的距离。**B 越大深度越准，但视场重叠越小**                                   |
| **折算到 1 m**    | 深度误差随距离**平方**增长（`ε_Z ≈ Z²δd/(fB)`），所以必须统一距离才能比                      |
| **配对率**        | 左图检测到的球，能在右图找到对应点的比例                                                     |
| **M0–M8**         | `计划书.md` 里的里程碑编号，M0 环境、M1 标定、M2 同步、M3 三角测量……                         |

推荐顺序（图形启动器里都已经做成按钮，也可走命令行）：

```
1. 相机管理      固定"左/右"到设备身份（免索引漂移）    apps/tools/cameras.py identify
2. 相机探测      核对两路分辨率 / 帧率一致              apps/tools/list_cameras.py
3. 摆放对准      用"标定前置检查"确认两路都看到棋盘、视野重叠
                                                       apps/tools/check_stereo_setup.py
4. 刚性固定      把两台相机锁死在横梁上
                 ⚠️ 这是标定的硬前提：装置一动，解出的 R/T 立刻作废
5. 双目标定      apps/calibrate_stereo.py --left left --right right
6. 标定复检      之后每次拍摄前确认装置没被碰动          apps/verify_stereo.py
```

## 6. 代码结构一眼

    启动程序.bat      根目录唯一入口：环境检查 → 装依赖 → 启动（见 §3）
    启动程序.py / 启动程序_命令行.py   它的两个界面（被 .bat 调用）
    sphere_tracker/   单目核心库：检测 → 跟踪 → 预测（逐帧）
    calib/            双目标定（离线一次）：挑帧 → 标定 → 精化 → 质量判定
    stereo/           双目逐帧：同步 → 成对取帧 → 极线配对 → 三角测量
    apps/             可执行程序（给人用的）
    tests/            回归测试（二十四个，改动后必跑）
    docs/             文档（就是你在读的这些）
    data/             真机录制会话（不入库，必须单独备份）
    config/ outputs/ models/ legacy/    运行期产物与归档（多数不入库）

> **根目录入口 vs 目录规范的取舍**：规则说"可执行程序放 `apps/`"。
> 而 `启动程序.bat` 放在**根目录**，是**有意的例外** —— 它唯一的价值就是
> "让人一眼看到、双击即用"，放深了反而失去意义。它不实现任何算法，
> 只是"检查环境 → 调用 `apps/` 里已有程序"的薄壳，所以不会破坏依赖方向。
> **根目录只有这一个双击入口**（外加它调用的两个界面 .py），不要再加新的；
> 新功能照旧进 `apps/`、`sphere_tracker/`。要"只做某一步"就给它加参数，
> 别再拆出新的 .bat。

**依赖方向是单向的，不要制造环** —— 图与解释见根目录 **`AGENTS.md` §5**（唯一权威）。
一句话版：

```
config/types/geometry → detectors/camera_motion
    → track/predict/sources/viz/camera_registry
    → pipeline → calib → stereo → apps/tests
```

> 反向依赖（比如 `geometry.py` 去 import `pipeline`）会立刻把项目变成一团乱麻。
> **这里不再重复整张图** —— 原来 `文件结构.md` / `开发指南.md` / 本文各画了一遍，
> 三份措辞不同、改一处忘两处，已经导致过文档与代码互相矛盾。

## 7. 三条最省时间的建议

1. **动手前先读 `交接文档.md` §5 踩坑。** 那里记了几十个已经踩过的坑
   （OpenCV 5.0 的 API 变化、相机索引互换、占位符克隆、
   `prs.slides` 不是快照、"先缩放再换算回去"把方向写反导致数值差一个 `s²`……），
   重复踩一次至少半小时。

2. **改完代码必跑回归测试。** 它们是这个项目唯一的质量防线，
   合成真值能抓住大部分回归。（`启动程序.bat test` 快速档约 1 分钟；
   改代码后跑 `test full`，23 个的清单在 `AGENTS.md` §7。）

3. **别信"数字漂亮"就等于"能用"。** 双目所有精度都来自合成场景
   —— 真机的镜头畸变、光照、同步误差都比合成恶劣。
   真机跑通之前，把那些数字当"上限参考"而不是"性能承诺"。
