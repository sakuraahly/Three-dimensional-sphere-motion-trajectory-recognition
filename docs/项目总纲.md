## 1. 一句话说清项目

**用两台普通 USB 摄像头，实时识别一个球形物体在三维空间中的位置，重建它的运动轨迹并预测未来位置。**

拆开是两件事：

|                        | 输入                | 输出                                           |
| ---------------------- | ------------------- | ---------------------------------------------- |
| **看见球**（单目感知） | 一路视频            | 每帧的球心像素坐标、半径（亚像素精度）         |
| **定位球**（双目几何） | 两路视频 + 标定参数 | 每帧的三维坐标 (X, Y, Z)、速度、预测的未来位置 |

关键点：**深度（Z）靠两台相机的视差算出来**，这是"双目"的全部意义。
单目也能靠"球有多大"估深度，但那依赖球径先验，且精度差一个量级。

## 2. 基本功能

### 2.1 两条技术路线并存

```
        ┌──────────────── 单目路线（已跑通、已量化）────────────────┐
        │                                                          │
  一路视频 → 检测 → 跟踪 → 单目测深 Z=fR/r → 二维轨迹 → 预测 → 可视化
        │                                                          │
        └──────────────────────────────────────────────────────────┘

        ┌──────────────── 双目路线（代码已完成，待真机验证）────────┐
        │                                                          │
  两路视频 → 各自走上面的"检测 + 跟踪" → 同步对齐 → 极线配对
           → 三角测量 → 三维轨迹 → （平滑 / 三维可视化：未做）
        │                                                          │
        └──────────────────────────────────────────────────────────┘
```

**"单目感知库 ×2 路"是设计核心**：双目不是另写一套检测，而是把同一套
`sphere_tracker/` 并行调用两次，再由 `stereo/` 把两路合成三维。
所以单目侧的每一次改进，双目自动受益。

### 2.2 单目能做什么

| 能力           | 说明                                                                 |
| -------------- | -------------------------------------------------------------------- |
| **检测**       | 四条互补线索：颜色分割 / 霍夫圆 / 背景差分 / 投票融合；可选 YOLO·SAM |
| **亚像素定位** | 径向一致性判据 + 边缘细化，半径误差 0.06 px                          |
| **跟踪**       | 卡尔曼滤波 + 机动检测 + 反弹重初始化；可应对短暂遮挡与检测失败       |
| **测深**       | 球直径先验 `Z = fR/r`；需要事先标定焦距（有专门工具）                |
| **预测**       | 已知重力约束 + 最长有效后缀拟合，预测 0.1–0.5 s 后的位置             |
| **相机自适应** | 自动探测后端 / 分辨率 / 帧率并缓存；支持手持、云台、平移拍摄         |
| **实时与离线** | 实时窗口交互；也可批处理视频导出 CSV                                 |

### 2.3 双目额外提供什么

| 能力         | 说明                                                 |
| ------------ | ---------------------------------------------------- |
| **双目标定** | 棋盘格 + `cv2` 标定，输出内外参、基线、校正映射      |
| **标定复检** | 判断装置是否被碰动过（未动 0.08 px vs 碰动 27.9 px） |
| **视频同步** | 拍手/闪光求帧偏移，自动对齐两路时间轴                |
| **极线配对** | 把右图搜索从二维降成一维，是双目实时的前提           |
| **三角测量** | 输出三维坐标，并给出交会残差作为可信度指标           |

### 2.4 明确的边界（别误期待）

- **不依赖特定颜色**是设计目标，橙色球只是已验证样例；但颜色线索仍是主力，
  所以拍摄时**曝光/白平衡/焦距必须固定**。
- **三维可视化（Plotly/Unity）尚未做**，两块主要缺口之一。
- **真机标定从未跑过**，这是另一块。所有双目精度数字都来自**合成真值**。
- 目标场景是**实验室条件**（固定机位、良好照明），不是户外或高速工业场景。

## 3. 怎么跑起来

**最省事的入口：双击项目根目录的 `启动程序.bat`（图形界面）或
`启动程序_命令行.bat`（彩色命令行）。** 它们会自动找到 Python 解释器、把下面这些
命令拼好，不需要记任何路径。图形版按"标定 → 参数 → 开始检测"三步走，还带
**标定前置检查**（判断两路是否都看得到棋盘）、相机探测和实时运行日志。

只有当你要命令行 / 脚本化时，才用下面这些原生命令。
只需要能跑 Python，不需要摄像头就能验证环境：

```powershell
# 必须用绝对路径！裸 python 会解析到 msys64 那个没装 opencv 的解释器
$PY = "C:\Users\<USER>\miniforge3\envs\myenv\python.exe"
cd D:\MY_CODING_PROGRAM\Three-dimensional-sphere-motion-trajectory-recognition

# 1) 先跑回归测试确认环境（不需要相机，约 1 分钟）
& $PY tests\selftest_synthetic.py

# 2) 接摄像头实时看效果（不写编号，启动时自动挑最优：优先外接、避开内置/红外、跳过全黑流）
& $PY apps\run_realtime.py --method fusion

#    双目第一次用先固定"左/右"角色（编号会漂移，身份不会）：
& $PY apps\tools\cameras.py identify
& $PY apps\calibrate_stereo.py --left left --right right --cols 8 --rows 5 --square 25
```

完整命令（含双目标定、离线批处理、各工具）见 `交接文档.md` §6 命令速查。
**六个回归测试都必须输出"全部通过"**，这是改动代码后的底线。

### 4.4 三处已知的"阅读陷阱"

1. **两份开题报告文稿的 slide 号对应旧版。**
   写作时报告是 19 页、四节在 slide 11–14；现在是 **34 页、四节在 17–26 页**。
   两份文稿开头都加了换算表，**页码别照抄**。

2. **逐页文稿的"模块对应表"用的是规划中的路径**，
   如 `sync/sync_videos.py`、`stereo/match.py`、`filter/` —— 这些目录**从未存在过**。
   该表已按实际路径重写，以它为准。

3. **不止一处提到"15 mm"，但基准不同**：
   - **15.1 mm** = 单目路线（`selftest_synthetic.py`，球径 22 cm、距离 3.7–4.4 m）
   - **15.6 mm** = 双目整链路（`selftest_stereo_branch.py`，另一套合成场景）

   **数值接近纯属巧合，不可直接比较**。比精度一律折算到同一距离（验收口径是 1 m 处）。

### 4.5 阅读时会撞上的术语

| 词                | 意思                                                                                         |
| ----------------- | -------------------------------------------------------------------------------------------- |
| **合成真值**      | 用程序渲染出来的"假视频"，每个像素的正确答案已知。用于回归测试与精度量化。**不等于真机能力** |
| **真实机 / 真机** | 真的插上摄像头、真的打印棋盘格去标定。**双目这一整条从未做过**                               |
| **极线误差**      | 立体校正后，同名点应落在同一条水平线上；偏离多少像素就是极线误差。越小越好（验收 ≤ 0.3 px）  |
| **基线 B**        | 两台相机光心之间的距离。**B 越大深度越准，但视场重叠越小**                                   |
| **折算到 1 m**    | 深度误差随距离**平方**增长（`ε_Z ≈ Z²δd/(fB)`），所以必须统一距离才能比                      |
| **配对率**        | 左图检测到的球，能在右图找到对应点的比例                                                     |
| **M0–M8**         | `计划书.md` 里的里程碑编号，M0 环境、M1 标定、M2 同步、M3 三角测量……                         |

## 6. 代码结构一眼

    启动程序*.py/.bat 根目录入口：面向人的薄壳（双击 .bat；见 §3 与下方说明）
    sphere_tracker/   单目核心库：检测 → 跟踪 → 预测（逐帧）
    calib/            双目标定（离线一次）：挑帧 → 标定 → 精化 → 质量判定
    stereo/           双目逐帧：同步 → 成对取帧 → 极线配对 → 三角测量
    apps/             可执行程序（给人用的）
    tests/            回归测试（六个，改动后必跑）
    docs/             文档（就是你在读的这些）
    config/ outputs/ models/ legacy/    运行期产物与归档（多数不入库）

> **根目录入口 vs 目录规范的取舍**：`文件结构.md` 规定"可执行程序放 `apps/`"。
> 而 `启动程序*` 放在**根目录**，是**有意的例外** —— 它唯一的价值就是"让人一眼看到、
> 双击即用"，放深了反而失去意义。它不实现任何算法，只是调用 `apps/` 里已有程序的
> 薄壳，所以不会破坏下面的依赖方向。**除此之外根目录不再放脚本**，新东西照旧进 `apps/`。

**依赖方向是单向的，不要制造环**：

```
config / types / geometry          （最底层）
    ↑
detectors/  camera_motion/
    ↑
track / predict / sources / viz
    ↑
pipeline                            （编排）
    ↑
calib → stereo                      （双目，依赖库但不被库依赖）
    ↑
apps / tests                        （只调用，不被调用）
```

> 反向依赖（比如 `geometry.py` 去 import `pipeline`）会立刻把项目变成一团乱麻。
> 细节见 `文件结构.md`。

## 7. 三条最省时间的建议

1. **动手前先读 `交接文档.md` §5 踩坑。** 那里记了十几个已经踩过的坑
   （OpenCV 5.0 的 API 变化、相机索引互换、占位符克隆、
   `prs.slides` 不是快照……），重复踩一次至少半小时。

2. **改完代码必跑六个 selftest。** 它们是这个项目唯一的质量防线，
   合成真值能抓住大部分回归。

3. **别信"数字漂亮"就等于"能用"。** 双目所有精度都来自合成场景
   —— 真机的镜头畸变、光照、同步误差都比合成恶劣。
   真机跑通之前，把那些数字当"上限参考"而不是"性能承诺"。
