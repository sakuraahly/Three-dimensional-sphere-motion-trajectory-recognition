# 界面技术选型论证：要不要把 Tkinter 换成 WebView2 / Electron

> 结论先行：**现在不换，主界面继续用 Tkinter。**
> 不是因为 Tkinter 好，而是因为"换"这件事在本项目的当前阶段**收益为负**。
> 唯一值得将来用 Web 技术重做的局部是 **3D 轨迹视图（`apps/view_3d.py`）**，
> 但那也是答辩之后的事。
>
> 本文的每个数字都有命令可复现，见 §2。

---

## 1. 先把问题问对

这段时间 GUI 报障六次，逐条归因（`docs/交接文档.md` §78–§95）：

| 报障 | 真实原因 | 是"Tk 做不到"还是"Tk 要手写"？ |
| ---- | -------- | ------------------------------ |
| 窗口没有最小化/最大化/关闭 | `transient()` 在 Windows 会清掉 `WS_MINIMIZEBOX/MAXIMIZEBOX` | 要手写（ctypes 补样式），**已修** |
| 分区被遮挡、不能拖 | `ttk.PanedWindow` 的 sash 不跟手 | 要手写，**已修** |
| 预览窗口撑爆屏幕 | 没按屏幕尺寸算 `geometry` | 要手写，**已修** |
| 多路预览互相顶帧 | 单点全局帧队列 | 要手写（每路独立 worker + 帧槽），**已修** |
| 点"预览这台"没反应 | `Treeview` 默认无选中行，按钮空转 | 要手写（默认选中 + 兜底），**已修** |
| **launcher.exe 起点下预览打不开** | **子进程环境差异（run.bat 能、launcher.exe 不能）** | **与 UI 框架无关，未修** |

**六次里五次是"要手写"，一次压根不是界面问题。**
换成 WebView2/Electron，前五次的手写量不会消失——只是从 Python 变成 HTML+CSS+JS；
第六次（进程环境）反而会**变难**：因为排查面从"Python 一个进程"变成
"宿主 + WebView 渲染进程 + 本地 HTTP/桥 三层"。

这是本文最硬的一条论据，也是我不想绕开的一条：**换框架不治当前的病。**

## 3. 三个选项的代价

### A. 继续 Tkinter（现状）

- 增量成本：**0**。
- 已知短板：布局靠 `place/grid` 手写（所以才会"分区被遮挡"）、样式靠 ttk theme 硬调、3D 靠 matplotlib 硬绕。
- 已知优势：**零新增依赖、零新增运行时、离线可用、打包就是一份 conda 环境。**

### B. WebView2（pywebview / 或 C# 宿主）

- 包体：**几乎不增**（复用系统 WebView2 运行时）。这是它相对 Electron 唯一的决定性优势。
- 代价：
  1. **界面要来一遍**。21k 行里的布局与事件全部重写；`_task_runner.py` 这类逻辑层可以留（见 §6）。
  2. **新装依赖** `pywebview`；交付机若被裁剪过、缺 WebView2 运行时，得多带 130 MB 离线安装包。
  3. 逐帧推流不能走 JS 桥（pywebview 的桥是 JSON 序列化，60 次/秒会堵），
     实际要**再起一个本地 MJPEG/WebSocket 服务**——**多一个常驻端口、多一条失败路径**。
     这和当前那个"launcher 起点下打不开"的 bug 是**同一类**问题（进程/端口/环境），
     只是换了个地方发生，而且更难查。
- 适合：想要现代布局与样式，但拒绝 200 MB 包体。

### C. Electron

- 包体：Chromium+Node 本体 **~200 MB 起**；本项目还要在里头捆 Python
  （opencv+numpy+matplotlib 约 400 MB；带 torch 上 GB）。
- 运行时从 **1 个变 3 个**（Node / Chromium / Python），包管理从 1 套变 2 套（npm + conda），
  IPC 从 1 层变 3 层（JS↔Node↔Python）。
- Electron 的强项是：多平台一致、前端生态、自动更新、复杂 SPA。
  **本项目四项全不占**：Windows 单机、一个人用、离线、界面复杂度中等。
- 本机**没有系统 Node**（只有 WorkBuddy 自带那份），构建链本身就要先补一套。
- 对本项目：**纯负债。**

## 4. 决策矩阵

| 维度（权重） | 继续 Tk | WebView2 | Electron |
| ------------ | ------- | -------- | -------- |
| 解决"要手写布局/样式"（中） | ✗ | ✓ | ✓ |
| 解决"当前唯一的未修 bug"（**高**） | — | ✗（变更难） | ✗（变更难） |
| 一次性迁移成本（**高**） | 0 | 4–6 周* | 6–10 周* |
| 交付体积（高） | 小 | 小 | **大** |
| 排障层数（**高**） | 1 层 | 2 层 + 端口 | 3 层 + 端口 |
| 离线可用（高） | ✓ | 基本 ✓（需运行时） | ✓（体积换的） |
| 与答辩的相关性（**最高**） | — | 0 | 0 |

\* 估算口径：按"每天稳定迁移 300–500 行并验证"折算 21k 行界面代码，
再加 20 个入口重新接线、9 个界面测试重写、打包改造。**是估算，不是承诺。**

**答辩相关性那一行是决定性的。** 按 `docs/开题报告_PPT逐页文稿.md` 第 16 页的 16 周表，
未开始的只剩第 13–16 周：对比实验、3D 可视化、论文、答辩。
**拿 4–10 周去换一层皮，等于把论文时间换掉。**
评委看的是极线误差、三角测量精度、轨迹平滑——**没有一条与控件库有关**。

## 5. 什么时候才该换（可检验的触发条件）

不要凭感觉。命中下面任意 **两条** 再动手：

1. **要跑在 macOS / Linux 上**（Tk 能跑，但三按钮与 DPI 又要各写一遍）。
2. **要给不装 conda 的人用**——但注意：那时该先做的是 PyInstaller 打包，
   **不是换 UI**。这两件事经常被混为一谈。
3. **界面要富交互**：拖时间轴联动多视图、实时曲线、轨迹回放 scrub。
4. **Tk 出现"做不到"而不是"难写"**——目前六次报障里一次都没有。

反过来的信号（说明**不该**换）：报障集中在"点了没反应 / 打不开"，
而不是"这块界面做不出来"。**现在正是这一类。**

## 6. 如果将来要换：骨架已经就位，换的是皮不是骨

这是本文唯一让人乐观的部分，也是"现在不换"不算欠债的原因：

- `apps/_actions.py` 是**唯一 argv 产地**（`AGENTS.md` 有硬约束 + AST 扫描）。
  → 任何新界面只要调它，就不会重演"界面说做了、命令行没收到"三次静默缺陷。
- `apps/_task_runner.py` **零 Tk 依赖**，定时轮询用注入的 `schedule` 函数
  （文件头第 9 行明写）。→ 换成 Web 宿主时，任务编排层原样复用。
- `sphere_tracker/` `calib/` `stereo/` 完全不认识界面。
- `visualization.json` 已经是**给网页/查看器用的数据契约**（`apps/export_visualization.py` 第 9 行），
  只是现在没有网页消费方。

**所以正确顺序是：先有"后端与界面解耦"（已完成），再有"换界面"（随时可做）。**
现在换，是把顺序做反。

## 7. 真正值得用 Web 技术的那一块：3D 视图

`apps/view_3d.py` 2,031 行里，**18 处**是在跟 matplotlib 3D 打架：
z 轴永远竖直、3D axes 被无条件收成正方形、刻度画到 axes 外面、
`roll` 参数在 matplotlib < 3.6 不存在、右轴被打断的曲线回接……

这些问题在 three.js / Plotly 里**一个都不存在**，因为它们是原生 3D 渲染器。
而且数据契约（`visualization.json`）已经现成。

**但也不是现在做。** 理由同 §4：它不影响论文评分，而它会吃掉一周。
如果答辩后还有时间，改造顺序是：

1. 写一个独立的 `viewer.html`（three.js，读 `visualization.json`），
   用 `webbrowser.open` 打开 —— **零依赖、不动主界面、可回退**。
2. 觉得好用，再考虑用 pywebview 把它**嵌进**主界面（此时才引入 WebView2）。
3. 主界面其余部分**永远不必换**。
