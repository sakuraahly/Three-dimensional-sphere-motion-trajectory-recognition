# 插件化架构（"一切皆插件"）

> **状态**：**P0–P5 已全部落地**（2026-10-26，24/24 测试通过）。逐阶段的证据见 §7；
> 新增一种实现只需「新建文件 + 一行 `@plugin`」，接口契约见 `API.md` §0b。
> **一句话**：把"按名字选实现"这件事从**散落在 9 处的 if 链**，收成**一张显式注册表**；
> 新增一个检测器/预测器/标定方法，从"改 9 个文件"变成"新建 1 个文件 + 1 行注册"。

---

## 0. 为什么做（不是"为了架构好看"）

审计（2026-10-26，逐行）量出来的账：

| 现象 | 事实 | 后果 |
| --- | --- | --- |
| 同一个清单写四份 | 检测器：GUI 7 项 / `run_stereo_video` 5 项 / `run_all` 4 项 / `run_realtime` help 6 项 | **已经漂移**：用户在不同入口能选的实现不一样 |
| 加一个检测器要改 9 处 | `detectors/__init__.py` 两处 import/`__all__`/if 链、`factory.py` 第二份 if 链、`config.py` docstring + `fusion_members`、GUI `METHODS`、3 个 app 的 `choices`/help、变异测试字面量 | 加功能先要背 9 个位置，漏一个就静默不一致 |
| 视频源装配有三份 | `sources.py:918`、`stereo/pair_source.py:661`、`apps/tools/capture_board.py:188` | 第三份是手抄的，只支持 2 种源 |
| `pipeline.py` 没有注入点 | 构造函数里 `build_detector` / `BallTracker` / `TrajectoryPredictor` 全硬 new（:48-50） | 想换实现只能改 `pipeline.py` 本身 |
| 反向依赖 | `stereo/sessions.py:359` → `from apps.tools.camera_quality import …`（包在 try/except 里静默） | 违反 AGENTS §5；库被 app 绑死 |
| 默认值漂移 | `config.py:116` = `"color"`，而 `apps/cli_main.py:69` = `"fusion"` | 两个入口的默认行为不同 |

**结论**：解耦的目标不是"多一层抽象"，而是**把"有哪些实现"变成可枚举、可校验、只有一处的事实**。

## 1. 核心设计（只做三件事）

新增一个模块 `sphere_tracker/plugins.py`（约 150 行，无第三方依赖）：

1. **`Protocol`**：每个扩展点的最小接口（鸭子类型，不强制继承）；
2. **`Registry`**：`kind → name → factory`，全局唯一一张；
3. **`resolve(kind, name)`**：拿实现；拿不到就抛 `UnknownPlugin`，**列出可用项**。

```python
from sphere_tracker.plugins import plugin, names, default, resolve, describe

@plugin("detector", "color", summary="颜色阈值（球色明显时最快）", default=True)
def _build_color(cfg) -> BaseDetector: ...

build = resolve("detector", "specular")   # 未知名字 -> UnknownPlugin（带候选清单）
```

`names("detector")` 取代所有手写清单：GUI 下拉、CLI `choices=`、`--help` 文本**都从这里取**。

## 2. 七条规则（这是"插件化不把项目搞烂"的边界）

| # | 规则 | 为什么 |
| --- | --- | --- |
| **R1** | 注册**显式**发生（import 时执行装饰器），**不扫描目录、不用字符串 import** | 可静态分析、可打包、改名不会静默失效 |
| **R2** | 名字在 kind 内唯一；重复注册默认**报错**，`replace=True` 才允许且必须写理由 | 静默覆盖 = 又一个"看不出来"的坑 |
| **R3** | 找不到就抛 `UnknownPlugin`，**列出候选**；**绝不 fallback 到默认** | 拼错名字时给出默认实现，比报错危险得多 |
| **R4** | 每个 kind **恰好一个** `default=True`；没有默认就用 `default()` 时报错 | 默认值不允许"看 import 顺序" |
| **R5** | 插件实现**不许 import `apps/`**；库内不做反向依赖 | AGENTS §5 是硬约束，用 AST 测试守住 |
| **R6** | 每个插件必须写 `summary`，并声明 `needs=()`（必需的可选依赖） | GUI/CLI 直接拿来当 help；缺依赖的项可灰掉而不是运行时报 ImportError |
| **R7** | 注册表是**唯一**选项来源；任何地方再出现"检测器名字清单"即视为缺陷 | 这就是四份清单漂移的根因 |

## 4. 注入点（`pipeline.py`）

```python
Pipeline(cfg, *, detector=None, tracker=None, predictor=None)
```
不传则从注册表按 `cfg.xxx.method` 取。**默认行为完全不变**，只是把"new 哪个类"从构造函数里挪出去。
这一步让单测能注入假实现（不用真开相机、不用真跑检测），也让"换实现"不需要改 `pipeline.py`。

新增 `tests/selftest_plugins.py`（第 24 个）：
1. 注册表不变量：名字唯一、每 kind 恰一默认、`summary` 非空、`resolve` 未知名字抛错且候选齐全；
2. 每个已注册实现能被**构造**（不跑推理），`needs` 缺失时给的是明确错误而不是 ImportError；

## 6. 明确不做

- **不做 pip entry_points / 第三方插件包**：当前是单仓研究代码，跨包分发没有收益，反而让"有哪些实现"变成运行时才知道。
- **不做目录自动扫描**：`pkgutil.walk_packages` 那种"看起来很方便"的做法，会让 import 顺序、打包、静态分析全部失控。
- **不重排目录**：`AGENTS.md` §5 已审计过分层清晰，插件层只是**替换分派方式**，不动依赖方向。
- **不动数值路径**：本改造是"选实现的机制"，不碰任何算法参数；`selftest_stereo_calib` 等数值断言必须逐位不变。
- **颜色预设不做成第七个 kind**（2026-10-27 判断）。它看起来很像插件（"名字 → 一份实现"），
  但预设是**数据**（一组 HSV 区间），不是可替换的算法；硬塞进注册表要把它包成工厂函数，
  还得给它编一个"默认项"——而 R4 要求每个 kind 恰好一个默认。真正的病根不是"没进注册表"，
  而是 `ColorConfig.preset()` 把表藏在函数体里，**没有任何出口告诉别人"有哪些预设"**，
  于是被抄了三份（CLI 帮助 / HSV 工具的数字键表 / GUI 下拉）。
  修法是补出口：顶层 `COLOR_PRESETS` + `preset_names()`，各方读它。
  **有出口就够了，不必为了形式统一去加一层间接。**
