## 1. 这是什么 / 能做什么 / 不能做什么

### 1.1 一句话

**用两台普通 USB 摄像头（双目），实时识别一个球形物体在三维空间中的位置，重建它的运动轨迹，并预测未来位置。**

深度（前后距离）不是靠"球看起来多大"猜的，而是靠**两台相机的视差**算出来的 —— 这才是"双目"的全部意义。

### 1.2 能做什么

| 能力 | 说明 | 怎么用起来 |
| --- | --- | --- |
| **检测** | 四条互补线索：颜色分割 / 霍夫圆 / 背景差分 / 投票融合；可选 YOLO·SAM | `--method fusion`（默认） |
| **亚像素定位** | 径向一致性判据 + 边缘细化，半径误差 0.06 px 量级 | 默认开启，无需操作 |
| **跟踪** | 卡尔曼滤波 + 机动检测 + 反弹重初始化，能扛短暂遮挡与漏检 | 默认开启 |
| **单目测深** | 球直径先验 `Z = f·R/r`，需先标定焦距、量准球径 | `--ball-diameter` + `--focal` |
| **轨迹预测** | 已知重力约束 + 最长有效后缀拟合，预测 0.1–0.6 s 后的位置 | `--horizon`（默认 0.6 s） |
| **双目三维** | 棋盘格标定 → 视频同步 → 极线配对 → 三角测量 → 输出 (X, Y, Z) | 见 §4 六步流程（真机标定已跑通、有 2 份产物，但整条链路尚未端到端验证） |
| **实时与离线** | 实时窗口交互；也可批处理视频/图片并导出 CSV | `run_realtime.py` / `run_video.py` |

### 1.3 不能做什么（先看清楚，省得白忙）

| 限制 | 说明 |
| --- | --- |
| **不依赖特定颜色只是目标，颜色仍是主力** | 橙色球只是已验证样例；球与背景同色时检出率会掉 |
| **拍摄时曝光 / 白平衡 / 焦距必须固定** | 颜色线索靠阈值，自动曝光一抖阈值就废了 |
| **三维视图分两档** | 单目实时只有俯视/侧视小面板；**双目实时**（平行/大角度窗口第③步「实时 3D（不落盘）」）在并排画面上内嵌一块三维小图（`3` 键开关）；**可交互的三维轨迹仍要离线看** —— 录完用 `apps/view_3d.py`（轨迹视频与 3D 同步播放，见 [`3D查看器.md`](3D查看器.md)） |
| **标定按装置档案分文件**（2026-11-11 更新） | 每套装置一份，落在 `config/calib/<装置档案名>.npz` + `.json`；**数值以当前激活档案那份 `.json` 为准**，本文只做指引。顶层 `config/stereo_calibration.*` 是 2026-11-03 的旧产物（基线 66.3 mm），只在档案没配 `calibration_path` 时才会被用到 —— 它不是"当前装置的几何"。哪套档案有标定、当前激活的是哪套，见 §15.2 |
| **多球跟踪没做** | 现在跟的是"一个球"，画面里两个球会互相抢 |
| **双目实时已接进主流程，但有边界**（2026-11-16） | 各双目窗第③步「实时 3D（不落盘）」→ `run_realtime_stereo`：两路实时采集 + 逐帧三角化，960 宽下 32–40 fps。**没有硬件同步**：只能测出两路时间差并做一阶补偿，超过 60 ms 的那一对直接丢弃；精度是**毫米级**（f≈700、基线 150 mm 时 1 px 视差 ≈ 2.4 mm @0.5 m），不是亚毫米；只支持 `color` / `motion` |
| **不适合户外 / 高速工业场景** | 目标是实验室条件：固定机位、照明良好、球完整可见 |

## 2. 三步跑起来

### 2.1 环境要求

Windows 上已配好，**不需要额外安装任何包**。Python **必须用绝对路径**：

```powershell
$PY = "$env:USERPROFILE\miniforge3\envs\myenv\python.exe"
cd D:\MY_CODING_PROGRAM\Three-dimensional-sphere-motion-trajectory-recognition
```

> ⚠️ **别用裸 `python`**：它会解析到 msys64 那个没装 opencv 的解释器，报 `No module named 'cv2'`；下面所有命令都复用 `$PY`。

### 2.2 根目录的四个入口：先装 Python → `install.bat` → `run.bat`

> **第 0 步：机器上先有一个能运行的 Python 3.10+。** 安装器靠它自举，
> 完全空白的机器装不了。没有就先装：
> - Miniforge（推荐，自带 conda）：https://github.com/conda-forge/miniforge
> - python.org 官方版：https://www.python.org/downloads/
>
> 装好后**双击 `install.bat`** 建环境，环境就绪再**双击 `run.bat`** 启动。

项目根目录有四个入口，按用途分工：

| 入口 | 用途 |
| --- | --- |
| `run.bat` | **主入口**：双击启动图形界面；加参数可直接做某一步（`cli` / `setup` / `check` / `calibrate` / `install` / …）。参数路由的唯一产地 |
| `install.bat` | **首次安装**：转发 `run.bat install`，调 `apps/setup_env.py` 建/复用环境并登记给所有入口 |
| `uninstall.bat` | **卸载**：只把自身所在的分发目录送进 Windows 回收站；拒绝开发仓库目录，需手输 `UNINSTALL` 二次确认 |
| `launcher.exe` | **可选无黑框启动器**（编译产物，不是脚本）：开发机上双击可静默起新 GUI；纯净分发包里**没有**它，要用得自己用 Go 重建；安装完成后的正式启动入口是 `run.bat` |

`run.bat` 启动器会做三件事：

1. **找 Python** —— 不是随便找 `python.exe`，而是逐个候选**真的试一次
   `import cv2, numpy`**，谁通过用谁。所以 PATH 里那个没装 opencv 的 msys64
   Python 会被自动跳过，你不会再看到 `No module named 'cv2'`；
2. **缺依赖就问一句，然后自动装** —— 找不到可用的 Python 时，它会找到任何一个
   能跑的 Python，问你一句要不要装，同意就用清华镜像装 `requirements.txt`
   （镜像失败自动退回官方源），装完复验 `import cv2`；
3. **启动界面** —— 默认图形界面；这台机器没有 `tkinter` 就**自动换成命令行界面**。

启动时会打印实际用的解释器与版本，例如：

```
[1/3] 检查 Python 环境 ...
      找到：%USERPROFILE%\miniforge3\envs\myenv\python.exe
      Python 3.14.7 / opencv 5.0.0 / numpy 2.5.3
[3/3] 启动图形界面 ...
```

#### 只想重做某一步？给 `run.bat` 加一个参数

**不需要额外记别的文件**。在文件夹里按住 Shift 右键 →"在此处打开 PowerShell 窗口"，
或者直接在地址栏敲 `cmd` 回车，然后：

```bat
run.bat            :: 图形界面（默认，等于双击）
run.bat cli        :: 命令行界面
run.bat setup      :: 相机设置（左 / 右 / 无关）
run.bat check      :: 相机检查（有没有漂移）
run.bat precheck   :: 标定前置检查（两路是否都看到棋盘）
run.bat calibrate  :: 双目标定
run.bat verify     :: 标定复检
run.bat run        :: 实时检测
run.bat test       :: 回归测试（默认快速档，约 1 分钟；加 full 跑全套 29 个）
run.bat install    :: 建/复用环境并装依赖（等于双击 install.bat）
```

> **日常使用不必敲这些**：双击 → 图形界面第 1 步就有
> 刷新并检测相机、相机设备管理（识别 / 固定 / 标无关）、相机探测、
> 标定前置检查、运行标定 / 复检、「无关」相机清单 等按钮，
> 参数化只是给"反复重标定"这种场景省两下点击。
>
> ⚠️ **2026-10-18 起**：原来的『刷新设备列表』**只枚举、不开相机**，
> 『检查相机映射』**只比配置** —— 两者都回答不了"相机现在活着吗"，
> 已合并为 **『刷新并检测相机』**（刷新下拉 + 自动跑一次真开相机的探测）。
> **2026-10-28 起（B-95）**：打开界面时**只枚举设备、不打开相机** ——
> 相机灯不亮、也不会白等约 24 秒；要实测"到底能不能出图"才点这个按钮。
> 配置漂移检查没有消失：它在**每次标定 / 复检前自动执行**，失败会弹窗拦住。

**这些参数与图形界面里的按钮是同一套命令**，界面与经过测试的底层链路始终一致。

> **为什么参数只有一个产地**：`.bat` 不适合承载逻辑（没有数组/异常，字符串处理靠
> `for /f` 硬凑），菜单必须活在 Python 里；而"图形 / 命令行"只是同一套菜单的
> 两种呈现，所以用 `cli` 参数区分，不额外给命令行版一个文件。`install.bat` 只是
> 转发 `run.bat install` 的薄壳，`uninstall.bat` 是只认自身目录的卸载薄壳，
> 不在第二个 `.bat` 里复制一份参数路由逻辑。
> 详见 `docs/文件结构.md` 根目录段与 `docs/决策记录.md` 2026-11-05 条。

#### 「无关」是什么

一台相机有三种**并列**的明确去处 —— 在 `identify`（图形界面第 1 步的
『相机设备管理（识别/固定/标无关）』，或 `run.bat setup`）的画面里按键：

| 按键 | 含义 |
| --- | --- |
| `l` | 这台是**左**相机 |
| `r` | 这台是**右**相机 |
| `n` | 这台**「无关」** —— 永远不要用它 |
| `m` | 单目**主**相机（只看一路时用） |
| `s` | 跳过，不改配置 |
| `q` | 退出 |

**「无关」的用处**：笔记本内置相机、红外相机这类**不该参与双目**的设备，
标一次就再也不用管 —— 自动挑相机（`--auto-cameras`、`--camera auto`）
会跳过它们，不会再出现"左边是外接、右边却挑到笔记本内置"。

- 左 / 右 / 无关**三者互斥**：改标一个，旧标记自动摘掉（不可能既是左相机又是「无关」）。
- 记的是**设备身份**，不是编号 —— 换 USB 口之后标记依然有效。
- **2026-11-20 起：`#N` 是 PnP 枚举位次，不是 OpenCV/MSMF 采集索引。**
  角色按设备身份绑定；真正打开相机用 `role.capture_index`，它必须由
  `python apps/tools/cameras.py identify` **实开一次**写入。未实测时按角色名
  启动会**明确拒绝**并指到 `identify`，不会拿枚举位次猜（那正是"显示的和真实
  的对不上"的来源）。相机管理里新增「位置」（床 / 阳台门）和「采集索引
  （未实测）」列；vivo 原子笔记 / OBS 等虚拟摄像机会标「虚拟，不参与绑定」。
- 万一**其它相机都不够用**，程序会**兜底动用**「无关」的相机，但一定会打印警告 ——
  它不会静默用错，也不会让你空手而归。
- 显式写编号（`--camera 3`）**仍然会用它**：你点名的那台优先级最高。
- 管理：`& $PY apps\tools\cameras.py ignored` 看清单、
  `unignore 3` / `unignore --all` 取消；图形界面有对应的
  `「无关」相机清单` / `清空「无关」标记` 两个按钮。

#### 「哪类名字算内置/红外」是可配置的（2026-10-18 起）

自动挑相机会**降权**"名字看着像内置/红外"的设备。这两条判据现在都在
`config\cameras.json` 的 `settings` 里，**不用改代码**：

```json
"settings": {
  "avoid_names": ["Integrated Camera", "Integrated IR Camera"],
  "avoid_name_patterns": ["infrared", "\\bir\\b"]
}
```

- `avoid_names`：**子串**匹配（不区分大小写）；
- `avoid_name_patterns`：**正则**匹配；
- 两者是"或"关系，命中任一即判为不适合双目；
- **换了一台名字里带 `IR` 的正常相机、被误伤了？**
  把 `avoid_name_patterns` 设为 `[]` 即可整体关掉红外启发式；
- 正则写错了不会让程序崩：**跳过那一条并打印警告**，其它规则照常生效。

> ⚠️ **但 2026-10-14 更正过一次结论，值得记下来**：我一开始把那次失败

### 3.1b 双目实时三维检测（2026-11-16）

在「平行双目」或「大角度双目」窗口的**第③步**点「实时 3D（不落盘）」，或直接跑：

```
& $PY apps\run_realtime_stereo.py --left 0 --right 2
```

它同时开两路相机，每帧做「检测 → 极线配对 → 三角测量」，并把两路画面并排显示。
**最右一列是三维小窗**，独占一列、不叠在相机画面上（2026-11-17 修：以前它贴在
右画面的右上角，轨迹一跳起来就盖住画面）。

窗口**顶栏是两行**：第一行是这一对的指标，第二行常驻按键提示
（`q 退出 · 空格 暂停 · 3 三维小窗 · v 录制 · s 快照 · c 切方法 · f 全屏 · r 重置`）。
主界面的底部状态条只放一句话 —— 长提示会被窗口宽度截断，所以按键说明放画面顶栏。

> **为什么入口在各装置窗口里、不在门厅**：实时与离线是**同一套装置**的两种处理方式 —— 录一段去第④步离线跑，或者直接开相机出三维。门厅放的是跨模式的工具（相机、数据、档案），装置自己的处理方式应该跟着装置。单目窗也是这个结构：第③步「识别来源」里有「实时（相机）」和「录像」两项，二选一。
**默认 `--detect-width 960`**：全分辨率下 `color` 单路 17.8 ms、两路就 35.6 ms，
帧率会掉到 20 fps 以下 —— 而“实时”才是这个入口的意义所在。

| 键 | 作用 |
| --- | --- |
| `q` | 退出 |
| `空格` | 暂停 / 继续 |
| `3` | 开/关内嵌三维小窗（画的是三角测量出来的真实三维点） |
| `v` | 录制并排画面到 mp4 |
| `s` | 快照（标注图 + 两路原图） |
| `c` | 切检测方法（只有 `color` / `motion` 可选） |
| `f` | 全屏 |

HUD 上多一行双目指标：`match 87%  res 0.8 px  disp 42.1 px  skew +12.3 ms  drop 3`。

**检测方法与颜色预设跟着第①步的球种类走**（2026-11-17 补）：

- **纯色塑料球** → `color`（HSV 阈值 + 形态学 + 轮廓）。用你在第①步选的**球色预设**；
  不选就是**白/浅色球**默认档（`V>175`、`S<80`）—— 红球/橙球的饱和度远高于 80，
  用默认档必然 0 检出。启动时窗口会打一行 `[颜色] … 生效阈值 H… S… V…`，
  先看这一行对不对，比盯着黑屏猜快。
- **镜面金属球** → 实时**不可用**：它要 `specular`，而 specular 靠 `seeds.json` 里
  「点选球心」的种子（只在高光附近找，不会自己初始化），实时没有种子。
  按钮会直接拦住并说明 —— 正确路径是「录一段 → 点选球心 → 第④步离线跑」。

**大角度装置**没有「视差」这个量（它用原始像素 + 基础矩阵配对），所以那一段改成
`epi 1.2 px  ang 41°`（极线距离 / 交会角），`disp` 写 `n/a` —— 不把角度下的数硬塞进
「视差」这个名字里。三维小窗的标题也会写 `3D angled (raw pixels)`，因为它的坐标系是
**原始左相机系**，与平行装置的校正后坐标系不能直接比。

- **`skew`** 是这一对帧两路采集时刻之差（正数 = 右路更晚）。没有硬件触发线时它**不可能为 0**。
- 程序会把**较晚那一路**的圆心按它自己的像素速度外推回较早时刻，再做配对（一阶补偿）。
  合成数据实测：右路人为延后 33.3 ms 时，三维 RMS 从 **665 mm 降到 32 mm**。
- 但**加速段补偿不干净**：5 m/s² 加速时残差仍有 ~65 mm。看到 `skew` 大、或球在急停急转，
  就该怀疑这一帧的数。
- `abs(skew) > 60 ms`（`--max-skew-ms` 可调）或任一路掉线 → **这一对直接丢弃**，不产出三维点，
  `drop` 计数加一。拿冻结帧硬算出来的点比没有点更糟。
- `--no-skew-fix` 可关掉补偿做 A/B 对比。



**重建器按标定自动选，没有开关**：标定 JSON 里 `stereo_mode=angled`（或标成 parallel 但
`rectification=none_raw` 的错标定）→ 走 `AngledReconstructor`；其余 → 走极线校正后的
`StereoReconstructor`。不提供 `--mode`，因为一旦能选，就能把它和标定写反 —— 用错几何
还自以为选对了。分不清时它会明确拒绝，并告诉你该重标还是该改标定。
**实时跑完会自动留一段会话**（2026-11-17 新增）。退出时写到
`data/stereo/<parallel|angled>/<时间戳>/`，内容是：

| 文件 | 有什么用 |
| --- | --- |
| `session.json` | 身份/装置/标定/帧数，带 `source: "realtime"` |
| `derived/traj3d.csv` | 15 列轨迹（`frame` 与视频帧号一一对应） |
| `derived/seeds.json` | 自动取第一对匹配点当种子（`source="realtime"`） |
| `derived/traj3d.json` + `visualization.json` | 3D 查看器就认这两个 |
| `derived/annotated.mp4` | **纯左右并排**（2:1），供查看器做轨迹与画面同步 |

于是：**数据管理**里会出现一条名称带「实时 ·」的会话，状态是 ✓ 有三维，
双击能在 **3D 查看器**里看轨迹、并跟着视频走。两条边界要说清：

- **它没有原始左右录像**，所以第④步「跑离线三维」会被拦住（否则等于让你白等一次
  注定失败的进程启动）。要能重算，就用第③步「开始录制」录一段。
- 三维点 **少于 30 个不落盘**（免得点开看一眼就在列表里留一条空会话）。
  `--no-save-session` 可以完全关掉；想省帧率也可以关它或调小 `--display-width`。

> 代价是实的：默认 `--display-width 1600` 下，写这段视频让每对帧多耗 **约 4.6 ms**
> （约 47 → 39 fps），因为每对多一次 `hstack` + 一次 mp4v 编码。

**窗口里的两个录制键不一样**（2026-11-17 加）：

| 键 | 写出什么 | 用途 |
| --- | --- | --- |
| `v` | 一份**检测画面**（`outputs/videos/stereo_<时间戳>.mp4`） | 回看检测效果 |
| `b` | 三份：检测画面 + `_raw_left.mp4` + `_raw_right.mp4`（**未绘制**的原始两路） | 需要原始画面留证 / 二次分析 |

`b` 比 `v` 多两次 1920×1080 编码，录制期间帧率会明显下降——只在真需要原始画面时用。
两者都只是**视频**，不是会话；会话仍然是按 `q` 退出时自动落的那一份。

> 退出码 2 的四种情形：标定缺失 / 标定读不出 / 标定是 `none_raw`（未极线校正）/ 相机实际分辨率与标定不符。
> 最后一条是刻意加的护栏：内参对不上时三角测量照样“出数”，每个点的深度按比例错而且看不出来。


`modes` 是**实测**，不是读驱动声明：它按 `capture_index` 逐档打开、读真帧、
数帧测 fps，并明确报告 `fell_back`（请求 2560 实际 1920）。整场只用一个后端；
不写 `config\cameras.json`，也不写 `config\camera_modes.json`。

**筛选门限**（`config\cameras.json` 的 `settings`，也可在相机管理窗口底部改）：
`min_width` / `min_height` / `min_fps` / `min_pair_fps`。`min_fps` 只在帧率
**数帧实测**时生效；`min_pair_fps` 留空 = 沿用 14.4。它们只影响**自动挑相机/
成对协商**，不影响已绑定角色。

**采集 API**（2026-11-21 新增，默认仍是 OpenCV）：
- `--capture-api opencv`（默认）：原 `cv2.VideoCapture(N)` 路径，行为不变；
- `--capture-api mf`：按设备 **symbolic link** 打开（Windows Media Foundation），
  不再依赖整数编号；需要 `--left left --right right` 这种**已绑定角色**；
- `--capture-api auto`：角色有 identity/端口时先 MF，失败打印警告后回退 OpenCV。
- 显式数字编号（`--left 0`）只能用 `opencv`。
- 当前限制：左相机 MF native 只有 1920×1080 NV12，双路 MF 实测约 15 fps；
  所以默认不切 MF，等左相机恢复 MJPG 后再评估。

`identify` 窗口按键：`l`=记为左相机、`r`=记为右相机、`n`=标为**「无关」**、
`m`=记为单目主相机、`s`=跳过、`q`=退出。**左 / 右 / 无关 三者互斥**，
改标一个会自动摘掉旧的（一台相机不可能既是左相机又是「无关」）。
「无关」的用途与行为见 §2.2 末尾。

#### ⚠️ 笔记本内置相机：**挡住它 / 贴住它**是常用做法，那时它会"打不开"

本机的**内置相机已被用户用遮挡物盖住**（有意为之，不参与双目）。
被遮住的相机在这个工具里表现为**"打不开"**：

```
#N 打不开：摄像头 N 用 MSMF 能打开，但一帧都拿不到
#N 打不开：无法打开摄像头 N，已尝试全部后端与分辨率   （DSHOW 侧：出帧但恒为纯黑）
```

**这不是故障，是预期行为** —— 没有光进来，就没有画面。
**处置：在 `identify` 里给它按 `n` 标成「无关」**（或者本来就已被标上），
之后自动挑相机就会跳过它。

> **怎么一眼认出是内置相机？** 两条判据，任一条成立即可：
> - **名单**：它的名字里有 `Integrated`（`Integrated Camera` / `Integrated IR Camera`）；
>   而外接的两台是 `aoni webcam A25`。
> - **画面**：把镜头盖住 / 正对桌面，**哪一台变黑就是它**。
>
> **别把"打不开"当成相机坏了**：先看名字。`aoni` 那两台打不开才需要查
> （见下面「相机打不开」那一行）；`Integrated` 那台打不开通常就是被挡住了。

> ⚠️ **`identify` 里"打不开"的相机不会让你按键**，于是有个陷阱：
> 如果**恰好只有一台能用**，你可能把同一个画面按两次、把**两个角色记成同一台**。
> 工具现在会在写盘后**检查两个角色是否指向同一台**并报警；看到那条警告就说明
> 得先把另一台弄出图（或把它标「无关」）再重来。

#### 两台外接相机现在是**不同名字**（2026-10-18 起的方案）

本机两台 aoni 已在系统里**改名**，名字唯一且自带左右标识：

| 名字 | 端口 | 角色（`config/cameras.json`） |
| ---- | ---- | ---------------------------- |
| `aoni webcam A25 left`  | `6&31324e2c&0&0000` | `left` |
| `aoni webcam A25 right` | `6&4489382&0&0000` | `right` |
| `Integrated Camera` / `Integrated IR Camera` | — | 「无关」 |

**为什么这么做**：**改名前**两台都叫 `aoni webcam A25`，而名字是唯一一个
"人能直接读懂"的标识 —— 同名时只能靠**端口串**区分，肉眼看不出谁是谁。
改名后 `list` / `identify` 的标签一眼可读，也就能在**目视确认**这一步少犯错。

**怎么查当前名字**（不开相机，秒级）：

```powershell
run.bat check                      # 顺带打印解析到的设备
& $PY apps\tools\cameras.py list         # 逐台列出 名字 / 端口 / 身份
```

**⚠️ 名字唯一 ≠ 可以只靠名字**：`cameras.py` 的匹配顺序仍是
**身份（`id:`）→ 端口（`port:`）→ 名字**，因为……

- 名字**可以被改**（改完旧配置就对不上了），而 `InstanceId` 不会；
- 换 USB 口会让 `InstanceId` 变（端口串嵌在里面）；
- 当前代码**不允许"确认过的角色"退回按名字匹配** —— 所以换口后 `check` 会报
  "解析失败"而不是自动找回，**这是有意的**（宁可报错，也不静默用错相机）。
  换口后**按名字重新绑一次**即可（见下）。

#### ⚠️ `identify` 窗口上的名字是**推测**，不是事实

`cv2.VideoCapture(编号)` **只能按编号打开相机，名字根本不参与**。
窗口上那行 `#N 推测:<名字>` 是"编号 N ↔ 设备列表第 N 台"这个**假设**的产物。

而这个假设**在两台同型号相机之间无法被程序证明**（它们同 VID/PID、同分辨率）——
所以你完全可能看到 **"命名为 right 的相机，画面上却是 left"**，那是标签错了，不是相机坏了。

**可靠的做法：按名字绑角色，完全不开相机、不碰编号：**

```powershell
& $PY apps\tools\cameras.py pin left  name:"aoni webcam A25 left"
& $PY apps\tools\cameras.py pin right name:"aoni webcam A25 right"
```

（名字可以写全，也可以写唯一的短串如 `name:left`。`pin` 按**设备身份**解析，
所以之后重插、换口都不影响已绑定的角色。）

> ⚠️ **"改名字" ≠ "告诉程序用哪台"。** 改名改的是 Windows 里那台设备的
> FriendlyName，它帮我们**认设备**，但不会改变程序**按编号打开**的事实。
> 要改角色，用 `pin`（或 `identify` 目视确认），**不要指望改名能影响程序行为**。
> 名字里写 `left`/`right` 只是**给人看的**。



> `pin` / `ignore` / `unignore` 的取值都支持四种写法：
> 索引（`3`）、`port:Port_#0001.Hub_#0003`、`id:USB\VID_...`、`name:aoni`。
> **优先用 `port:` / `id:`** —— 索引会漂移，身份不会。

```powershell
& $PY apps\tools\make_calibration_board.py --all      # 常用组合，输出到 assets\boards\
& $PY apps\tools\make_calibration_board.py --cols 8 --rows 5 --square 25 --page a4-landscape
```

### 3.5 双目标定与复检

#### 自动 FOV 对齐（两台相机视场不一样）

本机两台相机的**出厂视场不同**（左路比右路约放大 1.5 倍）。不做对齐就把两路按同一视场混用，像素尺度不一致会污染视差和深度；所以标定默认会先自动对齐一次。

> **2026-11-15 起是「装置级应用开关」**：FOV 管理器里「把这份 FOV 应用到当前装置
> 的左右相机」与双目窗第②步「把 FOV 应用到当前装置的左右相机」是**同一个开关**
> （都读写装置档案的 `fov_apply`，**默认关**）。「启用」= 把这份参数应用到当前装置
> 的两路相机画面上，是一个**装置级事实**，不是「标定时用不用」「录制时用不用」两个
> 流程开关：**标定与录制都服从它**。关 = 标定带 `--skip-fov` 按原始画面、录制不裁剪；
> 开 = 平行标定复用档案参数、录制按它裁剪两路；90° 装置即使开也不裁剪（两路几乎
> 不共视）。开但标定 JSON 的 `fov` 为 `null`、或与档案不一致时，录制**退出 2 拒绝**，
> 绝不静默回退成「照旧录制」。判定见 `stereo/fov_policy.py`。

| 问题 | 说明 |
| --- | --- |
| **做什么** | SIFT（失败自动换 ORB）+ homography 估计两路共同视场；**较窄、更放大**的一路当参考（不裁剪，但可能降采样），**较广**的一路裁到参考视场内的矩形；两路统一到**不放大任何一路的共同尺寸** = 参考帧与裁剪区逐轴取小、**再向下取偶**（无损 MKV 只支持偶数宽高）。这样不会把约 1685x979 的裁剪区上采样成 2560 导致模糊；参考路则由 2560 降采样到共同尺寸。两路本来就同视场时返回 `crop_side="none"`，不裁不缩 |
| **什么时候跑** | 只在 `calibrate_stereo.py` **启动时**：实时相机最多读 30 帧或约 5 秒，视频 / 图片用第一对有效帧；**只估计一次**，结果写进标定 `meta["fov"]`；之后每一帧都先归一化再检测角点（`--save-pairs` 另存的也是归一化画面），标定、录制、复检都复用这份记录（代码读 `rig.meta["fov"]`），不重估对齐参数；复检的视频 / 图片输入只在首对帧额外估一次，用于**验证输入已归一化** |
| **启动打印** | 参考路（较窄）/ 裁剪路 / `crop_rect` / 放大倍数（`max(scale, 1/scale)`）/ 较广一路保留的面积百分比，以及实际用的检测器与内点数 |
| **代价** | 只裁较广的一路：保留面积 = `(w×h)/(W×H)`，即共同视场只占较广一路约 **44–46%**（1.5× 视场差理论约 `1/1.5²≈43%`）；2026-10-24 本机两帧实测裁 `(409,126,1717,986)`（右路 2560×1440），保留 **45.9%**（约 54% 被裁）；**共同输出 = 裁剪区尺寸向下取偶**（本次 **1716×986**；另一次估计裁剪区 1685×979 -> **1684×978**），参考路从 2560×1440 **降采样**到该尺寸（不再原样保留），两路都不放大 |
| **标定前** | 两路同时看到**有纹理的同一场景**（标定板 / 桌面细节），光照均匀、对焦清晰、重叠足够；标定板要放在**两路共同视场**内（较广一路被裁掉的外圈不算），且**较窄一路的画面要完整落在较广一路视场内**（四角映射越界 > 16 px 视为共同视场不足，直接报错）。视频 / 图片输入也用它第一对有效帧估计，起始帧不能是空白 / 纯色 |
| **失败** | 读不到成对帧或估不出来 -> 打印原因并**退出 1**，**不会退回原生分辨率继续标定**；调好纹理 / 光照 / 对焦后重试 |
| **重新标定** | 换相机、换镜头、改分辨率或重新固定相机后必须重标；对齐参数与当前装置绑定，标定和录制都用同一份归一化画面，不要先按原生画面标定再裁视频 |
| **旧标定 / 旧会话** | 没有 `fov` 记录的旧标定按**原生画面**工作，行为和以前完全一样；旧的 1080p / 1440p 会话照常可读 |
| **新录制** | 两路视频已经是**归一化画面**，离线双目处理不要再裁；录出分辨率 = `fov.target_size`（当前一对约 **1684×978**，不是 2560×1440；相机仍按 2560×1440 打开）。`fov` 记录无法解析（含 `{}` / `[]` / 非 mapping），或启用对齐时 `target_size` 与 `image_size` 不一致、`crop_rect` 超出采集帧、`target_size` 大于裁剪区（旧版会放大的记录）或含奇数宽高，录制在写盘前**退出 2**，重新标定 |
| **视频 / 图片复检** | 首对帧会再估一次 FOV，证明输入确实已归一化：如果仍需要主动对齐（原生画面）、尺度不在 0.9–1.1，或纹理不足估不出来，复检**退出 2**，不静默假定、也不二次裁剪；确认输入已归一化时加 `--fov-input-normalized` 显式跳过校验，否则请用 `record_stereo.py` 以同一标定重录归一化视频 |

> **验证到哪一步（2026-10-24）**：模块级真机画面验证通过 —— 左路（较窄）为参考、右路裁 `(409,126,1717,986)`、`scale≈0.651`，对齐后残余尺度 **0.966**（目标 1.0，两路视觉尺度基本一致），17/17 项检查通过；但**这次验证跑在旧版（把裁剪区放大到 2560）上** —— 改成共同（不放大）尺寸后，真机帧对与清晰度门限 55 需重验；而且**“标定 → 录制 → 复检”（含自动 FOV）这条链还没有在真机上跑过一轮 E2E**，上面的数字不能当标定 / 三维精度承诺。

### 3.7 设世界系（把三维轨迹落到地面）

三维轨迹默认落在**相机系**（原点在左相机光心、X 右 / Y 下 / Z 前），只能看形状；
要让"高度"是相对地面的，得拍一张**棋盘平放在地面上**的左相机图，算一次
`T_world_cam` 落盘到 `config\world_frame.json`。这是**一次性离线标定**：拍一张、
算一次，之后运行期只读这个文件（定义与符号见 `docs/数据标准.md` §6「世界系」）。

**拍图要求**（有一条不满足就别算，算了也是错的）：

1. **用左相机拍，分辨率必须与当前标定一致** —— 脚本会自己校验，不一致直接退出 1
   （文案写明两边尺寸、哪份标定、下一步怎么改）；
2. 棋盘**平放**在地面上（或任一已知平面），图案朝上，整块落在画面内、四边留白；
3. 板占画面约 **10%~30%**，对焦清晰、板面别与镜头接近平行（别太斜）；
4. 方格边长以**尺子量出来的毫米数**为准（打印时选「实际大小 / 100%」，见 §6）。

```powershell
# 第一步：只算不写 —— 先看两行世界系定义（含 ground_axis 与 Z/Y 符号）与 rmse
& $PY apps\tools\set_world_frame.py --image <地面棋盘图> --dry-run
# 确认无误 -> 落盘
& $PY apps\tools\set_world_frame.py --image <地面棋盘图> --note "球桌左侧地面"
# Z 朝上（Y 会同时反向，保持右手系的代价）；不写 = z，与棋盘法向同向（板平放时朝地下）
& $PY apps\tools\set_world_frame.py --image <地面棋盘图> --ground-axis -z
# 换了一套装置：显式指定标定基名（不含 .npz）；默认 = 当前装置档案的标定
& $PY apps\tools\set_world_frame.py --image <地面棋盘图> --rig config\calib\<档案名>
```

**图形界面**：`工具 · 标定与训练…` → 第 ③ 张卡「设世界坐标系」：选地面棋盘图 →
棋盘列 / 行 / 边长（mm）→ **世界 Z 轴**（`-z` Z 朝上 / `z` Z 朝下）→
**标定文件**（**留空 = 当前装置档案**）→ 先点「只算不写」看定义，再点「计算并保存」。
这两个输入会**真的**进命令行；留空则一个都不传（落到当前档案 / 脚本默认）。

**验收线**：

| 判据 | 门槛 | 不达标怎么办 |
| ---- | ---- | ------------ |
| 棋盘重投影 `rmse` | **≤ 2.0 px**（超过脚本退出 1） | 重拍：板压平、正对镜头别太斜、对焦清晰、板别太远/太近 |
| 拍图分辨率 | == 标定的 `image_size` | 用**标定同分辨率**重拍；或按当前分辨率**重标**后再设世界系 |
| `ground_axis` | 与你想要的 Z 朝向一致 | 换 `-z` / `z` 重算。**rmse 不变**，光看误差判断不了符号 |
| 落盘文件 | `config\world_frame.json` 里 `ground_axis`/`source`/`units`/`T_world_cam` 齐全 | 缺就是没写成功，看「任务日志」里的报错 |
| **重复性（人工必做）** | 同一块板、同一位置拍 **3 张**各算一次：相机光心在世界系里的位置互差 **≤ 5 mm**，`ground_axis` 三次一致 | 说明板没放平 / 角点不稳，重新摆板再拍，别拿这份世界系下结论 |

> **`rmse` 只说明"PnP 拟合得好不好"，看不出"板是不是真的平放在地上"。**
> 板翘着算出来的世界系照样 rmse 很小 —— 所以「重复性」这一条不是可选项。
> 另外：`parallel`（校正后左相机系）**不支持**世界系变换，程序会拒绝并说明原因，
> 要用世界系请用 `angled`；同一份世界系也不要拿去解释另一套装置的录像。

## 4. 第一次上手的推荐顺序（真机双目）

**照顺序做，别跳步。** 每一步都写清"在干什么、为什么"。

> 💡 **不想敲命令的话**：这一节的第 1～6 步都能用同一个入口直接做 ——
> `run.bat setup` / `check` / `precheck` / `calibrate` / `verify` / `run`，
> 或者双击后在图形界面里点按钮。下面给的是等价命令，便于理解和脚本化。

### 第 1 步 · 固定左 / 右 / 无关角色（`run.bat setup`）

```powershell
& $PY apps\tools\cameras.py identify
```

逐个索引弹窗显示画面，你按 `l` / `r` / `n` 确认哪台是左、哪台是右、哪台**「无关」**，程序把**设备身份**（不是编号）写进 `config\cameras.json`。

- **为什么**：编号会随 USB 口漂移（见 §5），角色名不会。做完这一步，以后启动一律用 `--left left --right right`。
- 左右约定：**人面对镜头时，左手边那台为"左"**。
- **不打算用的相机就在这一步按 `n` 标成「无关」**（笔记本内置、红外相机）。
  本机枚举到的 4 台里，`#3 Integrated IR Camera`（红外、无彩色、OpenCV 打不开）
  就是典型该标「无关」的；标掉之后自动挑相机不会再考虑它。
- ✅ **本机 `config\cameras.json` 已存在**（2026-10-10 跑过 `identify`）：
  `left` = `#1 aoni A25`、`right` = `#0 aoni A25`。
  （`main` 角色已删除 —— 内置相机被标「无关」且实测打不开。）
  所以下面的示例都用角色名 `left` / `right`；**没做过这一步的机器**请改用
  `--auto-cameras`（自动挑两台），别用会漂移的编号。

### 第 2 步 · 探测两路的分辨率 / 帧率

```powershell
& $PY apps\tools\cameras.py list --probe          # 快，推荐
& $PY apps\tools\list_cameras.py --max-index 5    # 慢，但报实测帧率
```

- **为什么**：双目要求两路**同时**稳定出图；某台只有 10 fps 就会卡住实时双目（要求 ≥25 fps）。
- **请求分辨率 ≠ 实际分辨率 ≠ 实际帧率**：`CAP_PROP_FPS` 返回的是"你请求的值"，不是真值（实测请求 60、实际 29.8）。
- 参考基线（`config\camera_modes.json` 当前缓存，**编号↔设备的对应以当场 `cameras.py list` 为准**，缓存随插口/协商变化，必须当场复测）：

| 编号 | 后端 | 请求 | 实际 | 实测帧率 |
| --- | --- | --- | --- | --- |
| 0 | DSHOW | 1024×768 | 1280×720 | 16.58 fps |

### 第 3 步 · 标定前置检查（两路都看到棋盘、视野重叠）

```powershell
& $PY apps\tools\check_stereo_setup.py --left left --right right --cols 8 --rows 5 --square 25 --seconds 8
```

举着打印好的棋盘格在两路画面里慢慢移动，让它都出现过。输出形如：

```
左路看到棋盘      : 87/240  (36%)
右路看到棋盘      : 90/240  (38%)
两路同时看到      : 85/240  (35%)
左 / 右 分辨率    : (1280, 720) / (1280, 720)
[通过] 两路都能稳定看到棋盘 —— 视野重叠良好，可以开始标定。
```

- **为什么**：标定能成功的**第一个前提**就是"棋盘同时落在两个相机的视野里"。不做这步，标定时会一直收到 0 对帧，却分不清是视野不重叠还是相机坏了。
- `[失败] 只有右路能看到棋盘` 之类：先把两台相机的朝向调近、让视野重叠。
- 分辨率不一致会被警告：**标定要求两路完全一致**，先设成同一分辨率。

### 第 4 步 · 刚性固定（这一步是标定的硬前提）

把两台相机**锁死在同一根横梁 / 支架上**，之后不要再动。

- **为什么**：标定解出的旋转 `R`、平移 `T` 描述"两台相机之间的相对位姿"。**装置一动，R/T 立刻作废** —— 而画面看起来完全正常、指标也好看，只有三维结果系统性偏，这种错最难发现。
- 整体移动没问题（R/T 是常数，得到的是"相机坐标系下的轨迹"）；**两台各自移动完全不行**。

### 第 5 步 · 双目标定

```powershell
& $PY apps\calibrate_stereo.py --left left --right right --cols 8 --rows 5 --square 25
```

把板举到**两路都能看到**的位置，慢慢移动，**每个姿势停稳约 1 秒**（程序只收停稳的帧）。收满 40 对后自动标定，
输出质量报告并保存到**当前装置档案的标定位置**：`config/calib/<装置档案名>.npz`（参数）+ 同名 `.json`（人读报告）。

- **期望**：极线误差 **< 0.3 px**（验收线）。没通过质量判定不会保存，按提示重拍。
- **判定分四级**：优秀 / 可用 / **勉强可用**（精度刚过 ok 线但**基线没错** —— 会保存，
  报告里写清差在哪、怎么改）/ **不可用**（基线对不上 / 有效对 < 8 / 求解发散）。
- ⚠️ **判"不可用"时不会保存任何文件** —— 那是设计（"失败却留下一个能读的标定文件"更危险），
  不是程序坏了。此时该装置档案的标定位置**不会有**新文件，`verify_stereo.py` 也就无从跑起。
  **要看差在哪，读那份日志**：`logs/calib/<年月>/calibrate_<时间>.log` 里有完整拒收分布与逐项指标。
- ✅ **已经落盘的标定（2026-11-11 实况）**：`平行装置` 与 `实验性质平行装置1` 各一份。
  后者 2026-11-11 08:34 落盘：基线 **68.1 mm**、极线 RMS **1.14 px**、30 对里用了 28 对，
  判定"**勉强可用**"（极线还没到 0.3 px 的验收线，能先做三维）。
  ⚠️ **当前激活的档案是「实验性质大角度1」，它没有标定文件** —— 直接录制或分析会报
  "找不到标定"。先切回已标定的档案，或给这套装置标一次。详见 §15.2。
- 可选参数：`--target 40`（收多少对）、`--min-pairs 20`、`--fps 30`、`--baseline-mm <你量到的毫米数>`（预期基线，用来核对 —— **必须自己量，别照抄范例数字**）、`--save-pairs outputs\pairs`（另存收下的图像对，便于复查）、`--report-png outputs\calib_check.png`（验证图）。

> ⚠️ **`--baseline-mm` 要量当前装置的两镜头中心距，不是抄别人的数字。**
> 这一条是**唯一能发现"左右对应关系错配"的物理量**（详见 `真机标定操作清单.md` §2）。
> 给错比不给更糟：不给只是"守卫关着"，给错会让程序把**正确**的标定报成"基线对不上"，
> 或者把偏了的放过去。**重新摆过相机就要重新量。**
- **同步**：**标定不需要左右同步** —— 板是静止的，静止目标在任意时刻看起来都一样。

> ⚠️ **只有拍运动物体（小球）时才必须同步。** 实测右路只滞后 1 帧（17 ms），三维误差就涨 17–34 倍。

- **视场不一样会自动对齐**：启动时先用启动帧估计一次 FOV（较窄一路做参考，较广一路裁剪）；估不出来会直接退出 1。**一启动就把标定板 / 有纹理的场景放进两路**。细节见 §3.5「自动 FOV 对齐」。

### 第 6 步 · 复检并记下基线

```powershell
& $PY apps\verify_stereo.py --left left --right right      # 默认跟随激活装置档案
```

```
标定时记录的极线误差：0.0670 px
本次复检：8 帧，极线误差 RMS 0.0812 px（最大 0.1203 px）
变化量：+0.0142 px
[通过] 装置未发生明显变动，可以继续使用现有标定参数。
```

- **为什么**：判断装置有没有被碰动。未动是 0.08 px 量级，碰动 2° 后是 27.9 px，差 250 倍，一看就知道。
- **判定**：极线误差 > 0.6 px，或比标定时增大超过 `--tolerance`（默认 0.15 px）→ `[不通过]`，需重新标定；**把"标定当时"那个数抄进实验记录**，以后每次拍摄前对比。
- **FOV 会沿用标定记录**：实时相机复检先按标定里的 `fov` 记录（`rig.meta["fov"]`）归一化；视频 / 图片不再二次裁剪，但**首对帧会重新估一次 FOV** 证明输入确实已归一化 —— 仍需要主动对齐（原生画面）、尺度不在 0.9–1.1 或纹理不足估不出来，都会**退出 2**，不静默假定；确认已归一化可加 `--fov-input-normalized`。拿旧的原生视频配新标定会直接报错，需重录或重标。旧标定没有 fov 时按原生画面复检。详见 §3.5「自动 FOV 对齐」。

> **录完、标定完之后**：录像、标定产物、标定板照片各存在哪，哪些**删了就回不来** →
> 见 §15（§15.2 标定产物、§15.3 会话文件、§15.4 标定板照片）。

## 5. 相机为什么用"角色名"而不是编号

`cv2.VideoCapture(0)` 里的 `0` 由系统枚举顺序决定：换一次 USB 口、多插一个设备，编号就可能变。
本机实测就漂过：早期是"0、2 = 外接，1 = 内置"，换了个 USB 口之后变成"0、1 = 外接，2 = 内置"。
把 `--left 0 --right 1` 写死，索引一变就会**悄悄用错相机**（画面完全正常），标定白做。

| 做法 | 命令 |
| --- | --- |
| **固定**（推荐） | `cameras.py identify` → 之后用 `--left left --right right` |
| **按端口/身份指定** | `--left port:Port_#0001.Hub_#0003`、`--right id:USB\VID_...`、`--right name:aoni` |
| **让它自动挑** | 不指定（`run_realtime.py` 默认）或 `--auto-cameras` |

**配置与实物对不上时，程序不会替你猜**：已 `identify` 确认过的角色若身份消失，会直接报错并附当前设备清单；交互式终端下还会把清单摆出来让你自己选编号。

```powershell
& $PY apps\tools\cameras.py check    # 有 [危险] 项（如索引被别的设备占了）时退出码为 2
```

> ✅ **本机现状（2026-10-10）**：`config\cameras.json` **已存在** ——
> `left` = `#1 aoni A25`、`right` = `#0 aoni A25`。
> 所以双目**优先用角色名**（`--left left --right right`），
> 不要再用编号：本机 `left` 是 `#1`、`right` 是 `#0`，**照直觉写 `--left 0 --right 1`
> 正好是反的**（画面一切正常，但标定出来的 R/T 是反的）。
> 没跑过 `identify` 的机器请用 `--auto-cameras`（自动挑两台）。

## 6. 标定板：打印与核对

`assets\boards\` 里已有可直接打印的文件：

```
chessboard_8x5_25mm_a4-landscape.pdf / .png     ← 内角点 8x5，方格 25 mm，A4 横版
chessboard_8x5_20mm_a4-portrait.pdf / .png      ← 内角点 8x5，方格 20 mm，A4 竖版
```

打印与核对三条（**一条都不能省**）：

1. **必须选"实际大小 / 100%"打印**，不要选"适应页面 / 缩放"。缩放过的板方格不是 25 mm，焦距与基线会系统性偏。
2. **打印后用尺子量方格边长**：量到多少，`--square` 就填多少（量出 24.6 mm 就写 `--square 24.6`）。

## 7. 看数字：指标含义与验收线

### 7.1 指标表

| 指标 | 含义 | 验收线 | 现在最好成绩（**合成真值**） |
| --- | --- | --- | --- |
| **检出率** | 球完整可见时能检出来的帧比例 | ≥ 95% | 100% |
| **圆心误差** | 检测球心与真值的像素距离（RMSE） | ≤ 1.5 px | 0.54–0.87 px |
| **半径误差** | 像素半径与真值之差（RMSE）—— 单目测深的命根子 | ≤ 0.5 px | 0.06–0.23 px |
| **跟踪误差** | 滤波后轨迹与真值的中位偏差 | — | 0.65 px |
| **预测误差** | 预测未来位置与真值之差（2D，@0.2 s） | ≤ 5 px | 1.20–2.49 px |
| **极线误差** | 立体校正后同名点偏离同一水平线的像素数（越小越好） | ≤ 0.3 px | 0.067 px（**真机未测**） |
| **三维定位误差** | 重建 (X,Y,Z) 与真值之差，**折算到 1 m 处** | ≤ 10 mm @ 1 m | 1.13–2.27 mm（**真机未测**） |
| **实时帧率** | 实时处理速度 | ≥ 25 fps | 34 fps（单目，合成条件） |

这些数字在跑回归测试时会直接打印（`selftest_synthetic.py`、`selftest_stereo_calib.py`、`selftest_stereo_branch.py`）。
实时运行时 HUD 左上角的 `FPS` 是当场实测值 —— **它就是帧率，不要信 `--fps 60` 这个请求值**。

### 7.2 必须折算到 1 m（这条最容易读错）

深度误差随距离**平方**增长：

```
εZ ≈ Z² · δd / (f · B)        Z=距离  δd=视差误差(px)  f=焦距(px)  B=基线(m)
折算到 1 m 的误差 = 实测误差 × (1 / Z)²
```

所以**"4 m 处的 30 mm"和"1 m 处的 10 mm"完全不是一回事**：

- 在 3.73 m 处量到三维 RMSE **15.6 mm** → 折算到 1 m 是 `15.6 × (1/3.73)² ≈ 1.13 mm`；在 4 m 处量到 **30 mm** → 折算到 1 m 是 `30 × (1/4)² ≈ 1.9 mm`，**远好于** 10 mm 验收线。
- 本装置（f≈889 px、B=150 mm）在 3.73 m 处，**1 px 视差误差 = 7.5 mm 深度误差**；所以 4 m 处三维 RMSE 落在 15–35 mm 是这条定律的**必然结果**，不是实现差。

> 严格说，随距离平方增长的是**深度分量**（`εZ`），横向分量随距离**线性**增长（`εX ≈ Z·δp/f`）；项目里"折算到 1 m"统一按 `Z²` 折算整条三维 RMSE，属于**偏严**口径，测试会自己打印这一行，别自己换个口径再对比。

### 7.3 这些数字是"合成真值"，不是真机能力

**合成真值** = 程序渲染出来的"假视频"，每个像素的正确答案已知。它能验证"几何链路和算法写对了"，但**不等于真实相机能做到** —— 真机的镜头畸变、光照变化、同步误差、滚动快门都比合成场景恶劣。
**双目标定已经在真机上跑通并落盘，但自动 FOV 对齐只做过模块级真机画面验证；"标定 → 录制 → 复检"（含自动 FOV）整链还没有在真机上跑完一轮 E2E**，这是当前最大的未知数；把上面那些数字当**上限参考**，不要当性能承诺。

## 8. 故障排查表

| 现象 | 原因 | 怎么办 |
| --- | --- | --- |
| **某台相机"打不开"但另一台正常，换 USB 口/重插都不管用** | 我们**请求了它给不了的分辨率**：实测有 aoni 在 MSMF 下**只认 1920×1080**，请求 640×480/1280×720 会"打开成功但一帧都不给" | 已修（预览/探测改请求原生分辨率）。自查：`python apps/tools/cameras.py probe --backends msmf` 要**两台都 ✅** |
| **识别窗口要等十几秒才出画面** | 其中一台相机**首帧要 ~23 秒**（另一台 ~2 秒） | 正常，不是卡死；预览已给 30 秒首帧时间，且显示降到 960 宽（不再逐帧搬 1080p） |
| **`identify` 里某台相机"打不开"/纯黑，而它名字里有 `Integrated`** | **它是笔记本内置相机，而且被挡住了**（本机就是有意遮住的）—— 没光进来就没画面，**不是故障** | **按 `n` 标成「无关」**，之后自动挑相机会跳过它。判据：名字含 `Integrated` = 内置；盖住镜头看哪台变黑也能认出来 |
| `identify` 里某个 `aoni` 相机"打不开" | 后端问题（MSMF/DSHOW 在这台机器上**会来回翻**）或那一台真有问题 | 换后端试（工具已自动试两个）；仍不行就**交换两台的数据线**定性：问题跟着相机走 = 相机问题，留在原口 = 线缆/端口。详见下面那行 |
| 裸 `python` 报 `No module named 'cv2'` | `python` 解析到 msys64 那个解释器，没装 opencv | 用绝对路径 `& "$env:USERPROFILE\miniforge3\envs\myenv\python.exe" ...`（先设 `$PY`） |

| 两路分辨率不同（如 1280×720 vs 1280×1080） | 系统给每台相机协商出的模式不同 | 预览不会崩：程序**各自独立缩放、再补齐到同一高度**；但**标定要求两路完全一致**，先设成同一分辨率再标定（前置检查会警告） |
| 标定老说"棋盘还在移动，请停稳再收" | 板没停稳，或帧积压（读到旧帧） | 每个姿势**停稳约 1 秒**；实时相机走 `LatestFrameCamera` 取最新帧、不排队积压；手别抖 |
| **左 / 右装反** | 画面正常、单看指标也好看，但配对率 0%（"视差必须为正"的静默陷阱） | 现已自动判视差符号（`StereoRig.disparity_sign()`，`T[0] < 0` 时 `describe()` 打警告）；跑 `verify_stereo.py` 兜底；重跑 `identify` 把左右改正 |
| 分不清"请求分辨率 / 实际分辨率 / 实际帧率" | `CAP_PROP_FPS` **返回的是你请求的值**，不是真值（实测请求 60、实际 29.8） | 看 HUD 的 `FPS`，或 `list_cameras.py` 的实测帧率；录像/评估一律用实测值 |
| 某台相机帧率只有 ~10 fps，卡住实时双目（要求 ≥25 fps） | 分辨率/后端协商到低帧率模式 | 换一档分辨率（如 640×480）、换后端（`--backend dshow/msmf`）、换 USB 口；**A25 是 USB 2.0 设备，插蓝色 3.0 口也不会变快**，换口只为"分总线" |
| 处理视频时播放速度不对 | 把 `CAP_PROP_FPS`（请求值）当真实帧率用了 | 本项目时间戳走 `perf_counter`（真实时间），速度与预测时间轴是对的；自己写脚本时别用 `CAP_PROP_FPS` |
| 标定收不到帧 / `[失败] 只收到 N 对，少于 10 对` | 视野不重叠、板太小/太暗/贴边、移动太快 | 先跑 `check_stereo_setup.py`；板更大更清晰、慢一点、每个姿势停稳 1 秒、覆盖画面各区域 |
| **标定一开始就退出 1，报「无法自动估计两路 FOV 对齐」** | 启动帧对没有足够共同纹理（空白墙 / 纯色桌面 / 欠曝 / 两路没对准同一场景），SIFT/ORB 匹配不够；或参考帧没有完整落在较广那一路的视场内（共同视场不足，四角越界 > 16 px） | 把标定板或有纹理的物体同时放进两路，光照均匀、对焦清晰后重试，并确认较窄一路的画面完整落在较广一路里；程序**不会**按原生分辨率继续标定 |
| **录制 / 复检报 `meta.fov` 解析失败，或 `fov.target_size` 与 `image_size` 不一致（退出 2）** | 标定 JSON 里的 fov 记录损坏 / 被手改，或标定与当前分辨率不匹配 | 重新跑 `calibrate_stereo.py`；不要手改标定 JSON 里的 `fov`，也不要用旧标定配新裁剪的视频 |
| **视频 / 图片复检退出 2，提示输入像是未归一化 / 无法验证已归一化** | 拿原生（raw）视频配带 `fov` 的新标定，或首帧共同纹理不足、估不出尺度 | 用 `record_stereo.py` 以同一标定重录归一化视频；确认输入已归一化时加 `--fov-input-normalized` 跳过校验 |
| **新录制的两路视频视野比以前窄 / 分辨率变成约 1684×978（不是 2560×1440）** | 标定带 FOV 对齐：**较广一路被裁**，两路统一到共同视场；共同输出 = 裁剪区尺寸向下取偶，**不放大**（无损 MKV 只支持偶数宽高） | 正常，这是为了像素尺度一致且不牺牲清晰度；相机仍按 2560×1440 采集；旧标定（无 fov）不会这样 |
| 复检 `[不通过]` | 装置被碰动，或相机取下重装 | 重跑 `calibrate_stereo.py`；标定完**记下当时那条基线值**，以后每次拍摄前对比 |
| 检不到球 / 检到乱七八糟的东西 | 颜色阈值不对（曝光/白平衡一变就变） | 跑 `calibrate_color.py` 看掩膜里是不是只有球是白的；按 `1`-`6` 换预设；**拍摄时固定曝光/白平衡/焦距** |
| 深度不对（球在动 Z 却不动） | `--ball-diameter` 填错（填错多少，深度就错多少） | 用卡尺量球径，单位是**米**：`--ball-diameter 0.04` |
| 在 AI / 沙箱进程里查不到 USB 和相机 | 沙箱不在交互式桌面会话里，DShow/MSMF 按会话枚举相机 | **这不是你的机器坏了**；相机相关实测必须在自己的终端里跑 |

## 9. 已知限制（诚实清单）

| 限制 | 影响与说明 |
| --- | --- |
| **真机标定只到"勉强可用"，FOV 整链未 E2E** | 已有真机标定落盘，但判定只是"勉强可用"；**自动 FOV 对齐只做过模块级真机画面验证**，标定 → 录制 → 复检还没有在真机上跑完一轮。合成真值仍不代表真机能力 |
| **实时窗口里没有三维视图** | 实时界面只有俯视/侧视小面板；可交互三维要离线看（`apps/view_3d.py`，见 [`3D查看器.md`](3D查看器.md)）。plotly 未装，3D 图走 matplotlib |
| **反弹后 3–4 帧跟踪变差** | 机动检测需要观察窗口（速度突变要两次观测才测得出），约 0.05–0.07 s 后恢复，**物理限制**不是 bug |
| **多球跟踪未做** | 画面里两个球会互相抢；跟踪器支持多目标，但缺外观特征做关联 |
| **双目实时已接进主流程，但有边界**（2026-11-16） | 各双目窗第③步「实时 3D（不落盘）」→ `apps/run_realtime_stereo.py`：两路实时采集 + 逐帧三角化，960 宽下 32–40 fps。**没有硬件同步**：只能测出两路时间差并做一阶补偿，超过 60 ms 的那一对直接丢弃；精度是**毫米级**不是亚毫米；只支持 `color` / `motion`。实时退出会落会话（`source=realtime`）。详见 §1.3 |
| **三维平滑已实现，但主输出默认不开** | `stereo/motion.py` 的逐段 S-G（0.20 s 窗口 / 2 阶，缺口不补点）已接 3D 查看器与运动量导出；离线双目要另存平滑轨迹得显式加 `--smooth`（默认不开是为了保持旧行为，不是没做） |

## 10. 出问题时按这个顺序查

1. **先跑回归测试**：`& $PY tests\selftest_synthetic.py` —— 通过说明是"相机/参数"问题，不是代码问题。
2. **再看相机**：`cameras.py check` → `cameras.py list --probe` → `list_cameras.py --max-index 5`。
3. **再看视野与标定**：`check_stereo_setup.py` → `calibrate_stereo.py` → `verify_stereo.py`。
4. **再看颜色与参数**：`calibrate_color.py`（掩膜对不对）、`--ball-diameter`（球径填对没）；还不行就翻 [`交接文档.md`](交接文档.md) §5「踩过的坑」与 §7「硬件现状」。

## 11. 两个最耗时间的坑（都有工具了）

### 11.1 "某一路画面明显不如另一路"——先分清是**带宽**还是**光学**

跑：

```powershell
run.bat diag
# 等价于：& $PY apps\tools\camera_quality.py --left left --right right --together
```

它会逐台量，然后**给结论**。判据是这两种故障各自特有的指纹：

| 现象 | 带宽/链路不足 | 光学/曝光问题 |
| --- | --- | --- |
| 实测帧率 | 明显偏低；两路同开时骤降 | 正常 |
| **残帧**（下半幅是常量） | **会出现**（传输没传完） | 不会 |
| 实际分辨率 | 被驱动降到更低档 | 正常 |
| 清晰度（Laplacian 方差） | 正常 | **明显偏低** |
| 过曝 / 动态范围 | 正常 | 可能过曝，或范围被压扁 |

**关键认知：带宽不足不会让画面变"糊"，只会让它变"卡"。**
如果你看到的是"一边清楚一边像蒙了雾"，**那几乎一定不是 USB 的问题** ——
去擦镜头、撕保护膜、查起雾、查逆光，比换线换口有效得多。

**唯一的定性归因办法 —— 交换测试（5 分钟）**：

1. 把两台相机的 **USB 口对调**（连数据线一起对调），再跑一次 `diag`；
2. 问题**跟着相机走** → 是相机（光学/传感器）；问题**留在原来的口/线** → 是链路；
3. 再把两台插到**不同的 USB 控制器**上（机身不同的口，别都走同一个扩展坞）测第三次。

`--together` 会额外测"两路同开"：单开正常、同开掉速，才是真的带宽紧张。
本机两台 aoni 都在同一条 USB 2.0 总线上（见 [`交接文档.md`](交接文档.md) §7.1），
所以**分总线**是唯一值得试的方向 —— 注意 A25 是 USB 2.0 设备，插蓝口也不会变超速。

### 11.2 "标定收不到帧 / 手一抖就不收"

先看**标定窗口右上角那两行**（新加的）：它会逐路告诉你状态。

```
左: 未找到板
右: 清晰度  210 面积 4.2% 曝光 118
```

一眼就能看出是**哪一路**的问题。如果两路都写"未找到板"，右下角还会给出会诊，例如：

```
last: 左路未检测到棋盘（右路正常）｜左：画面动态范围被压到只剩 58 级（均值 196）——
      像蒙了一层雾：先擦镜头、撕掉保护膜，检查有没有起雾/结露、或有没有东西紧贴镜头
```

**90% 的"收不到帧"其实是画面质量问题，不是门限太严**（`x122 两路未同时检测到棋盘`
通常意味着一路压根看不见板）。先按 §11.1 把那一路修好。

如果画面已经正常、只是**手抖**，按"代价从小到大"这样处理：

| 办法 | 怎么做 | 代价 |
| --- | --- | --- |
| **① 让板"靠"住（最推荐）** | 把板**靠在椅背 / 纸箱 / 墙上 / 书架**上，或夹在书立、谱架上。你只需要它**停住 1 秒**，不需要三脚架 | 无。**这一步通常直接解决问题** |
| **② 提高快门（减少运动模糊）** | 开灯 / 加台灯，让画面更亮，自动曝光就会用更短的曝光时间；手抖带来的模糊随之变小 | 无 |
| **③ 放宽"停稳"门限** | `run.bat` 之后在命令行加：`--stationary-px 8`（默认 3） | 中度。这条门限**同时替代了左右同步**，放太松 = 两路拍到不同位姿 → R/T 会系统性偏 |
| **④ 手持宽松预设** | `& $PY apps\calibrate_stereo.py --left left --right right --relaxed` | 较大。预设放宽 6 项：停稳(10px)、清晰度(400)、板的最小面积(0.8%)、贴边余量(6px)、亮度(25–245) |

> ⚠️ **`--relaxed` 是"用精度换成功率"**，程序会明确打印这句话。
> 判据：标定完看 **极线误差**，验收线是 **≤ 0.3 px**；
> 如果超了，或者代进三维后抖得厉害，就处理好光照与支撑、**去掉 `--relaxed` 重标一次**。
>
> ⚠️ **从图形界面勾「放宽」有个坑（B-97；2026-10-28 起日志会如实算）**：面板预填的
> 「停稳上限 **3** / 清晰度下限 **800**」会**显式下传**，覆盖预设的 **10 / 400** ——
> 所以界面只算"放宽了 4 项、2 项按你的值"。日志现在会**按实际参数**打印
> 「预设共 6 项，生效几项、被你的显式参数覆盖几项」并点名。**想全套放宽就把这两格清空再勾**，
> 或直接用上面的命令行（命令行不传这两项，预设 6 项全生效）。

**为什么"停稳"这条门限不能随便关掉**：两台 USB 相机**没有硬件同步**，
程序只能保证"这一对帧是同一轮读出来的"。板在动的时候，左右两路实际拍到的
**位姿不同**，三角测量的约束就是错的 —— 而且这种错**不会报错**，
只会让标定结果整体偏掉、事后查不出来。所以"板静止"是用**静态目标在任意时刻
看起来都一样**这个性质，来替代时间同步。这是设计决定，不是苛刻。

**另一个常见误判**：`--cols/--rows` 填错（比如板是 9x6 内角点却填 8x5）。
角点数对不上时，检测器只会返回"找不到"，表现为和"画面太糊"一模一样。
用 `& $PY apps\tools\make_calibration_board.py --all` 生成时，
文件名里就写着内角点数，照着填。

## 12. 图形界面：窗口、任务、日志（2026-10-14）

### 12.1 所有视频窗口都能全屏

| 键 | 作用 |
| --- | --- |
| **`f` 或 F11** | 切换全屏 |
| **`Esc`** | **全屏时 = 退出全屏**；不在全屏时才退出程序 |

窗口打开时取"画面的 1.5 倍"与"屏幕的 90%"里较小的那个，所以不会只占屏幕中间一小块。

> **`Esc` 这条是刻意的**：全屏之后第一反应就是按 Esc 退出来；
> 如果它直接退出程序，你会把正在跑的东西关掉。
>
> **例外**：颜色标定（`calibrate_color.py`）里 `f` 已经是"冻结画面"，
> 所以那个程序**全屏只用 F11** —— 抢掉别人已经用的键比没有全屏更糟。

**哪些程序有**：实时检测、离线视频、标定前置检查、双目标定、相机识别、
颜色标定、焦距标定 —— 共 7 个。

### 12.2 任务：能中断跑飞的程序

启动器里有一张「任务」卡片，列出**启动器起过的每个程序**：

| 按钮 | 做什么 |
| ---- | ------ |
| **中断选中** | 先请求**优雅退出**（让程序自己收尾），3 秒不退再强制结束**整棵进程树** |
| **强制结束选中** | 立刻杀掉（会二次确认），来不及保存已完成的结果 |
| **全部中断** | 一次停掉所有在跑的任务 |
| **查看输出** | 把该任务的命令行 / PID / 耗时回显到日志区 |
| **打开日志文件** | 用系统默认程序打开该任务的完整日志 |
| **清理已结束** | 清掉已结束的记录（在跑的**绝不动**） |

任务列表右侧有**滚动条**；下方「显示行数」滑块可在 3–20 行之间调整任务表高度。
任务再多，也能拖动滑块查看，不会把整页撑到无法操作。

> **实时运行任务面板**：「任务」区还常驻一条**实时运行任务栏**，读的是**跨进程任务注册表**（`apps/_task_registry.py`）—— 不只启动器自己起的程序，别的窗口 / 命令行进程登记的任务也会出现在这里；**关掉任务所属窗口会按 owner 停掉它的任务**（`stop_by_owner`），不会留下"界面没了、进程还占着相机"的孤儿。

**为什么"杀整棵进程树"重要**：`terminate()` **只杀直接子进程**。
我们的子进程是 python，它自己还有子进程。**父进程死了子进程还活着 —— 相机就还占着**，
下一次运行打不开相机，而用户看到的是"停了但相机用不了"。

**关窗口也会先收干净**：点关闭时如果还有任务在跑，会先停掉它们（含子进程树）再退出。
**旧版直接 `destroy()`，子进程不会被杀**。

### 12.3 日志都在哪

| 文件 | 内容 |
| ---- | ---- |
| `logs/tasks/<日期>/task<NN>_<时间>_<标题>.log` | **每个任务一份**：命令行、PID、全部输出、退出码、耗时 |
| `logs/realtime/<年月>/realtime_<时间>.log` | 实时检测：环境、相机模式、**每 5 秒一行健康度**、逐帧明细（DEBUG）、按过的键 |
| `logs/calib/<年月>/calibrate_<时间>.log` | 双目标定：**每一次拒收的原因**（这是查"为什么收不满"的唯一依据） |
| `logs/calib/<年月>/calibrate_mono_<时间>.log` | 单目标定 |
| `logs/calib/<年月>/capture_board_<时间>.log` | 采标定板图 |
| `logs/capture/<年月>/record_<时间>.log` | 双目 / 单目录像 |

**目录规则**（`sphere_tracker/paths.py` 的 `log_dir()` 是唯一来源）：
`logs/<来源>/<时间片>/`。来源是 `tasks` / `calib` / `capture` / `realtime` / `misc`；
任务按**日**分片，其余按**月** —— 任务一个月有几千个，按月分仍是一个大目录；
标定/录制一个月才几十个，按日分只会碎成一堆空壳。

> 2026-11-04 之前日志在 `outputs/logs/` 平铺一层（9196 个文件）。老日志已按
> 同样规则搬进 `logs/`；再看到 `outputs/logs` 说明是更早版本写的残留，
> 「垃圾管理器 → 一键清日志」会把它一起清掉。

> **卡顿/失败时最有用的一条**是实时日志里的「健康度」行：
> ```
> 健康度 cap 31.6  loop 85.1  detect 7.9 ms  age 1.4 ms  drop 2
> ```
> `cap` 远低于 `loop` = 相机慢；反过来 = 我们慢。`age` 一大就是在积压。

### 12.4 标定参数面板

「第 1 步 · 相机标定」下有 **『基本设置』/『高级设置』** 两个**可展开/收起**区，
默认基本展开、高级收起；收起不会丢值，展开后所有旧控件仍在。
默认值**就是正式档（40 对 / 最少 20 对 / 24 fps）**，直接点「运行标定」即可。

| 折叠区 | 放什么 |
| ---- | ------ |
| **基本设置** | 目标/最少对数、标定板（内角点列·行、方格边长 mm）、分辨率、帧率 |
| **高级设置** | 停稳上限、**清晰度下限（focus）**（默认 800 低于检出下限、平时不构成闸门）、放宽模式、相机后端、**预期基线 mm**、存图像对、验证图 |

参数会被校验（非数字、越界、"最少对数 > 目标对数"都会被拦下并说明原因）。

> **清晰度是怎么判的**（2026-10-25 改、2026-10-28 补口径，B-99）：**主判据是相对本组中位数 40%** —— 只拒"**明显比本组中位数糊**"的帧，整路偏软只提示不拒收。
> 另有**绝对下限** `min_sharpness`（面板上叫「清晰度下限（focus）」，默认 **800**）：程序默认的 800 **低于相机能检出棋盘的下限**，所以平时**不触发**；只有调大才会更严（会成片拒收）。以前那种"明明格点都识别出来了却报糊"的情况，就是绝对阈值按死造成的。

**第 2 步 · 检测与测距参数**：

- 常用区只放 **检测方法**、**颜色预设**，这三类流程都读：
  实时摄像头 / 离线视频 / 双目会话；
- **高级（仅单目实时 / 离线视频）**默认收起：
  摄像头编号、球直径、预测视野、焦距 fx、启用三维估计；
- 双目会话**不使用**球直径/预测视野/焦距/单目三维开关：
  深度来自双目标定，点「这些参数用在哪？」可看完整表；
- 右上角有固定 **快速跳转**（①标定 / ②参数 / ③开始 / 工作台 / 任务 / 日志），
  窗口会按屏幕工作区自动缩放，不需要拖到屏幕外。

> **板占画面 10%–30%、每个姿势停稳约 1 秒** 这两条比“对数”更影响精度；
> 40 对是**输入**对数，真机会因移动/位姿重复剔掉一部分，留出余量后仍有 20+ 对参与求解。

> **⚠️ 「预期基线 mm」默认是空的，这是故意的。**
> 程序**无法知道**你装置的中心距 —— 编一个数字进去会让基线核对**锚在错的值上**，
> 比留空更糟。**强烈建议用尺子量一下两镜头中心距填进去**：
> 这是唯一能发现"对应关系错配"的护栏（错配会把基线吹到真值的 8~15 倍）。

### 12.5 GUI 录制双目（无损）

「第 3 步 · 开始轨迹检测」里有 **『录制双目（无损）』** 按钮，不需要记命令行。

1. 先在「第 1 步」完成标定或复检（左右下拉选 `left` / `right`）；
2. 点『录制双目（无损）』；
3. 弹窗填**录多久**（默认 10 秒，1–600）和**标签**（可空，会写进 `session.json`）；
4. 点确定后，任务管理器会起一个 `record_stereo.py` 任务，并弹出 **left | right 并排预览**；
5. 倒计时结束后开始录：
   - **看到/听到“开始！现在闪光！”后立刻闪一次光**（不要提前在倒计时里闪）；
   - 结束前再闪一次；
   - 球保持在两路视野内；按 `q` / `Esc` 可提前结束；
6. 录完日志里会打印会话目录、帧数、实测 fps、同步结果和校验结论。

**预览窗口的 HUD**（不再只在终端提示）：

```text
READY 2.4s                  ← 倒计时
FLASH NOW after the beep    ← 开始后立刻闪
REC 3.2/10.0s  L 96 R 96    ← 录制进度 + 两路帧数
FLASH NOW!                  ← 前 2 秒
FLASH AGAIN BEFORE END      ← 最后 2 秒
FLASH DETECTED              ← 检测到一次亮度跳变
```

HUD 只画在预览画面上，**不写进 left.mkv / right.mkv（或 left.avi / right.avi，扩展名随容器）**（原始数据保持干净）。

> **闪光有没有拍到，看日志这一行：**
> `[同步诊断] 最大亮度跳变 左=... 右=...；明显事件 ...`
> 正常闪光应能让最大跳变 **≥2.0**（`SyncConfig.flash_min_jump` 默认 2.0）；
> 如果低于 2.0，说明相机没拍到足够强的闪光（/ 闪得太早或太晚），
> 录制器会直接写“未同步”，并画出 `derived/sync_brightness.png`。
> 这时**不要直接拿它做三维**，重录。
> 如果 10 秒录制里两路帧时间戳很稳，录制器会自动改用 **`timestamp` 近似同步**
> （主机读帧时间，不是硬件触发）；日志会写 `method=timestamp`。
> 它只适合慢速球；能闪光时仍以 `flash` 为准。

默认值：

> **新界面的 ③ 采集卡直接有「格式」下拉（mkv / avi）**，不用记命令行；
> 命令行等价于 `--container avi`。旧界面的同名下拉已随经典界面废止，
> 能力已原样搬进新界面（2026-11-20）。

| 项 | 默认 |
| --- | --- |
| 编码 | **HFYU + MKV**（无损；1440p@24 能跟上） |
| 容器 | **mkv（默认）** / **avi**（新界面 ③「格式」下拉或 `--container avi`；AVI 有经典单文件 **2 GiB** 上限，长录制建议 mkv；**mp4 不支持** —— HFYU/FFV1 进 mp4 会被静默换成有损 h264） |
| 分辨率 | **`2560x1440`**（真机实测两台外接相机无视 1920/1280 请求、恒给这一档） |
| 帧率 | **24 fps**（1440p 主循环实测 24.07 fps 是稳定目标；请求 30 会丢帧） |
| 时长 | 10 秒 |
| 标定 | 跟随**激活装置档案**：`config/calib/<装置档案名>`，自动复制快照 + sha256 进会话 |
| 后端 | **MSMF 角色路径**（`left` / `right`） |

> **可选更高档（2026-11-18，默认值不变）**：分辨率共 **8 档** —— 8K / 5K / 4K / 1440p（默认） / 1080p / 720 / 540 / 480；`--width/--height` 给 0（默认）时逐档自动协商，**上限是 4K**，5K / 8K 须显式指定才会用。帧率可选 24 / 30 / 60 / 120 / 240 / 500 / 1000 档，**可填小数如 `--fps 29.97`**（不会被截断成整数）。档位与解析的唯一产地是 `sphere_tracker/video_profiles.py`；上面的 1440p / 24 fps 仍是本机稳定默认档。

> ⚠️ **1440p@30 录制不稳定：主循环跟不上。**
> 2026-10-24 真机实测：`record_stereo` 在 2560x1440@30 下**主循环只有约 24.07fps
> （242/300 帧/路，10 秒，HFYU，两路一致）**——按 30 录会丢帧；裸采集能到 30
> 不等于主循环能到 30。所以**默认就是 1440p@24**；只有明确接受丢帧时才显式
> 传 `--fps 30`（本机不推荐）。长录与其他机型仍未验证；首次用先录 10 秒看日志实测。
> **旧 1080 标定 / 旧 1080 会话照常可读**，只是录制分辨率必须与标定 `image_size`
> 一致（1080 标定 + 1440 录制会在开始前直接报错退出 2，不会静默混用）。

> ⚠️ GUI 录制按钮固定走 **角色名 + MSMF**。  
> 如果你要用 DSHOW，必须用显式编号（例如 `--left 0 --right 1 --backend dshow`），
> 那种情况请走命令行 `apps\record_stereo.py`；界面里的后端下拉是给**标定/复检**用的。

> **FOV 对齐（2026-11-15 起先过装置级应用开关）**：装置档案 `fov_apply` 开启、且标定 JSON 的 `fov` 与档案一致时，录制按档案那份 FOV 沿用标定 JSON 顶层的 `fov` 记录（开关关闭但标定自带 FOV 时也沿用，见下方说明） —— 较广一路先裁剪；两路统一到 `target_size`（参考帧与裁剪区逐轴取小、**向下取偶**；当前一对约 **1684×978**，**不是** 2560，避免上采样模糊），然后才写盘 / 进预览；源相机仍按 2560×1440 采集，writer / `session.json` 的 `left/right.width/height` / `calibration.image_size` 都记 `target_size`。`session.json` 的 `rig.fov` 只在对齐真的生效时写入。标定 JSON 的 `fov` 缺失 / 为 `null`（本机当前状态）时按原生画面录，与旧版行为一致；`fov` 为 `{}` / `[]` / 非 mapping 等其他无法解析的值都算损坏，或启用对齐时 `target_size` 与 `image_size` 不一致、`crop_rect` 超出采集帧、`target_size` 大于裁剪区（旧版会放大的记录）或含奇数宽高，都会在打开 writer 前**退出 2**。关掉 `fov_apply` 但标定自带 `fov` 时**沿用标定自带的 FOV 裁剪**（见下），标定 `fov` 为 `null` 时按原始画面写盘；开启但标定 `fov` 为 `null` / 与档案不一致时**退出 2** 拒绝（不静默回退）。细节见 §3.5「自动 FOV 对齐」。

> **装置开关关闭时，若标定 JSON 自带 FOV**（2026-10 月那几份旧标定），录制
> **沿用标定自带的 FOV 裁剪** —— 因为内参本就是在裁剪帧上算的，跟着裁才自洽；
> 命令行会打一行醒目提示，说明本次是跟着标定走、并建议在 FOV 管理器里打开开关并读入记录。
> **旧流程行为不变。** 标定 JSON 的 `fov` 为 null（本机当前状态）时按原始画面写盘。
> 开关打开后，档案里的 FOV 成为唯一权威：标定与它不一致、或标定没在 FOV 对齐下做，
> 都会拒绝录制（`return 2`），不会静默混用。

录完的数据在（`<根>` = `data/stereo`，可选分组目录、可嵌套）：

```text
data\stereo\<可选分组>\<YYYYMMDD-HHMMSS>\
  left.mkv  right.mkv              ← 无损原始视频（唯一不可再生的资产；容器选 avi 时为 left.avi / right.avi）
  left_times.csv  right_times.csv  ← 逐帧时间戳
  session.json                     ← 唯一权威元数据
  calib\<装置档案名>.npz / .json    ← 这次录制用的标定快照（老会话是 stereo_calibration.*）
  derived\                         ← 可再生产物（含 sync_brightness.png 闪光诊断图）
```

`session.json` 是唯一权威元数据；`derived/` 放可再生的 CSV / 图。
**逐文件"能不能删"、分组与 `stereo_mode` 的注意事项见 §15.3。**

2. 第 3 步点 **『离线双目（会话）』**；

```text
derived\traj3d.csv          逐帧 matched, t, X/Y/Z, 左右像素, 极线/交会残差

derived\annotated.mp4       左右并排 + 检测圈 + 轨迹线

```

> **金属球用 `specular`，不要用 `color`**：实测 `color` 会锁背景高光。
>
> **GUI 点选 seed（推荐，不用手写坐标）**：
> 1. 第 2 步检测方法选 `specular`；
> 2. 第 3 步点 **『点选球（双目 seed）』**；
> 3. 选会话目录 → 左图点球心 → 右图点球心；
> 4. **圆心默认严格取你点击的位置，不自动吸附**；如果想让程序帮忙，
>    点 **『吸附Hough圆心』** 才会把左右圆移到附近 Hough 圆心（可选）；
>    半径由 Hough 估计，**滚轮粗调**或在“半径(px)”输入框直接填精确值（8–300）；
>    1080p 下这颗球通常 `r≈45–70`，`r>90` 时界面会提示“半径偏大”；
> 5. 点 **『保存 seed』**，写 `derived\seeds.json`；
> 6. 再点 **『离线双目（会话）』**；没有 seed 时会自动打开点选窗口。
>
> **2026-11-06 起**：`seeds.json` 会记 `ball_kind`（`metal` / `plastic`）。
> 纯色球点选后**仍然用 `color`**（种子用来从点击处取 HSV 并锚定半径），
> 不会被强制换成 `specular`；镜面球才用 `specular`。旧种子文件没有这个字段，
> 按镜面球兼容。单目窗同理，打开会话时会按 `seed.json` 的 `ball_kind` 恢复球种类。
>
> 命令行等价：
>
> ```powershell
> python apps\run_stereo_video.py data\stereo\20261019-221550 ^
>   --method specular ^
>   --seed 1260,830,65 --seed-right 920,830,65 --seed-frame 0
> ```
>
> - 半径按**外轮廓**量（这颗约 65 px，不是预览里的 8–12 px）；
> - 如果离线双目 `0 匹配`：先看日志最后 `[诊断]`；`无左/无右` 大 = tracker 跟丢，
>   多半是 seed 半径太大/点偏；`极线拒` 大 = 左右 seed 中心不在同一球心或不同帧。
>   不要靠放大 `--max-epipolar` 硬吃错配；
> - `--seed` 左路、`--seed-right` 右路，不能共用一个；
> - 自动初始化不可靠，故意不猜；丢失时返回空，不 snap 背景圆；
> - 命令行 seed 会写回 `seeds.json`，保证可追溯。
>
> **双目模式（2026-10-21）**：
> 右上角 `双目模式` 可选 `auto`（默认，按会话/标定推断）、
> `parallel`（强制现有平行双目）或 `angled`（强制大角度/近似直角）。切到 angled 后：
>
> - 标定、录制命令会带上 `--stereo-mode angled`；
> - 实际夹角由标定 R 计算，不要求正好 90.0°；球不保证全程双路可见，
>   单路帧会标记 missing，不硬凑三维；
> - 旧会话没有模式字段 → 自动按 parallel 打开，行为不变；
> - 点 `基线夹角估算`，输入两镜头中心距（基线 B，mm）和球到相机的工作距离（D，m），
>   可看估算的两光轴夹角；
>   90° 对称双目需要 B≈2·D，先确认机械上是否成立。
>
> 详细设计：`docs/planbooks/2026-10-22_双目90度升级.md`。

> **双目工作台（第 3 步下方）**：
> 选任意会话后，状态会显示帧数/sync/seed/轨迹/Z/残差；
> 列表默认显示 `data/stereo` 下全部会话（按时间倒序）。不在这个目录里的会话，
> 点 **『浏览会话…』** 选目录即可加入，然后同样按

> `④ 3D + 视频` → `⑤ 导出 JSON` 操作。
> 坏会话（如帧数 302/304）会直接禁用点选/跑双目/查看，只留校验和打开目录。
>
> **半径、半径锚定门、尺寸门自动阶梯（2026-11-14 起）**：这三件事说的不是同一个尺寸，别混：
>
> - **半径** —— 第 2 步「点选球心」时点球边得到的**像素圆半径**，写进 `derived/seeds.json.radius`，只用来初始化检测器；同一颗球近处约 90 px、远处约 30 px。
> - **像素半径门限**（第 ④ 步「高级」里两个「像素半径门限」框）—— 只把明显过大/过小的候选筛掉，和球的物理直径没有换算关系；**留空即走自动阶梯**（GUI 恒走、无取消开关）。
> - **半径锚定门** —— 勾上第 ④ 步「半径锚点门」后，用左右点选球心三角测出深度 Z，再按真实球直径换算「该有多大视半径」，拒掉半径离谱的假配对；须先点过球心，默认关。
> - **球直径（mm）** —— 填真实物理直径，下传 `--anchor-diameter-mm`；**只喂半径锚定门，不控制尺寸门**。锚点门不勾时该输入禁用、也不下传。
> - **尺寸门自动阶梯** —— 默认路径：用 12 帧试探画面里最大候选，按 0.18 / 0.30 / 0.45 / 0.65 四档比例逐档升，门外还有更大候选就继续升；这样球靠近时不会被写死的上限判成不对。留空两个像素框就走它，命令行不会加 `--no-radius-auto`。
>
> 相关命令行参数（`apps\run_stereo_video.py`）：
>
> | 参数 | 默认 | 作用 |
> | ---- | ---- | ---- |
> | `--anchor-gate on` | off | 打开半径锚定门；须先有 `derived/seeds.json` |
> | `--anchor-diameter-mm` | 0（内置 21.6 mm） | 半径锚定门换算视半径用的真实球径（毫米）；**不影响尺寸门** |
> | `--min-radius` / `--max-radius` | 留空 | 写死像素半径门限；留空即走自动阶梯 |
> | `--no-radius-auto` | 不加 | 显式关掉尺寸门自动阶梯 |

> 两种交付包的区别、目录包怎么导入 → §15.5；清理顺序与备份 → §15.6。

> **⚠️ 没闪光 = 没同步**：`session.sync.method=none` 时三维会错位。
> 录制时开始后 1 秒内闪一次、结束前再闪一次；确认日志出现 `flash +N`。
> 正常 10 秒录制如果没闪光，会自动尝试 `timestamp` 近似同步（看日志）。

### 12.7 GUI 单板链式标定（大角度 / 两路几乎看不到同一区域）

**什么时候用这一条**：各装置窗第②步的「标定方法」下拉共有**五条**路，按窗口过滤，别选错：

| 选哪个 | 前提 | 典型场景 | 出现在哪个窗 |
| ------ | ---- | -------- | ------------ |
| 「两路共视」（joint） | 两路在**每个姿态**都要同时看到同一块板（充分共视） | 近平行（几度到十几度） | 平行窗 |
| 「单板链式」（chain，本节） | 各拍一组内参图，再在**一处两路都能看到整块板**的位置拍参考图（小块共视区） | 大角度但还有一块重叠区 | 大角度窗 |
| 「双板链式（两板固定在同一支架）」（chain_dual） | 两块板刚性固定，**全程不需要两路看到同一块板**，但要一台相机同框拍到 A、B 两板 | 真 90° / 宽基线 | 大角度窗 |
| 「轴向大板（前后推）」（axial） | 两路**平行**，板正对相机、只沿光轴推进已知距离 | 平行、板不能多姿态移动 | 平行窗，见 §12.8.1 |
| 「中轴90°装置（每相机各一次）」（device90） | 两路成 90°，同一块板绕中轴转 90°、两板中心重合，**内参已知** | 大角度、每相机只能正对一次 | 大角度窗，见 §12.8.2 |

> 下拉按窗口过滤：**平行窗**只有 joint + axial，**大角度窗**只有 chain + chain_dual + device90，别的项根本不会出现。轴向大板与中轴 90° 的完整操作步骤见 §12.8。

**拍前**：两台相机装好后**不要再碰**；曝光/对焦锁手动；板要平整、光照均匀不过曝。

**三段怎么拍**（都是**自动连拍**：板停稳约 0.3 秒就自己存，不用按键；`q` 退出）：

1. `拍左内参图`：拿着板在**左相机**前走 15 张左右——四角 + 中心，板面与光轴夹角在 ±45° 内转。
   标签上的 `N/15` 会自己涨，所以不用数张数。
2. `拍右内参图`：同样 15 张，给**右相机**。
3. `拍参考图（双路同时）`：**把板固定在一个位置**（两路都要能看到**整块**板，不要只露一角），
   之后一张都别再挪，然后点这个按钮——一个窗口同时看两路，**同一时刻**存进 `ref_left` 和 `ref_right`，拍 3 对。

   **窗口怎么读**（2026-10-27 改版，之前的"摆放"确实没法看）：

   - 每路画一个「目标区」内框：板**至少填满它**（建议面积 8%~35%，画面左下实时显示 `板 x.x%`）；
     外面那圈灰框是"**不许出界**"——贴边会被"图棋盘贴边"门限拒掉；
   - 每路顶部直接写**这一路为什么还不能存**（`还在动 12px` / `图模糊` / `图棋盘贴边` / `太小`），
     不再只有一句"左 OK"；
   - 底部一行是**两路共同状态**：`两路同时可见 ✓ 可以存`，或者点名哪一路不满足 ——
     参考图的核心就是"同一块板、同一时刻两路都看到"，这一条必须一眼可见；
   - `f` / `F11` 切全屏，`Esc` 在全屏时只退全屏，`空格` 立即存一对，`q` 退出；
     窗口可以拖动改大小，**版式跟着重排**（文字不会跟着分辨率缩到看不清）。

> 参考段为什么合并成一次双路拍摄：它把"左拍完 → 手碰到板 → 再拍右"这个时间差彻底消掉。
> 链式外参靠这两组图把两路拼到同一个世界坐标系（`T_{C_R←C_L} = T_{C_R←W} · T_{W←C_L}`），
> 板挪 1 mm，外参就错 1 mm，而且**看不出来**。

> 为什么参考图必须"板不动"：链式外参靠这两组图把两路拼到同一个世界坐标系
> （`T_{C_R←C_L} = T_{C_R←W} · T_{W←C_L}`）。板挪 1 mm，外参就错 1 mm，而且**看不出来**。

四组目录都有图之后（`left` / `right` / `ref_left` / `ref_right`），「开始链式标定」才会亮。跑完看这三行：

- `实测光轴夹角 xx.x°`——**这是判断装置到底多少度的唯一证据**（由标定算，不是手填）；
- `T_AB : I（单板；参考图 左 3 / 右 3）`；
- `T_AB 重复性 n=…`——参考图之间的离散度。

**两个警告要当真**：

- `[警告] 参考图之间位姿不一致 → 板在拍参考图时动了或对焦变了`：
  外参已经不可信，重拍参考图（这个状态也会写进 `quality["same_board_ref"]`，事后能查）。
- `单板模式 + 夹角 > 60°`：90° 时一块板只能朝两光轴角平分线放，两路都是斜视（约 45° 入射），
  PnP 会有系统偏差（实测 45–60° 入射约 0.45 mm / 0.07°）。板扭得越正越好，参考图多拍几张更稳。

**命令行等价**（不想点界面时）：

```bat
python apps\tools\capture_board.py --out outputs\chain\run1\left --side left --target 15
python apps\calibrate_stereo.py --method chain --same-board ^
  --left-dir outputs\chain\run1\left --right-dir outputs\chain\run1\right ^
  --ref-left outputs\chain\run1\ref_left --ref-right outputs\chain\run1\ref_right
```

### 12.8 两种受限装置的标定（轴向大板 / 中轴 90°）

前面 §12.4 / §12.7 的标定都要求**把板拿在手里多姿态移动**。如果你的装置做不到，
只能按下面两种方式摆板，就用这一节——它们是**新增加的两条路**，原来的 joint /
链式标定完全不受影响。

#### 什么情况用哪一种

| 你的装置 | 用哪个 | 界面入口 |
| --- | --- | --- |
| 两相机**平行**，板正对相机、只能沿光轴前后推 | **轴向大板（前后推）** | 平行双目窗 → 第②步「标定方法」选「轴向大板（前后推）」 |
| 两相机**成 90°**，板一次只能正对其中一台 | **中轴 90° 装置** | 大角度双目窗 → 第②步选「中轴90°装置（每相机各一次）」 |

> 别在平行窗选「中轴90°」、也别在大角度窗选「轴向」——下拉里根本不会出现，
> 因为两者的几何前提完全不同，选错只会得到一份看着正常、实际不能用的结果。

#### 12.8.1 轴向大板（平行双目）

**前提（必须满足，否则算不出来）**：

1. 棋盘格**正对相机**（板面垂直光轴），只沿光轴前后推；
2. **每次推进的距离你知道**（位移台读数或刻度），单位 mm；
3. 方格的**物理边长填对了**（§12.4 的「方格 mm」）。

**怎么拍、怎么归档**：

采集端不用改——现有怎么拍板图就怎么拍，只要**按深度分目录**：

```
你的采集根目录\
  z000mm\  left\  （第 1 个深度的左右图）
          right\
  z010mm\  left\  （往前推 10 mm）
          right\
  z020mm\  left\  （再推 10 mm）
          right\
  ...
```

目录名支持 `z000` / `z010mm` / `0mm` / `10` 等写法，程序按名字里的数字解析推进量；
也可以在第②步「高级」里不填目录名、改用命令行的 `--delta-z 0,10,20,30` 显式指定。

**操作步骤**：

1. 平行双目窗 → 第②步 →「标定方法」选「轴向大板（前后推）」；
2. 展开「高级」，在「采集根目录」里选上面那个根目录（浏览按钮可选）；
3. **「机械保证两光轴平行（强制 R=I）」**：如果两相机是同一支架固定、光轴确实平行，
   勾上——只沿光轴推进时相机间的旋转角本来就测不准，机械保证比图像估计更可靠；
4. 「卷尺量两镜头中心距 mm」建议填（见下面"装反怎么办"）；
5. 点「开始标定」。

**结果里要看的两件事**：

- 产物 JSON 的 `distortion_calibrated`：一定是 `false`。这种拍法**标不出畸变**，
  D 全 0；如果镜头畸变明显（广角），边缘点会有系统误差，需要另做一次常规多姿态标定。
- `quality.verdict`：若填了预期基线且解出的基线差太多，会被判「不可用」而不是"好看的假结果"。

**命令行等价**：

```bat
python apps\calibrate_axial.py --root "你的采集根目录" --cols 8 --rows 5 --square 25 ^
  --assume-parallel --expected-baseline-mm 66.6
```

#### 12.8.2 中轴 90° 装置（大角度双目）

**前提**：

1. 两台相机光轴互成 90°；
2. 板 A **正对相机 1**，绕**板的中轴**（过板中心的中线，不是板边）旋转 90° 后，
   板 B **正对相机 2**；两板中心在空间里重合；
3. **两相机内参已知**——先按 §12.8.1 做一次轴向标定，或用已有的标定产物。

**操作步骤**（只拍两步，原来的 ③④ 不需要）：

1. 大角度双目窗 → 第②步 →「标定方法」选「中轴90°装置（每相机各一次）」；
2. 点「采集标定板图…」，界面只给两步：
   - ① 拍 A 板：正对相机 1，板别动，多拍几张；
   - ② 绕中轴转 90°，拍 B 板：正对相机 2，同样多拍几张；
3. 展开「高级」，填：
   - **内参文件**：选上一步轴向标定产出的 `.npz`（或已有的 `config/calib/*.npz`）；
   - **中轴**：`x` 还是 `y`（你的板绕哪条中线转）；**旋转角**：默认 90；
   - **Z_A / Z_B**（可选）：板中心到相机 1 / 相机 2 的距离 mm。留空则由图像自己解；
   - **卷尺量两镜头中心距 mm**：**强烈建议填**，见下；
4. 点「开始标定」。「重拍某一步」「检查链式输入」在这模式下会置灰——③④ 用不上。

**⚠️ 装反了怎么办（必须知道）**：

「中轴是 x 还是 y」「正转还是反转」填错，程序**不会崩**、残差也照样好看，但结果是错的。
现有判据抓不住它（板确实正对，图像自洽），**唯一的自动信号是基线长度**。实测装错时基线
只偏 7.8%–16.9%，所以：

- **务必用卷尺量两镜头中心距并填进「卷尺量两镜头中心距」**；
- 填了以后，解出的基线差超过 5% 会被判**不可用**并写明"疑似中轴/转向与装置不符"；
- 不填这个值，程序没有任何办法发现装反——结果可能"优秀"但完全不能用。

另外程序会检查内参：如果左右相机焦距差超过 30%（比如本机那份旧大角度标定差 33%），
会警告 `intrinsics_suspect`；它不阻止出结果，但你看到这条就该先复核内参。

**命令行等价**：

```bat
python apps\calibrate_device90.py --left-dir <A板目录> --right-dir <B板目录> ^
  --intrinsics config\calib\你的轴向标定.npz --rot-axis y --rot-angle 90 ^
  --expected-baseline-mm 300
```

#### 12.8.3 这两种方式的已知边界（诚实清单）

- **轴向模式不标畸变**，D 恒 0（`distortion_calibrated=false`）。广角镜头须另做常规标定。
- **轴向模式只沿光轴推进时，相机间旋转 R 弱可观测**（约 1° 不确定度）。平行装置请勾
  「强制 R=I」，用机械保证换精度。
- **中轴 90° 模式依赖正确的内参**：内参错，外参必错，且残差可能依然好看。
- **装置先验（中轴 x/y、转向、基线）填错的代价由你承担**：程序只在基线偏离超 5% 时
  拦住；没有卷尺值时没有自动护栏。
- **真机精度尚未验证**：目前只有合成数据自验（ideal 角点端到端误差 0.000%，
  中轴 90° 相对位姿 R 误差 0.00001°、T 误差 0.0001 mm）。首次真机使用时，请用已知
  尺寸的球做一次往返测量，核对量级再用于数据结论。
- 板建议**双面印棋盘格**：绕中轴转 90° 后，某些转向会让相机看到板的背面，单面印刷会
  检测不到角点（算法能处理 180° 翻转，但检测器得先能看到图案）。

## 14. 清理器：什么能删、什么不能删（2026-11-05 逐项校验）

> **文件地图（哪个目录装什么、删了会怎样）见 §15。** 本节只讲清理器的判据。

主界面「垃圾清理」会先列清单再动手，分两档：

- **推荐（默认勾选）**：删了下次跑就有的东西 —— 运行日志、Python 字节码缓存、
  测试报告、纯探针脚本。
- **谨慎（默认不勾）**：删了要重跑或**重拍**才能再生的东西。

**实验采集数据一律不删**。2026-11-05 把 53 个候选目录逐个打开核过内容，
下面这些都属于「谨慎」，一个都不在默认勾选里：

| 目录 | 里面是什么 |
| --- | --- |
| `outputs/ball_dataset` | 2819 张训练图 + 2819 个 YOLO 标签 |
| `outputs/chain`、`outputs/mono_calib_frames` | 链式 / 单目标定板实拍图 |
| `outputs/chain_frames` | 正在用的标定图（清理器**结构性排除**，根本不列） |
| `outputs/train_ball` | 训练出来的 `.pt` 权重 |
| `outputs/_ab`、`outputs/rec` | 实验轨迹 CSV + 原始 `.mkv` |
| `outputs/backups` | git 仓库备份 bundle |
| `outputs/mono_calib_batch4` | 单目标定结果 JSON |

原先的清理器只按「目录名前缀 + 文件大小」判档，导致下面这些**小但删不得**
的目录被误判成「推荐」：`_cvcheck` 里的 `stereo_calibration.json` / `.npz`、
`_diag` 里的诊断图和 txt 结论、`_handoff_read` 里的交接文档、
`agent_gui_audit` 里的人工复核记录、`tmp_frames*` 里从真实会话抽的帧。

现在多了一道 `looks_like_research_artifact()`：目录里只要含 `.md` 人工文档、
三个以上 `.txt` 记录、`calibration` / `seeds` / `report` / `evidence` 这类命名，
或成组的结果文件（≥5 个且占一半以上），就**降级为谨慎**并在清单里写明原因。
默认勾选因此从 29 项 / 332 MiB 收敛到 11 项 / 39.9 MiB。

> 判据的原则：降级的语义是「我不确定，你自己勾」，不是「这是垃圾」。
> 清理是唯一会减少磁盘内容的操作，宁可少清一项，不可误删一次实验数据。

## 15. 数据与文件都在哪

> 这一节回答四个问题：**东西存在哪 / 哪个删不得 / 哪些能删 / 换电脑怎么搬**。
> 下面的段数与体积都是 **2026-11-11 实测**，会随录制变化 —— 当参考，不当承诺。
> 界面里也有一份精简版：「操作说明」→「数据与文件」分区（见 §13）。

### 15.1 一张总表：目录 → 装什么 → 谁写 → 删了会怎样

| 位置 | 装什么 | 谁写的 | 能不能删 |
| --- | --- | --- | --- |
| `data/stereo/` | **双目会话根**（2026-11-11 实测 45 段 / 约 65 GB） | 录制器 | **不能删** —— 原始视频只能重录 |
| `data/mono/` | 单目会话（6 段 / 约 5.2 GB） | 单目录制器 | **不能删** |
| `data/sessions/` | **旧位置**，只读兼容（当前为空） | 老版本录制器 | 可删；留着也不影响读取 |
| `data/collections.json` | 你手工点的**分组树**（`sid → 节点`） | 数据管理面板 | **不能删** —— 丢了要重新分组 |
| `data/index.json` | 会话状态**缓存**（时间 / 状态 / 帧数 / 大小） | 程序自动重建 | 可删，下次自动重建 |
| `data/_trash/` | 回收站批次 `<时间>_<标签>/` | 清理器 / 数据管理 | 清空前先确认没有要恢复的 |
| `data/calib_pairs/` | 早期单目标定实拍图（50 张 / 164 MB） | 早期采图工具 | 可删，但**重标就得重拍** |
| `config/profiles.json` | **装置档案库**，`active` 指向当前装置 | 装置档案对话框 | **不能删** —— 装置身份全丢 |
| `config/calib/` | 每套装置自己的标定 `<档案名>.npz` / `.json` | 标定 | **不能删** —— 删了要重标 |
| `config/stereo_calibration.*` | 顶层**回落**标定（2026-11-03 旧产物） | 老版标定 | 别删；新装置不该用到它 |
| `config/backup/` | 标定被覆盖前的旧文件 | 标定（覆盖时自动） | 可删（最新的那份别动） |
| `config/mono_calibration.json` | 单目内参（按 `left` / `right` 角色记） | 单目标定 | 别删 |
| `config/cameras.json` | 左 / 右 /「无关」的角色绑定 | `cameras.py identify` | 别删 —— 删了要重新 identify |
| `config/camera_modes.json` | 每档分辨率 / 帧率的探测缓存 | 探测工具 | 可删，会重新探测 |
| `config/gui_state.json` | 界面记住的下拉值 / 上次选择 | 界面 | 可删（等于恢复默认） |
| `outputs/` | 可再生的运行产物（约 3.7 GB，其中 `_ab` 一项 1.6 GB） | 各种跑批 | 多数可删；`_ab` / `rec` / `chain*` / `ball_dataset` / `train_ball` 属谨慎档，清单见 §14 |
| `logs/` | 运行日志（48 MB） | 所有程序 | **可全删** |

一句话记住：**`data/` 删了就没了；`outputs/`、`logs/` 删了能再生。**
`config/` 夹在中间 —— 能再生，代价是**再标定一次真机**。

**分组树的状态符号**（数据管理面板的会话节点前面，工作台同款；按**产物**判，不按某个输入文件判）：

| 符号 | 含义 |
| ---- | ---- |
| `✓` | 有可用三维轨迹（`traj3d.json` / `traj3d.csv` 有足够匹配点） |
| `◑` | 跑过三维但**三维点过少**（匹配率 < 5%，画不出可用轨迹）—— 不是"没做"，仍可打开 3D 查看器 |
| `○` | 有录制 / 输入，但**还没有三维** |
| `—` | 空目录 / 还没开始的分组 |
| `◐` / `✗` | 仅点过球心（有 `seeds.json`）/ 坏会话（帧数矛盾、元数据与产物冲突等） |

老会话只有 `traj3d.csv` 也能识别，不会因为缺 `traj3d.json` 就被误判成"没跑过三维"。

### 15.2 装置档案与标定产物（当前最容易踩雷的地方）

**档案在哪**：`config/profiles.json` 是装置档案库，`active` 指向当前装置。每套档案用
`calibration_path`（**不带扩展名的仓库内相对路径**）指向**它自己那一份**标定 ——
所以"切档案"是真的换标定，不是假动作。

**双目标定落一次，落两个文件**（文件名都跟装置档案名走）：

```text
config/calib/<装置档案名>.npz    ← 程序读的数值
config/calib/<装置档案名>.json   ← 人读副本：基线、夹角、极线 RMS、配对数、判定、采集档、profile 归属
```

每覆盖一次，旧文件自动进 `config/backup/`。

**回落规则（这条要记死）**：

- 只有"档案没配 `calibration_path`、没有激活档案、档案文件损坏"这三种情况，才回落到顶层
  `config/stereo_calibration.*`。现存那份是 **2026-11-03 的旧产物（基线 66.3 mm）**，
  **不是**当前装置的几何。
- 档案配了路径、但**文件不存在 → 直接报错，绝不回落**。这是 `stereo/profiles.py` 里刻意的设计：
  宁可让你先去标定，也不拿别套装置的几何冒充"已标定"。

**当前实况（2026-11-11，务必看清）**：四套档案里只有「平行装置」和「实验性质平行装置1」
真有标定文件；**激活档案是「实验性质大角度1」，它没有标定文件** —— 现在一录制 / 一分析
就会报"指定的标定文件不存在"。两条处置：

1. 在装置档案里**切回已标定的那套**（前提是相机确实装在那套装置上，别为了能跑就随便切）；
2. 或者**先给「实验性质大角度1」标定一次**，结果会自动落到它自己的路径。

**会话里的标定快照**：每次录制会把当次用的标定复制（`shutil.copy2`）进会话的 `calib/`，
并把 sha256 记进 `session.json`；文件名跟档案名走，老会话是 `calib/stereo_calibration.*`。
**读哪个文件永远看 `session.json` 的 `calibration.path`**（相对会话目录），别把文件名当模板照抄。
**删了这段会话就再也无法离线重算** —— `apps/run_stereo_video.py` 只从这里读标定。
这是全套文件里最"看着没用其实要命"的一项。

**单目标定**只有一个文件 `config/mono_calibration.json`，**按角色名（`left` / `right`）记、
不按物理设备分文件**。`camera_source` 是 `role-only` 时**无法核对是哪台机器** ——
换了机器不换文件，就只能指望两台的焦距与主点一致。换机请重标。

### 15.3 录制会话：每个文件干什么、哪个删不得

**目录形态**：`<根>/<可选分组>/<时间戳>/`，**支持任意嵌套**（默认深度上限 5 层）。
当前 45 段分布在三处：根层 29 段 + `parallel/` 15 段 + `angled/` 1 段 ——
**只看 `data/stereo/` 第一层只能数到 29 段**（另外 16 段在分组目录里；而那一层的 31 个
条目里还有 2 个是分组目录本身）。界面里的树按索引建，别拿资源管理器的一层目录当会话数。

| 文件 / 目录 | 是什么 | 删了会怎样 |
| --- | --- | --- |
| `session.json` | **唯一权威元数据**：相机 identity / port、分辨率、帧数、实测 fps、同步方式与置信度、`calibration.path` + sha256、`stereo_mode` | **不能删** —— 会话直接变"坏会话" |
| `left.mkv` / `right.mkv`（容器选 avi 时为 `left.avi` / `right.avi`） | HFYU 无损原始视频，唯一不可再生的资产 | **只能重录**（本机 1080p / 10 s 单路中位 758 MB，最长的一段 1.28 GB） |
| `left_times.csv` / `right_times.csv` | 逐帧 `(帧号, 时刻, 间隔)` | 精度**永久下降**（时间戳配对只能退回索引 + 偏移） |
| `calib/` | 这次录制当时的标定快照 | **不能删** —— 删了这段会话再也无法离线重算 |
| `derived/` | `seeds.json`、`traj3d.csv`、`traj3d.json`、`visualization.json`、`traj3d.png`、`annotated.mp4`、`*_brightness.npy`、`sync_brightness.png` | **全部可重跑，删了不用重录**（亮度 npy 要重扫一遍视频，没有单独的重算入口）；只有 `seeds.json` 例外 —— 那是你人工点的球心，删了要重点 |

**单目会话长这样**（`data/mono/<时间戳>/`）：

```text
clip.mkv          ← 原始视频
clip.mkv.json     ← 录制器写的边车：实测分辨率 / 帧数 / 编码器
session.json      ← 会话元数据
derived/          ← traj.csv / annotated.mp4 / visualization.json
```

单目**要进 3D 查看器，必须有 `derived/visualization.json`** —— 没有就只是"跑完了"，
查看器里看不到结果，得先跑一遍 `apps/run_video.py --vis-json`（或用数据管理的导出）。

**`stereo_mode` 为 `null` 的意思是"没记录"，不是"平行"**：2026-11-04 之前的会话都没有这个字段。
目录名与 `session.json` 记录不一致时，界面会把模式列标 ⚠ 模式冲突 ——
`.npz` 里的几何和目录名表达的意思不是一回事，以 `session.json` 为准。

### 15.4 标定板照片

**照片不在 `data/`**，按装置分成两处：

- 链式 / 双板标定 → `outputs/chain_frames/<时间戳>/`，里面按 `left`、`right`、`ref_left`、
  `ref_right`、`board_b`、`pair` 等子目录分组；
- 单目标定 → `outputs/mono_calib_frames/<时间戳>/`。

两处根目录都会有一个 _current.json 指针，指向"当前这次"（还没采过图时就没有）。

**2026-11-09 起每次采图建一个独立会话目录**，不再往固定目录追加 —— 之前真机实测出过一次
混样本（`board_b` 里 344 张混了三个日期的 304 + 40 张）。没有当前会话时程序
**明确报错，绝不回落到根层**。

**平行装置（joint）标定默认一张图都不存**：实时取帧只在内存里，只有显式 `--save-pairs`
才落盘。所以"找不到上次平行标定的照片"不是丢了，是从来没存。

早期单目产物在 `data/calib_pairs/<日期>/left|right/001.png…`（当前 50 张 / 164 MB）。

**能不能删**：删了不会让已有标定失效（`.npz` 早就算好了）；但要**重标就得重拍**。
占空间（164 MB 起），建议标定通过后保留最近一次，旧的按需清。

### 15.5 导出与交付：两种包，别搞混

**① zip 包**（现有 GUI 就这一个）：选好会话与类别 → 一个 zip，里面是

```text
sessions/<会话ID>/{metadata, derived, derived/plots, calibration, videos, videos/raw}
manifest.json   会话清单、类别、文件大小
README.md       口径说明：类别、脱敏口径、变量字典
```

类别可勾（默认不含视频），可脱敏（相机 identity / name / port、会话 label / notes、
platform 会被移除），默认落在 `outputs/exports/detailed/`。

**② 自包含目录包**（`apps/package_export.py`，2026-11-11 新增）：**目录本身就是交付物**，
接收方不解压、不联网、不依赖本仓库也能看懂。

```text
package.json    机器读的清单：会话、类别、文件、标定来源
README.md       给人看的导入说明
sessions/<会话>/…
calib/<标定基名>.npz | .json
```

package.json 里的 calibration 块记 `path` / `json` / `source` / `note`；`source` 是三态：
`registered`（标定 meta 登记了装置名）、`unregistered`（老标定，没登记）、
`none`（这个包不含标定）。`note` 固定写"sha256 只证搬移无损、不证来源" ——
别把它读成"来源已核实"。

导入用 `import_package(..., dry_run=True)`：**默认一个字节都不写**，只回一份"将会写哪些
路径"的清单；确认后 `dry_run=False`，目标已存在的会话记进 `problems` 并跳过，不覆盖你现有
的数据。标定落点用 `calibration_dir=` 显式给，不给就不拷（不猜落点）。中文名与文件名逐字不变。

> ⚠️ **诚实说明**：目录包目前**只有库和命令行，GUI 里还没有按钮** —— 别在界面上找"导出目录包"。
> 手工导入也行：把 `sessions/<会话>/` 整个拷到 `data/stereo/` 下，目录名（时间戳）就是界面的排序键。

### 15.6 回收站、清理与备份

**回收站**：`data/_trash/<时间>_<标签>/`。清理器与数据管理都是"先预览 → 再移动"，
**不直接永久删除**；恢复走 **『回收站…』**，彻底删除要输入 `DELETE`。
**只有"整个会话"这种操作才会动原始视频**，其余（"只清 `derived/`"）是文件级回收。

**清理顺序**（判据细节在 §14，这里只讲先后）：

1. **先备份**（见下）；
2. `logs/` —— 48 MB，纯运行日志，可全删；
3. `outputs/` 里的诊断目录 —— 可删；
4. **最后才碰 `data/`**。

`outputs/chain_frames/` 是**清理器白名单保护的**（它是标定输入，删了要重拍），别整目录清掉。

**磁盘账本**：无损录制单路 10 秒约 0.7–0.8 GB（1080p 实测中位 758 MB），一段双目会话
1.5–2.5 GB，1440p 更高。当前 `data/` 约 70 GB（`data/stereo` 约 65 GB + `data/mono` 约 5.2 GB
+ 早期标定图 164 MB）——
**录二十次就是几十 GB**，开录前先看盘。

**备份与迁移（最重要的一条）**：`data/` 与 `config/` **整个被 .gitignore 忽略**，
git 里只有 data/README.md 和 config/.gitkeep。所以换机器、重装系统、跑一次 `git clean -xfd`，
**标定和全部录制会彻底消失**，只有手工拷贝能救。

要带走的最小集合：

```text
config/profiles.json          装置档案（没有它，标定文件不知道属于哪套装置）
config/calib/                 每套装置自己的标定
data/collections.json         你点的分组树
data/stereo/<你要留的会话>/    录像本体
```

放回原位（相对路径不变）后，装置档案与分组就都回来了。`data/index.json` 不用带，程序会重建。
