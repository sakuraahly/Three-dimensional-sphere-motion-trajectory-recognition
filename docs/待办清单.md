## 怎么用

- 这张表**不手写细节**，只写：`ID / 状态 / 一句话 / 卡在什么或证据 / 详情指路`。
  为什么这样能防漂：细节散着没事（它本来就在各章节里），**状态**一旦有第二份就会矛盾。
- 加一条：先给下一个 `B-NN`，写清"卡在什么"，再在 `docs/交接文档.md` 对应章节补细节。
- 做完：状态改 `done` 并填 `commit=<短 hash>`。**不给 hash 不算做完** ——
  检查器会去 `git log` 里核对（这是"结论要有产物"的落地）。
- 决定不做：状态写 `wontfix` 并写清为什么，**别删** —— 删了下次还会有人重新提。

## 状态词汇（只认这四个 + 一个）

| 状态      | 含义                                     | 硬要求                                                 |
| --------- | ---------------------------------------- | ------------------------------------------------------ |
| `open`    | 现在就能干（不需要相机、不需要用户决策） | —                                                      |
| `doing`   | 正在做                                   | —                                                      |
| `blocked` | 干不了                                   | **必须写清卡在什么**（缺相机 / 缺用户决策 / 缺数据）   |
| `done`    | 已交付                                   | **必须带 `commit=<短 hash>`，且能在 `git log` 里查到** |
| `wontfix` | 明确不做                                 | **必须写清为什么不做**，否则下次会被重新提             |

> 校验实现：`apps/tools/check_standards.py` 的 **D 类**（`启动程序.bat standards` 会跑）。
> 它还查一条**反向**：`交接文档.md` 里每个"待办 / 还没做"章节，必须至少被本表一条引用 ——
> 否则就是"有个待办没人管"。加新章节而不登记，检查器会红。
>
> ⚠️ **判定口径是按标题字面**：章节标题里出现「待办 / 还没做 / 尚未处理」就算待办章节。
> 所以**介绍这套机制本身的章节，别把这几个词写进标题**（§26 就是这么改的：
> "待办清单与自动门" → "单一清单与提交前的自动门"）。
> 不做"看起来像元信息就跳过"的启发式 —— 那种豁免迟早会漏掉真的待办。
