### 1.3 OpenCV 5.0 的 API 差异（不记住会白花半小时）

| 坑                                         | 现象                                                                | 本项目怎么办 |
| ------------------------------------------ | ------------------------------------------------------------------- | ------------ |
| `calibrateCamera` **物体点必须 float32**   | float64 报参数错；float32 正常（`K`/`distCoeffs` 用 float64 无妨）   | `calib/stereo_calib.py:173-183` 的 `_as_objpoints()` 统一转 float32，注释写明了原因 |
| `cv2.computeReprojectionErrors` **不存在**  | `hasattr(cv2, "computeReprojectionErrors")` → `False`               | 改用 `cv2.calibrateCameraExtended` 拿逐图重投影误差（`calib/stereo_calib.py:116-126`），或自己 `projectPoints` |
| `cv2.aruco` **只有新 API**                  | `cv2.aruco.detectMarkers` 已移除；只剩 `CharucoBoard` / `CharucoDetector` / `CharucoParameters` | 本项目标定走**棋盘格**（`findChessboardCornersSB`），没用到 aruco；将来换 ChArUco 板才要面对 |

实测复现（30 秒）：`hasattr` 那两行在 OpenCV 5.0.0 上直接返回 `False False`；把 `calibrateCamera` 的物体点做成 `float64`（其余不变）会报下面这句，换成 `float32` 立刻正常：

```
error: (-210:Unsupported format or combination of formats) objectPoints should contain vector of vectors o...
```

```powershell
& $PY -c "import cv2; print(cv2.__version__, hasattr(cv2,'computeReprojectionErrors'), hasattr(cv2.aruco,'detectMarkers'))"
```

> 这是 OpenCV 5 的行为，OpenCV 4 时代同一份代码多数能过 —— 从旧项目抄代码最容易中招。

## 2. 回归测试工作流

### 2.1 十个测试，各守什么

`tests/` 下现有 **21 个** `selftest_*.py`（`Get-ChildItem tests\selftest_*.py` 数得出来）：

| # | 文件                          | 一句话：它守什么                                                                 |
| - | ----------------------------- | -------------------------------------------------------------------------------- |
| 1 | `selftest_synthetic.py`       | **单目全链路**：合成真值下 clean / realistic / panning 三场景的检出率、圆心、半径、三维、预测误差 |
| 2 | `selftest_pair_source.py`     | **成对取帧 + 同步偏移语义**：把帧号编进画面，验证"取到的到底是第几帧"、偏移正负号、图片/视频两条取帧路径、`from_args` 参数映射 |
| 3 | `selftest_stereo_calib.py`    | **双目标定**：真值装置下内参 / 基线 / 相对旋转 / 极线误差 + 端到端三维精度（最后一项才是"能不能用"） |
| 4 | `selftest_stereo_pipeline.py` | **同步 + 极线配对 + 三角测量**：直接喂真值像素、不含检测；人为平移 ±k 帧能不能找回 |
| 5 | `selftest_stereo_branch.py`   | **双目整条链路**：真渲染两路画面 + 两路真检测 + 三角测量；顺带量化"右路滞后 1 帧 → 三维误差 34 倍"、钉住基线符号 |
| 6 | `selftest_camera_registry.py` | **摄像头设备管理**：身份 / 端口解析、索引兜底、"绝不静默用错相机"。全注入假数据、**不开任何相机**，`--probe` 才碰真机 |
| 7 | `selftest_camera_motion.py`   | **相机自运动**（本轮新增）：`is_moving()` 迟滞状态机 + 位移换算方向（真值不变时报出值不许随 `work_width` 变） |
| 8 | `selftest_preview_lib.py`     | **PPT 预览连线画没画出来**（本轮新增）：用像素证据判"整页不再空白"；缺 `python-pptx` / `Pillow` 时整体 `[跳过]`，**算通过** |
| 9 | `selftest_camera_quality.py`  | **相机画质会诊**：把"糊"和"卡"分开的判据 —— 蒙雾（动态范围被压扁）/ 过曝 / 过暗 / 残帧（下半幅常量）。全合成图，**不开相机** |

分工别搞混（`selftest_stereo_branch.py` 头部自己写了一段）：3 只测标定、4 只测算法、5 测"接起来"。**谁也不能替代谁** —— 3 和 4 假设"像素检测是准的"，而实际误差的大头常常在检测那一侧。

### 2.2 判定口径（只有一条标准）

```powershell
$PY = "$env:USERPROFILE\miniforge3\envs\myenv\python.exe"
Get-ChildItem tests\selftest_*.py | ForEach-Object {
    & $PY $_.FullName *> "$env:TEMP\$($_.BaseName).log"
    "{0,-30} exit={1}  {2}" -f $_.Name, $LASTEXITCODE, (Select-String "$env:TEMP\$($_.BaseName).log" '判定结果').Line.Trim()
}
```

| 判据             | 说明                                                                                   |
| ---------------- | -------------------------------------------------------------------------------------- |
| 逐项结论         | 多数测试逐项打印 `[通过]` / `[不达标]`，少数（如 `selftest_camera_motion.py`）把"通过 / 不达标"写在行尾 —— **格式不统一，别写脚本去 grep 单条** |
| **最后一行**     | 必须是 `判定结果：全部通过`；出现 `判定结果：有不达标项` 就是失败                       |
| **进程退出码**   | 必须是 `0`。10 个测试的 `main()` 都是 `return 0 if ok else 1` + `raise SystemExit(main())`，CI 里看退出码最省事 |
| `[跳过]` 也算通过 | `selftest_preview_lib.py` 缺 `python-pptx`/`Pillow`、`selftest_pair_source.py` 的真机双相机部分、`selftest_camera_registry.py --probe` 都会 `[跳过]` 且保持退出码 0。**跳过不等于验证过**，只是不让环境缺失变成假失败 |

逐条命令就是 §2.1 表里的 21 个文件，形如 `& $PY tests\selftest_synthetic.py`（这个最慢，约 1 分钟）；要一次跑完并核对判定行与退出码，用上面的循环。

### 2.3 什么时候必跑

**改任何代码之后** —— 这是本项目的质量底线，没有第二个防线。

- 碰了 `sphere_tracker/`、`calib/`、`stereo/`、`apps/` → **21 个全跑**；只改文档 → 跑一个轻量的（如 `selftest_camera_motion.py`）确认环境没坏即可。
- 碰了精度相关的代码 → 除了"全部通过"，还要**逐项对比改前的数字**。本项目历史上确实靠这个拿到过结论：一轮整理 + 三个 bug 修复之后，六个既有测试的**每一个精度指标逐字不变**（只有 fps 列随机器负载浮动）—— 有对照才敢说"零行为变化"。
- ⚠️ 图形启动器只挂了一个 `selftest_synthetic` 按钮（`启动程序.py:392-394`）。**21 个测试要在命令行自己跑**，别以为点一下按钮就等于跑完了。

def main() -> int:
    print("=" * 62)
    print("<测试标题>")
    print("=" * 62)
    ok = test_xxx()
    print()

## 6. 代码风格约定（从既有代码总结）

### 6.1 注释与文档字符串用中文，解释"为什么"而不是复述代码

**判断标准**：把注释删掉，读者还能从代码本身看出来的，就是废话，不要写。三个真实例子：

```python
# sphere_tracker/detectors/motion.py:196-197
# 注意：形态学"闭"会把团块胀大，直接导致半径偏大 -> 测深偏小。
# 所以只用 1 次闭运算，半径的精度靠后面的圆拟合找回来。

# calib/board.py:139-142
#     SB + EXHAUSTIVE + ACCURACY   约 300 ms   <- 精确但慢，只能用在"要收的那一帧"
#     SB 不开 EXHAUSTIVE           约 93 ms
# EXHAUSTIVE 在**找不到板**时会穷举搜索，所以绝不能每帧开。

# stereo/triangulate.py:104-110
# 视差用**绝对值**判范围，符号另判。为什么不能直接写
# `if not (min <= disparity <= max): continue`：那等于把"视差必须为正"藏进了范围检查里。
# 一旦左右装反 …… 每一个点都被静默拒绝（配对率 0%），而三角测量本身没错，根本查不出来。
```

共同点：**都带数字或具体后果**（"半径偏大 → 测深偏小"、"300 ms"、"配对率 0%"）。只写"这样更稳"没有信息量，写"不这样会差 36 倍"才拦得住下一个人改回去。

### 6.2 阈值 / 参数集中在 `sphere_tracker/config.py` 的 dataclass 里

不要在使用处散落魔数。改参数只改一处，并且能存成 JSON 复用（`AppConfig.save()`）。

| dataclass        | 管什么                                                       |
| ---------------- | ------------------------------------------------------------ |
| `ColorConfig`    | HSV 范围、形态学核、颜色预设（`preset("orange_ball")` 等）    |
| `DetectorConfig` | 方法选择、尺寸/形状门限、霍夫参数、背景差分、**相机运动补偿**、融合门限、AI 后端 |
| `TrackerConfig`  | 卡尔曼阶数/噪声、门控、机动检测、轨迹来源（观测 or 滤波）     |
| `CameraConfig`   | 内参、视场角、球直径、是否算三维                             |
| `PredictConfig`  | 预测方法/时长、拟合窗口、像素重力约束                         |
| `VizConfig`      | HUD / 拖尾 / 掩膜 / 三维面板开关                              |
| `AppConfig`      | 上面六个的聚合，负责 save / load                             |

新增参数先问"它属于哪个 dataclass"，写进去并加一行说明**取值依据**。样板是 `config.py:76-83` 的 `min_circularity`：它写了"真实摄像头下实测真球只有 0.61~0.63，原来定 0.62 正好卡在临界点，导致约 30% 的帧被误杀"—— 这种注释能阻止下一个人再调回去。

### 6.3 其余约定

## 8. 两条方法论（这个项目最值钱的部分）

### 8.1 合成真值自测

**为什么需要**：真实摄像头前你永远不知道"正确答案" —— 球心在哪个像素、深度几米，没有真值就没法说
"我的检测差 0.5 px"。所有精度数字（检出率 100%、圆心 0.54 px、半径 0.06 px、极线误差 0.067 px、
1 m 处 1.13 mm）**全部来自合成真值**；它们的价值是"回归防线"，不是"性能承诺"。
`tests/selftest_synthetic.py:52-58` 的 `Scene` 就是真值生成器：

| 机制           | 实现                                                                 |
| -------------- | -------------------------------------------------------------------- |
| 三维真值       | 在三维空间按真实重力 `g=9.80665` 以 1 ms 步长积分，含落地反弹（恢复系数）、前后/左右碰壁 |
| 像素真值       | `project(t) -> (u, v, r)`：球半径恒定、`r = f·R/Z` 随深度自然变化（`selftest_synthetic.py:147-154`） |
| 相机自运动真值 | `pan_offset(t)`：匀速横移多少像素是已知的，所以"补偿做对了没有"可以量化 |
| 恶劣条件与评估 | 逐帧噪声、按曝光模拟的运动模糊、**两个陷阱干扰物**（与球同色的白方块、与球同形的橙色圆）；`run_case()` 逐帧比对检出率 / 圆心 RMSE / 半径 RMSE / 三维 RMSE / 预测误差 |

**精度必须折算到同一距离才能比。** 深度误差服从

```
εZ = Z² / (f · B)        # 1 px 视差误差 → 多少米深度误差
```

`tests/selftest_stereo_branch.py:192-209` 就是这个公式的实现（`depth_error_coeff()` /
`mm_at_1m()`），测试自己会把"折算到 1 m 处"打印出来。三个推论：

1. **`Z` 是平方项**：4 m 处要达到 1 m 处的同等精度，检测精度得提高 16 倍。"4 m 处 30 mm"和"1 m 处 10 mm"不是一回事。
2. **数值接近纯属巧合**：`15.1 mm`（`selftest_synthetic.py`，球径 22 cm、3.7-4.4 m）与 `15.6 mm`（`selftest_stereo_branch.py`，另一套装置）**不可直接比较**（`项目总纲.md` §4.4 陷阱 3）。
3. **验收口径是"1 m 处 ≤ 10 mm"**，任何新数字都要折算过去再跟它比。

写新合成场景的要点（都是踩出来的）：两台相机的贴图比例必须一致（坑 9）、像素级断言别自己手算中间量（坑 16）、存素材别用 mp4v/XVID（坑 17）。

### 8.2 "数字漂亮 ≠ 能用"

**双目这一整条链路（标定、同步、配对、三角测量）从未在真实相机上跑过。** 所有漂亮数字都来自合成
场景，而真机的镜头畸变、光照、白平衡漂移、两路同步误差都比合成恶劣。所以：**把合成数字当"上限参考"，不当"性能承诺"。**
**本轮刚发现的反面实例**（`fix(camera_motion): 位移换算方向写反` 那个提交）：

| 项                     | 内容 |
| ---------------------- | ---- |
| 症状                   | `camera_motion._estimate_features()` 把"小图上解出的相似变换"换回全分辨率时写成 `S @ M_small @ Si`，正确方向是 `Si @ M_small @ S` |
| 后果                   | 旋转/缩放项怎么夹都一样，**只有平移项差一个 `s²`**。默认 `work_width=320` 配 1920 宽画面 `s=1/6`，位移被**缩小 36 倍**；`motion.magnitude` 偏小 → `is_moving()` 几乎永不判"在动" → `detectors/motion.py` 的相机补偿（坑 10）**永远不会启用**；`matrix` 平移同比例偏小 → `warp_to_current()` 对不齐，差分退化成"月牙"（坑 2） |
| **合成测试为何没抓住** | 合成 panning 场景**恰好走 grid 分支**（特征点在缩放图上没凑够内点），而 `_estimate_grid()` 的 `med / s`、`_estimate_phase()` 的 `sx / s` 两处换算都是对的 —— **三个方法里只有主力那个错**，于是"补偿把半径误差从 1.58 px 降到 0.23 px"依然成立，把 bug 完整盖住了。而真机画面纹理丰富，走的正是 features 分支 |

由此提炼三条可操作规则：

1. **凡"缩放到小图算完再换算回去"的地方，都要有一条"结果与缩放比例无关"的断言。** 已钉进 `tests/selftest_camera_motion.py:192-205`：真值固定 16 px，`work_width` 取 160 / 320 / 640，报出值都必须 ≈16 px。
2. **合成场景只覆盖一条分支 = 没覆盖。** 加场景时问一句"这条路径真会走到我想测的分支吗"，最好让估计方法可注入，逐个分支单独测。
3. **报出数字前先问"这个数字从哪来"**：来自合成 → 只能说"回归通过"；来自真机 → 才能说"能力"。真机没跑过的模块，文档里一律标"未验证"。

## 9. 沙箱里做不了什么（省时间，别反复试）

本项目的 agent 沙箱**不在交互式桌面会话里**。这不是机器坏了，也不是 OpenCV 缺后端 ——
`getBuildInformation()` 显示 `DirectShow: YES` / `Media Foundation: YES` / `FFMPEG: YES`，
是会话隔离。下表都在本沙箱里现场复现过：

| 想做                                               | 实际结果 | 替代 / 结论 |
| -------------------------------------------------- | -------- | ----------- |
| `cv2.VideoCapture(0)`（任意 index / 后端）          | DSHOW：`VIDEOIO(DSHOW): backend is generally available but can't be used to capture by index`；MSMF 同样；FFMPEG：`should be configured with libavdevice`；obsensor：`Camera index out of range` → **全部 `opened=False`** | **相机与帧率实测只能让用户在本地跑** |
| `Get-PnpDevice -Class Camera`                      | `拒绝访问` | 见下两条 |
| `Get-CimInstance Win32_USBController`              | `拒绝访问` | 见下两条 |
| `pnputil /enum-devices /connected /location`       | ✅ 可用（本机 3056 行）。`Location Paths` 里有 `ACPI(...)#ACPI(XHCI)#ACPI(RHUB)#ACPI(HS03)#USB(3)` 这种段，**`HSxx` / `SSxx` 才判得出 USB 速率** | 查设备与端口拓扑用这条 |
| 读注册表 `HKLM:\SYSTEM\CurrentControlSet\Enum\USB`  | ✅ 可用（本机 50 个子键，能列出 `USB\VID_1BCF&PID_2A25...`） | 用 `ParentIdPrefix` 拼设备树；`Device Parameters` 子键里**没有**速率字段 |

补充：

- `HSxx` ≠ "插在 USB 2.0 口"：`HS` 是 High Speed（USB 2.0 速率），`SS`/`SSP` 才是 SuperSpeed。设备本身只支持 2.0 时插 3.0 口也一样是 HS —— 判"换口有没有用"要看**设备规格**，不是口子颜色（坑 19）。
- 沙箱里**能做**：跑不需要相机的 selftest、`py_compile`、`--help` 检查参数、用上面两条查硬件拓扑、写合成素材。
- 沙箱里**做不了**：任何要真采一帧的指标（帧率、分辨率、黑帧判定）、真机标定、`apps/tools/cameras.py identify`。
- 网络是"分工具"的：`web_search` / `web_fetch` / `pip install` 可用，PowerShell 的 `Invoke-WebRequest` / `curl` 直连会失败（执行环境的出网限制，不是断网）。
