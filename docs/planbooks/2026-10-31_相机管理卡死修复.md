# 相机管理「卡死」修复 — 计划书（2026-10-31）

> 用户指令：「双目摄像机的摄像机管理依然是卡死了,确定一下目前的摄像机管理是不是可以泛化使用的版本,
> 还是只是针对几个摄像头的特定版.」→ 判定已给出（半泛化），用户选定范围：

> **不碰 MSMF 平台抽象**（那属"全面泛化"档，另议）。

---

## 1. 现象与定位（只读审计结论，均带 `文件:行号`）

「卡死」**不是死锁**，是三个可独立验证的**等待源**叠加，且其中两个**不可中断**：

| #   | 等待源                                                                                                                       | 上界                                                                                                                                        | 现症状                                                                                                                                             |
| --- | ---------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| A   | [`cmd_identify`](../../apps/tools/cameras.py#L807) 逐台**串行**开相机；每台的打开+等首帧发生在 `CameraSource` **构造函数内** | `PREVIEW_FIRST_FRAME_S=30s`（[:236](../../apps/tools/cameras.py#L236)）/ `PREVIEW_BUDGET_S=40s`（[:239](../../apps/tools/cameras.py#L239)） | `n×30s`，6 台≈3 分钟；**期间按 Esc/q 完全无效**（按键循环 `_preview_and_assign` 只在**首帧到达后**才跑，[:376](../../apps/tools/cameras.py#L376)） |
| B   | [`CameraPairReader.__init__`](../../stereo/pair_source.py#L359) 两路并行开后 `th.join()` **无 timeout**                      | 无（只有内部 `search_budget_s` 间接封顶）                                                                                                   | 内部线程若在 cv2 驱动层挂住，主线程**永久**等待；`daemon=True` 只保证进程能退，不保证主线程不被卡                                                  |
| C   | [`select_cameras`](../../sphere_tracker/camera_registry.py#L918) 给"未被 PnP 枚举到的"索引补 `range(0, max_index+1)`         | `7 × 40s`                                                                                                                                   | phantom 索引（不存在的编号）也要试开一次，纯浪费；`max_index=6` 是**写死的上限**，第 7 台及以后永远发现不了                                        |

`_WaitTicker`（[:250](../../apps/tools/cameras.py#L250)）已让等待期**有输出**，所以"一个字都不打"这一条已解决；
**未解决的是"打出来了但你拦不住、也等不完"**。

## 2. 范式审计（§11.7 硬条款 — Leader 亲自做）

逐条列出本方案沿用的隐含前提，并判定**在新条件下是否成立**：

| #   | 隐含前提                                             | 成立？                       | 依据 / 换成什么                                                                                                                                                                                                                                                |
| --- | ---------------------------------------------------- | ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| P1  | 「等待不可避免，只能靠'告知'缓解」                   | ❌ **不成立**                 | 等待可以三向收窄：① **可中断**（Esc/s 立即放弃当前台）；② **可缩短**（phantom 连续失败即停）；③ **上界可配**（`--first-frame-timeout`）。只加 ticker 是把"卡死感"说成"在等"，没解决"拦不住"                                                                    |
| P2  | 「每个索引都值得试一遍」                             | ⚠️ **部分成立**               | 对本机真相机（`#0/#1`）成立；对**不存在**的编号不成立 —— 试开一次最坏 40s。前提核实：`select_cameras` 里**真设备（PnP 枚举）先试、phantom 在后**（[:916-922](../../sphere_tracker/camera_registry.py#L916-L922)），故"phantom 段连续失败即停"不会误伤真设备    |
| P3  | 「`th.join()` 无 timeout 也无害，因为内部有 budget」 | ❌ **不成立**                 | 内部 budget 只保证"正常情况下会返回"，**不保证线程一定结束**（cv2 打开/首次 grab 可在驱动层挂住）。daemon 与主线程死等是两件事                                                                                                                                 |
| P4  | 「Esc/q 在等待期间也有效」                           | ❌ **不成立**                 | 按键循环在 `_preview_and_assign` 里、位于 `_open_preview` **之后**；等待期最长 40s 内任何键都无效果                                                                                                                                                            |
| P5  | 「从 GUI 启动时也能读到控制台键盘」                  | ❓ **未证实，按不成立处理**   | GUI 用 `tasks.start([...cameras.py...])` 起**子进程**（[`_gui_app.py:579`](../../apps/_gui_app.py#L579)、[`_gui_stereo.py:666`](../../apps/_gui_stereo.py#L666)），stdin 不一定是控制台 → `msvcrt.kbhit()` 可能抛/恒假。**必须兜底成"不可中断"且绝不因此崩溃** |
| P6  | 「把超时调小是安全的」                               | ❌ **不成立**                 | 本机慢相机实测首帧 ~24s（[:230-231](../../apps/tools/cameras.py#L230-L231)）；30s 是**实测下限**，调小会让该相机"从界面上消失"。故**只加参数、默认值一字不改**                                                                                                 |
| P7  | 「跳过一台 = 漏掉一台」                              | ✅ 成立，但**是用户明示意图** | 按 Esc 就是"我不要等它"；且跳过**不写配置**（`_preview_and_assign` 返回 `None` = 不改角色，[:815](../../apps/tools/cameras.py#L815)）                                                                                                                          |

**明确不换方法的**：MSMF 平台抽象 / `INDEX_BACKEND` 语义 / 动态路数（`need=2`）/ 内置·红外默认名收进配置
—— 这些在"全面泛化"档，且改变 PnP 位次语义属**原理级**改造，与本方案不同量级。用户已明确排除。

**结论**：P1/P3/P4 是**必须修**的范式失效；P2/P5 是**必须留兜底**的边界；P6/P7 是**必须守住的约束**
（不改默认超时、跳过不写配置）。无"spec 与原理冲突"待升仲裁的项。

## 3. 目标与范围

**做**（三条，互不重叠的文件）：

- **A. identify 可中断 + 超时可配**（`apps/tools/cameras.py`）
  - 把"开预览"改成**后台线程 + 主线程轮询键盘**：等待期按 `Esc` / `s` → 立即放弃当前台（返回 `None`，不写配置、不崩）；后台若最终打开成功则**自动 `release()`**（不留悬空相机）。
  - 新增 `--first-frame-timeout SEC`（默认 **30**，即现值），整台上限派生为 `timeout + 10`（保持现 30→40 关系）。
  - 控制台不可读时（P5）→ 该功能**静默降级为"不可中断"**，不报错、不崩；文案说明。
- **B. `pair_source` 打开加超时**（`stereo/pair_source.py`）
  - 抽出可测的 `_join_all(threads, timeout_s) -> list[Thread]`（返回超时后仍存活的线程）；超时 → 记录明确错误、释放已开的那路、走既有的"换下一个后端 / 抛错"路径。
  - 超时常量 `OPEN_JOIN_TIMEOUT_S`，取值须 **> `search_budget_s`(60)**。**定为 `150.0`**
    （原写 90.0，Critic 指出 `_open` 在打不开时会再试一次 `backup_camera`，
    正常路径最坏 ≈ 2×60 → 90.0 会把"正常但慢 + 走了备用相机"的相机误判成超时；
    150 = 2×60 + 30 余量）。
- **C. `select_cameras` 自适应扫描**（`sphere_tracker/camera_registry.py`）
  - phantom 段（未被枚举到的索引）**连续失败 `max_consecutive_miss=2` 次即停**；`max_index` 保留为**上界安全网**（不再是唯一的终止机制）。
  - 真设备段（`rank_candidates` 结果）**行为一字不变**。

**不做**（明确记录，不假装不存在）：平台后端抽象、动态路数、avoid_names 收进配置、`need=2` 改动、
`traj3d.*` / `visualization.json` 契约改动、默认超时值改动。

### 7.5 已知未覆盖 / 未验（诚实记录）

1. **真机**：`OPEN_JOIN_TIMEOUT_S=150` 下"驱动真挂死"路径只能以缩短常量的等价分支证明；GUI「换相机…」原症状需真人走一遍。
2. `pair_source.py` 的 `failures` 分支 `print` **无自动化守护**（`selftest_pair_source` 只测 `_join_all`；替身需注入 `CameraSource`，代价高于收益）—— 明记于此，不假装有。
3. 连续跳过会在后台留下若干"仍在开相机"的 daemon 线程（一旦开出会自行 `release()`）；线程永不返回时句柄留到进程退出，属低风险。
