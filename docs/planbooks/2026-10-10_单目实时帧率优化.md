# 单目实时帧率优化（2026-10-10）

> **要解决什么**：跳过标定直接跑实时检测，HUD 显示 **`FPS 1.1` / `detect 1527.9 ms`** ——
> 一秒一帧，完全不可用（球早就飞过去了）。
>
> **一句话**：先测出 1.5 秒花在谁身上，再决定动哪个。

---

## 1. 实测：慢的是 HoughCircles，而且只在真机画面上慢

用同一台相机的一帧真机画面，与项目自带的合成视频帧对比
（1920×1080，`method=fusion`，`fusion_members=[color, hough, motion]`）：

| 检测器 | 合成图 | **真机图** | 倍率 |
| ------ | ------ | ---------- | ---- |
| `color` | 18.3 ms | 9.3 ms | — |
| **`hough`** | 81.3 ms | **1751.6 ms** | **21×** |
| `motion` | 15.9 ms | 16.3 ms | — |
| `fusion` | 121.3 ms | **3372.4 ms** | **28×** |
| **整条 pipeline** | **135.0 ms** | **2675.4 ms** | **20×** |

**决定性的一条**：`hough` 在真机帧上花了 **1751 ms，最终只找到 1 个候选**。

**相机自运动估计不是瓶颈**：实测 1280×720 是 3.2 ms、1920×1080 是 2.0 ms。

### 为什么只在真机帧上慢

`cv2.HoughCircles` 的代价由**边缘密度**决定（Canny 边缘图 + 累加器投票）。
合成视频是干净的渐变背景，边缘很少；实验室画面有桌椅、窗帘、架子、地板反光 ——
1080p 下边缘数量相差几个量级，累加器随之爆炸。

**关键推论**：这不是"分辨率太高"这么简单，**光降分辨率治不彻底**。

### 分辨率这个杠杆（真机帧实测）

| 分辨率 | `hough` | `fusion` | 整条 pipeline |
| ------ | ------- | -------- | ------------- |
| 1920×1080 | 1706 ms | 1794 ms | **2020 ms** |
| 1280×720 | 814 ms | 595 ms | 533 ms |
| 960×540 | 216 ms | 236 ms | 215 ms |
| 640×360 | **64 ms** | 68 ms | **68 ms** |

**即使降到 640×360，`hough` 的 64 ms 仍是整帧的主要开销**（`color` 在 540p 约 4 ms）。
降分辨率有效（1080p → 640p 快 30 倍），但**它同时损失球心精度**，
而球心精度直接决定单目测深 —— 不能无脑降。

## 2. 做到什么算完成

| 项 | 验收标准 |
| -- | -------- |
| **F1 可用帧率** | 1920×1080 下整条 pipeline **≥ 15 fps**（即 ≤ 66 ms/帧）；或明确降到某个分辨率档后达标，并把该档写进文档 |
| **F2 不掉精度** | 与优化前相比，`tests/selftest_synthetic.py` 的球心/半径指标**不得退化**（排除 fps 列逐行比对） |
| **F3 可解释** | HUD 上能看出各阶段耗时占比，而不是只有一个总数 |
| **F4 可选择** | 保留一条"高精度慢速"通道给离线视频处理（精度优先时用） |

## 3. 候选措施（按"收益/风险"排序）

### P0 —— 直接治 Hough

| # | 做法 | 预期 | 代价 |
| - | ---- | ---- | ---- |
| **F0-1** | **Hough 只在降采样图上跑，再把圆映射回全分辨率**，然后在全分辨率上做**局部**亚像素细化 | 1080p 的 hough 从 1706 ms → 约 64 ms（按 640 宽算），**约 27×** | 圆精度靠后续细化找回来，需要验证 F2 |
| **F0-2** | **限制搜索区域（ROI）**：用上一帧的轨迹位置开一个窗口，只在窗口内跑 Hough | 与窗口面积成正比；球不会瞬移，窗口可以很小 | 丢失后要有"全图重捕"的兜底路径 |
| **F0-3** | **收紧 HoughCircles 参数**：`param2`（累加器阈值）调高、`minRadius/maxRadius` 收到球的真实尺寸范围 | 投票阶段的候选大幅减少 | 参数要对"球在不同距离"都成立，需要标定半径范围 |

### P1 —— 结构调整

| # | 做法 | 预期 |
| - | ---- | ---- |
| **F1-1** | **把 `hough` 从 `fusion_members` 默认里拿掉**，改成"color 与 motion 都没把握时"的**兜底**才跑 | 默认帧从 2020 ms → 约 25 ms（color+motion） |
| **F1-2** | **分级流水线**：每帧只跑便宜的线索；只在"可疑"时（分数低、跟踪丢失）才跑贵的 | 平均帧率大幅提升，峰值不变 |
| **F1-3** | **多线程/流水线并行**：检测与跟踪/绘制分开（`LatestFrameCamera` 已经是这个思路，检测侧还没有） | 受 Python GIL 限制，收益有限，先测再定 |

### P2 —— 框架

| # | 做法 |
| - | ---- |
| **F2-1** | HUD 加**分段耗时条**（F3）：`color 9 / hough 1706 / motion 16 / track 3 / draw 5` |
| **F2-2** | 加一个 `--bench` 开关：对当前相机跑 N 帧，输出各阶段耗时表（这次诊断是临时脚本做的，应该固化下来） |

---

## 4. 明确不做

| 不做 | 理由 |
| ---- | ---- |
| 不为了帧率**换掉融合策略**（改成单一 color） | 融合是抗误检的主力；应先治最贵的那个分量，而不是砍掉整条策略 |
| 不先降相机分辨率了事 | 球心精度直接决定单目测深，降分辨率是**用精度换帧率**，必须当成显式取舍而不是默认动作 |
| 不动 `sphere_tracker/track.py` 的卡尔曼参数 | 与耗时无关 |
| 不做 GPU/ONNX 加速 | 当前瓶颈是 CPU 上的 Hough 投票，不是模型推理 |

---

## 5. 执行顺序

```
F2-1/F2-2 分段耗时可见 ──> 用真机复测，确认瓶颈分布 ──┐
                                                      ↓
                              F0-1 Hough 降采样（收益最大、改动集中）
                                                      ↓
                                   跑 selftest_synthetic 验证 F2 不掉精度
                                                      ↓
                              F0-2 ROI 限制 ──> F0-3 参数收紧
                                                      ↓
                              F1-1/F1-2 结构调整（若还不够）
```

**F0-1 先做**：它是单点改动、收益最大（约 27×），而且不改变融合策略。
**F2 是硬门槛**：任何一步之后 `selftest_synthetic` 的精度指标不许退化。

---

## 6. 风险

| 风险 | 影响 | 对策 |
| ---- | ---- | ---- |
| 降采样后 Hough 漏检小/远的球 | 检出率下降 | `min/maxRadius` 按"最远距离下的球半径"定；F2 的合成场景含远距离案例 |
| ROI 策略导致丢失后找不回来 | 跟踪中断 | 必须保留周期性的全图重捕（例如丢失 N 帧后） |
| 收紧 `param2` 后真球被漏 | 检出率下降 | 用现有 `camera_quality.py` / 真机录像回归，而不是只看合成 |
| 优化后合成场景变绿但真机没变快 | 白忙 | **每一步都用真机帧复测**（这次的教训：合成图 135 ms vs 真机 2675 ms，差 20 倍） |

> ⚠️ **本次最值钱的教训**：合成视频测出 135 ms、真机 2675 ms。
> **性能问题绝不能用合成数据下结论** —— 与项目已有的
> "不要用合成真值漂亮推断真机可用"是同一条。
