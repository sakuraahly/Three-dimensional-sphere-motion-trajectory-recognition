# 架构接缝与缺失基础设施（2026-10-10）

> **一句话**：模块划分不用动（无环、分层清楚）。要改的是**四条接缝**——
> 时间层、标定身份层、证据层、失败闸门层——外加一层**支撑它们的工程与治理基础设施**。
>
> 本计划书**只给清单**：每条都要能落到"改哪个文件、怎么算做完、拿什么命令验"。
> 诊断已经做过（证据见 §2），这里不重复论证"为什么是问题"。

| | 内容 |

### 2.3 推断（**不是结论**，P0-4 的第 0 步就是去证伪/证实它）

> **推断 P**：真机那次 46 px 的成因是**左右两路混用了检测器**（一路 SB、一路经典 → 角点顺序整体反序）。
>
> - **支持**：混合检测器的签名（RMS 42.0 px）与真机（46.4 px）同量级；
>   `BoardObservation` **不记录**角点来自谁；
>   单目标定对顺序反序免疫，"单目正常、双目爆炸"正好是它的签名。
> - **⚠️ 反对（原稿漏了，由对抗性审查逼出来；现已用用户实测数据判到底）**：
>   **用户实测两镜头中心间距 = 65 mm（下 60 / 上 70）**，而真机标定算出 **199.67 mm = 3.07 倍**。
>   基线确实被吹飞了 → **方向支持推断 P**；
>   但**幅度不支持**：同样的错配在 65 mm 装置上应把基线吹到 **8–15 倍**（实测 8.2–14.6×），
>   真机只有 **3.07 倍**。→ **结论：基线异常是真的，但"纯混合检测器"单独解释不了它的量级。**
>   最可能的形态是"**部分对应错配**"或"**另有叠加因素**"（例如：板在两路之间并未真正静止 ——
>   日志里 58.3% 的拒收正是"棋盘还在移动"，而"板静止"是这两台**无硬件同步**相机
>   替代时间同步的唯一手段，交接文档.md §10.10(4) 已写明这条门限承担的职责）。
> - **未坐实的原因**：真机那次**没有留下逐帧"哪一路用了哪个检测器"**，也没有留图；
>   而且（见 §2.1）**采集链路上根本走不到经典回退分支** —— 所以"混用"这件事在真机上
>   是否可能发生，本身就要先查清楚（见 P0-2 的更正）。
> - **证伪判据（一次问清，零成本）**：
>   ① 问用户**两台相机的实际间距**是多少。若与 **199.67 mm** 相符 → 基线正常 →
>   推断 P 的"同签名"论据当场失效，**必须换假设**；若实际远小于 200 mm → 基线被吹飞 → 推断 P 得到加强。
>   ② 读现有 8 份日志（§2.1），确认拒收分布与检测器出身。
>   ③ 再不行才按 P0-4 抓会话。
> - **正确的姿态**：在 ① 得到答案之前，**不要把 P0-2 当成"已定位的修复"**，它当前是
>   "一个把静默失败变成显式失败的**基础设施**"（这一条无论推断 P 真假都值得做）。

## 5. 模块职能与确定性链路设计（全局 §十 / §十二 硬门禁）

### 5.1 新增职能与边界（先定死，再动手）

| 新增对象 | 职能（只做这些） | 输入 → 输出 | 依赖方向 |
| -------- | ---------------- | ----------- | -------- |
| `sphere_tracker/frames.py` | 定义 `Frame` / `StereoFrame` 数据结构与不变量（`t_capture` / `seq` / `dropped` / `skew_ms`） | 无副作用 | 最底层（只依赖标准库 + numpy），**不 import 本项目任何模块** |

**边界死守**：

- `sessions.py` 只读写会话目录，**不做检测、不做标定**；
- `check_standards.py` **只读**，不许改任何文件；
- **反向依赖禁令依旧**：`detectors`/`track` 不许 import `apps`；库层不许 import `tkinter`。

### 5.2 确定性链路（能脚本的不问模型）

| 环节 | 走什么 | 为什么 |
| ---- | ------ | ------ |
| 时间戳 / seq / dropped | **代码**（`cap.read()` 返回值处直接取） | 可确定表达，不许"估计" |
| 角点顺序校验 | **代码**（枚举自同构 + RMS） | 有限枚举，确定性算法 |
| 顺序守卫 | **代码**（赢家/亚军分离度） | 数值判据，不靠人看 |
| 会话读写 / 清单校验 | **代码** | 结构固定 |
| 测试分档 / JSON 结果 | **脚本**（`启动程序.bat test`） | 可复跑、可机器读 |
| 派生事实生成 | **脚本**（生成器 + `--check`） | 抄一遍就会漂移 |
| 规范落差检查 | **脚本**（`check_standards.py`） | "不靠人记得比对" |
| 真机异常归因（如 46 px 的最终定性） | **模型**（人为判断）+ **脚本**（取证） | **为什么必须**：真实画面的异常是开放集，无法预先枚举；**边界**：模型只做"从证据挑假设"，不许改判据；**兜底**：所有结论必须落到 §2 那种可复现产物上，否则标「推断」 |

**新增抽象必须回答"减少了什么重复"**（全局 §六）：
`frames.py` 减少的是"每个帧源各自发明时间语义"（库层 **9 处 `read()` 签名**各写各的，见 P0-1）；

1. **`cv2.setRNGSeed()` 管不住 `cv2.stereoCalibrate` 内部的 RANSAC** —— 同一份输入，
   基线估计在 2000~13000 mm 之间跳。所以那几节的断言**刻意只钉数量级**
   （> 5 倍、> 10 倍、> 30°）——**这是设计，不是疏漏**（已写进测试文档串）。
2. **白名单不能用行号做键** —— 第一版用 `<文档>:<行号>:<原文>`，结果一改
   `交接文档.md` 的行数，15 条白名单里 4 条失配、测试误报。已改为
   `<文档>:<原文>`（行号只进值里做定位）。**这一条是 `selftest_doc_facts` 自己抓出来的。**

### 9.4 P0-2a 执行明细：角点出身（2026-10-10）

**产物**：

| 文件 | 改动 |
| ---- | ---- |
| `calib/board.py` | `BoardObservation.detector`（`""` / `"sb"` / `"classic"`）；`_finish()` 增加必填的 `detector` 参数；`detect_board()` / `detect_board_in_roi()` 增加 `allow_classic_fallback=False` |
| `calib/capture.py` | 收帧路径**显式**打开回退；两道"两路出身必须一致"守卫（粗检后、精确复核后） |
| `tests/selftest_calib_provenance.py` | 5 节：出身可辨识 / 回退显式 / ROI 透传出身 / 混用被拒（用替身真造出来）/ 守卫不误伤 |

**两处与计划原文不同的判断（都有实测依据）**

1. **回退在采集路径里是"显式打开"的，不是关掉。**
   计划原文只要求"把隐式闸门变成显式参数"。做的时候实测了一遍
   （一次性对照，脚本已删、结论留此）：高斯模糊 k=15 时
   **SB 失败、经典成功**；而真机上"左路偏糊"正是已知现象。
   所以"默认不回退"虽然更安全，**会真的少收帧**。
   → 采取的策略是"**允许回退，但绝不允许一对之内混用**"：
   回退在 `capture.py` 里显式打开，两道守卫当场拦混用。
   这样既保住覆盖率，又不会静默产出垃圾标定。

2. **出身以"精确复核这一次"为准，不照抄 hint 的来源。**
   粗检在 640 宽上跑、精确复核在全分辨率裁剪上跑，两者成败**可以不同**
   —— 所以两道守卫都要有，只留一道会漏。这一点也已用替身分别验证。

**验证（命令 + 退出码）**：

```

受影响的既有测试：stereo_calib(237.1s) / stereo_pipeline / stereo_branch / camera_quality 全 exit=0
全套 15 个：exit 全 0，合计 396.6 s（产物 outputs\_full_suite_15.txt）
```

**反向自证（4 个变异，全部报红）**：

| # | 注入 | 结果 |
| - | ---- | ---- |
| M1 | `_finish` 里 `obs.detector = "sb"`（出身永远记 sb） | exit=1（3 条） |
| M2 | 回退恢复成隐式（去掉 `allow_classic_fallback` 闸门） | exit=1 |
| M3 | 去掉粗检那道出身守卫 | exit=1（4 条） |
| M4 | 去掉精确复核那道守卫 | exit=1（4 条） |

**又一处"测试自己有 bug"（如实记录）**

第 4 节第一版用 `want_detectors[i % 2]` 取每次调用该返回哪个检测器 ——
只要调用次数超过 2 次，取模就错位，于是"**粗检一致、精确复核才混用**"
这个场景**根本没被造出来**，测试却报"通过"。
是**它自己的断言**抓出来的：加了"替身必须被调用 ≥4 次，否则这个场景没被构造"
这一条之后，该场景立刻报红并暴露出取模 bug。已改成按调用序号取值。

→ 这条值得记下来：**"测试通过"里最危险的一种，是它其实没测到东西。**
凡是用替身构造场景的测试，都应该断言"替身确实被调用到了那一步"。

### 9.5 P0-6 执行明细：把重复劳动固化成脚本（2026-10-10，用户指定）

用户原话：**"重复的能用脚本和程序的工作统统固化程序和脚本"**。

| -- | -------------- | -------- |

**A. `apps/run_tests.py`** —— 项目里**唯一**跑全套测试的地方

- `fast` / `full` 两档；每个测试**独立子进程**跑，一个崩了不带走其余。
- **分层不写死名单**：读 `outputs/test_results/timings.json` 里的**实测中位数**
  （保留最近 5 次）。第一次跑会自动跑全套并建起基准。
- 判定口径与 `AGENTS.md` §7 一致：输出含 `判定结果：全部通过` **且** 退出码 0。
  实测验证过：一个测试**打印了"全部通过"却非零退出**，运行器仍判 FAIL。
- 结果写 `outputs/test_results/<时间戳>.json`（`name/status/seconds/exit_code`）。
- 实测：`fast` **13 个 / 62.7 s**；`full` **16 个 / 约 7 分钟**。

**两处设计决定（都是被实测逼出来的）**

1. **阈值从 30 s 提到 60 s + 显式保底名单。**
   实测 `selftest_pair_source` 耗时 **1.5 / 8.6 / 37.6 / 39.7 / 50.1 s** ——
   方差极大（要写临时视频素材）。30 s 阈值下它一慢就被踢出 fast 档，
   而它守的正是"同步偏移符号搞反"这类**静默错误**。
   现在阈值 60 s，另有 `MUST_RUN` 保底名单；`pair_source` 稳定在档内。
   → 取舍写在代码注释里：**"自动分层"与"必须跑"是两件事**，
   把"跑不跑"完全交给一个会漂的数字，迟早会悄悄漏跑。
2. **取中位数，不取最后一次。**

**B. `apps/tools/sync_facts.py`** —— 计数的权威实现

- 检查测试数量（**15 处**说法）、`AGENTS.md` §3 的分组清单与计数、§7 的测试登记。
