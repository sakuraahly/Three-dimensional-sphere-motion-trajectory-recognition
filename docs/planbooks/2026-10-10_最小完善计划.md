# 最小完善计划（2026-10-10）

> **目标：让"跑到真机标定成功"这条路不再有静默失败。**
>
> 不是把项目做完整 —— 是**把当前唯一卡住的那条路修通，并且让下一次卡住时你能自己看出卡在哪**。

---

## 1. 要解决什么

**一句话**：现在标定跑不通，而且**失败原因是不可见的**。

具体三个现象（都由用户实测报告）：

| # | 现象 | 性质 |
| - | ---- | ---- |
| A | 收了 8 对之后**再也不收**，也看不出为什么 | 静默失败 —— 最贵的一种 |
| B | 逐路状态标记画在面板右上角，**压在右相机画面上** | 布局 |
| C | 拒绝原因画在面板底部，**被窗口下沿截断** | 布局（这才是看不到真因的原因） |

**注意 A 与 C 的关系**：C 是 A 的**放大镜缺失**。程序其实统计了拒绝原因，
但排在后面的原因看不到，而"收满 N 对后不再收"的那条门槛恰好不在前三条里。
所以**先修 C，A 才可能被诊断** —— 这也是本计划的排序依据。

### 已经确定的（不需要再查）

- **板静止的门限已经修好**：`calib/board.py` 的归一化写错，导致 `pose_distance`
  量的是数值噪声（板静止却报 14~86 px，门限 3 px）。已修，实测降到 0.02~0.44 px。
  → **你截图里的 419 次"棋盘还在移动"就是这个**，不是策略苛刻。
- **检测没有自己造轮子**：已经在用 `findChessboardCornersSB`（抗模糊那版）
  → 经典版兜底 → `cornerSubPix`；单应、标定、校正全是 OpenCV 的。
- **`--left-dir/--right-dir` 批量模式已存在**，且自动跳过"静止"门限。

## 4. 日志系统：现状与最小设计

### 现状（实测）

| 项 | 结果 |
| -- | ---- |
| `logging` 模块 | **0 处使用** |
| 输出方式 | 全项目 **629 处 `print`** |
| 日志文件 | **无** |
| 级别 / 时间戳 / 落盘 | **都没有** |

**问题不在"没上框架"，在两个具体的后果**：

1. **库代码里也在 print**（`sphere_tracker/`、`stereo/` 共 24 处）——
   库不该直接往终端写，调用方无法接管。
2. **最有价值的数据没落盘**：标定的拒绝原因分布、相机协商结果、
   每帧判定 —— 全是瞬时输出，**失败了就什么都没留下**。

### 最小设计（**刻意不上第三方框架**）

项目规矩：能脚本化/代码化的不引入依赖。`logging` 是标准库，够用。

```
outputs/logs/                         ← 新增，已被 .gitignore 的 outputs/ 覆盖
├── calibrate_20261010_153012.log     每次标定一份
├── run_20261010_160000.log           每次实时跑一份（P1 再说）
└── ...
```

**约定**：

| 项 | 定 |
| -- | -- |
| 格式 | `HH:MM:SS.mmm LEVEL  消息`（单行，便于 `Select-String`） |
| 级别 | 只用三级：`INFO`（每帧判定）/ `WARN`（门槛拒绝）/ `ERROR`（致命） |
| 落盘 | **只在 app 层**（`apps/`）配置；**库层不配、不 print** |
| 终端 | 同时输出（人看终端，机器看文件） |
| 库层改造 | **只改最值钱的几处**：`calib/capture.py` 的 `_reject`、`stereo/pair_source.py` 的后端/索引解析。**不做全项目 print→logging 重构**（629 处，收益远小于风险） |

> **为什么不全改**：`print` 在 app 与工具里是**面向人的输出**，不是日志，
> 改掉它们既没收益又要重跑所有测试。**只把"失败后想回看"的那几处变成日志。**

## 5. 明确不做

| 不做 | 理由 |
| ---- | ---- |
| 不引入 `loguru`/`structlog` 等第三方日志库 | 标准库够用；多一个依赖就多一条"新机器要装什么" |
| 不全项目 `print` → `logging` 重构 | 629 处，风险大收益小 |
| **不凭猜调 `diversity_min` / `max_per_region`** | 还不知道是不是它们卡的。**先加日志拿数据** |
| 不改模块划分、不动依赖方向 | `AGENTS.md` §9 已明确 |
| 不动 `pipeline.render()` 的 scale 语义 | 它需要先定"scale 是什么意思"，是设计决策不是修 bug |
| 不把 `docs/` 再分目录 | 除用户明确要求的 `planbooks/`（新目录，不打断既有引用） |

### 顺带修掉的一个真 bug

`self.rejected` 原来用**完整原因字符串**当 key，而原因里嵌着每帧不同的数字
（`左图模糊(清晰度 42)` / `(清晰度 51)` 是两个不同的 key）——
**统计被打散成几百个只出现一次的条目**，"最常见原因"因此没有意义。
新增 `reject_category()` 归一化：`左图模糊(清晰度 42)` 与 `(清晰度 51)` 归为 `左图模糊`；
完整原因另存 `reject_examples`，聚合与细节都不丢。
