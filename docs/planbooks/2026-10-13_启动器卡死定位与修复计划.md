# 启动程序.bat 各选项"卡死" · 根因定位与修复计划（待批准）

> 用户报告：运行 `启动程序.bat` 后**大部分选项都会卡死**。
> 本文是**定位结果 + 修复计划**，按"先定位再定计划"的要求分两部分。
> **尚未动手改代码**——计划待确认。

---

## 一、定位：不是一件事，是**四个独立原因**叠加

实测方法：逐个模式起进程、超时 40 s、输出写文件（**不能用管道**，见 §四）、
stdin 给 NUL 模拟"没有键盘输入"。逐模式结果：

| 模式 | 实测 | 耗时 | 停在 |
| ---- | ---- | ---- | ---- |
| `check` | 正常完成 | 1.9 s | `Press any key to continue` |
| `standards` | 正常完成 | 5.1 s | 同上 |
| `precheck` | 正常完成（exit=1，需参数） | 16.5 s | 同上 |
| `verify` | 正常完成（exit=1，无标定文件） | 2.4 s | 同上 |
| **`diag`** | 完成但**极慢** | **64.2 s** | 命令行输出，无交互 |
| **`setup`** | **真卡死** | >125 s 被杀 | 无限循环 + 无输出 |
| **`run`** | 卡死（等按键） | >40 s | 图像窗口 |
| **`calibrate`** | 卡死（等棋盘） | >40 s | 采集循环 |
| **`test`** | 卡死（跑全套） | >40 s | `selftest_pair_source` |

### 原因 1（最关键）：**相机打开极慢，而这段等待没有任何反馈**

实测同一台机器、两个同型号 `aoni webcam A25`：

```
#0: 开成功，30 帧里 ok=30 失败=0   ( 1.8s)
#1: 开成功，30 帧里 ok=30 失败=0   (22.9s)   ← 慢 12 倍
```

`#1` 光**打开并读到 30 帧**就要 **22.9 秒**。

而这段等待期**一行输出都没有** —— `CameraSource` 会按
"后端 × 分辨率 × 最多 12 次读帧"逐个试（`sphere_tracker/sources.py:391`），
每次都可能在等驱动超时。用户看到的就是**一个不动的窗口**。

**这是"卡死"最主要的来源。** `setup` / `run` / `calibrate` / `diag` 全都要先开相机，
所以它们**全都中招**。

### 原因 2：`cameras.py identify`（即 `setup`）在相机读不到帧时**无限空转**

125 s 的实测输出里只有这一种行在重复：

```
[ WARN] CvCapture_MSMF::grabFrame videoio(MSMF): can't grab frame. Error: -2147483638
```

而 `apps/tools/cameras.py:151-170` 的循环是：

```python
while True:
    ok, frame, _t = src.read()
    if ok and frame is not None:
        ...imshow...          # ← 读不到帧时**这整块被跳过**
    key = cv2.waitKey(1) & 0xFF
    if key == ord("q"): return ""
```

读不到帧时：**不 imshow（窗口黑/冻）、不打印任何东西、不计数、不超时、不退出**。
`waitKey(1)` 又只在**窗口有焦点**时收到键 ——
用户看着黑窗口按键，而焦点在控制台，于是**按什么都没反应**。

**根因：这条循环没有"失败路径"，只有"成功路径"。**

### 原因 3：`.bat` 结尾的 `pause` 长得像卡死

`check` / `standards` / `precheck` / `verify` 实测**都正常完成、exit 0**，
最后一行是 `Press any key to continue . . .`。

用户双击运行 → 程序做完 → 停在"按任意键" → **看起来就是卡死**。
而且这几个模式的输出会**滚上去**，最后一屏只剩这句话。

### 原因 4：`test` 默认就是"几分钟没输出"

`test` 走 `apps/run_tests.py`，`fast` 档里 `selftest_pair_source` 中位 **36~42 s**，
`stereo_branch` 再 15~20 s。40 s 超时必然"卡死"。
它**不是缺陷**，但用户看到的是同一个现象。

### 附带发现（不是卡死，但要看）

- **`diag` 的单开测量不可信**：`#1 单开 0.4 fps -> 同开 28.5 fps`。
  `0.4 fps` 显然是把**打开阶段的 22.9 s** 算进了帧率里。
  即"实测帧率"的分母包含了打开耗时 → **慢相机被误判成"带宽不足/占用"**，
  而真实原因是"打开慢"。这会把人引到错误方向。
- **相机的 `-2147483638`（`MF_E_VIDEO_RECORDING_DEVICE_INVALIDATED`）**：
  "设备失效"，通常是**被别的进程占用**。我做探测时并发跑过多个 python，
  互相抢相机就会出这个。**排除方法：确认没有别的程序（含本项目的另一个实例）占着相机。**

## 二、修复计划（按"收益 ÷ 风险"排序，**待批准**）

### P0：让"等待"变得可见（直接消灭最主要的"卡死"观感）

| # | 改什么 | 怎么改 | 验收 |
| - | ------ | ------ | ---- |
| 0.1 | `CameraSource` 打开过程打印进度 | 每试一个后端/分辨率打一行（`试 MSMF 1920x1080 …`），带耗时 | 慢相机打开时能看到 22.9 s 花在哪一步 |
| 0.2 | 打开阶段加"心跳" | 每 2 s 打一行 `仍在尝试…已 6s`，避免长静默 | 无 3 s 以上的无输出间隔 |
| 0.3 | 打开超时可配 + 有上限 | 总尝试时间上限（如 30 s），超了给出**明确结论**与下一步 | 不会无限等；结论里含"换 USB 口 / 关掉占用程序" |

### P0：`setup`（`cameras.py identify`）补失败路径

| # | 改什么 | 怎么改 |
| - | ------ | ------ |
| 0.4 | 读不到帧要**计数 + 报出来** | 连续 N 次（如 30）读失败 → 打印原因 + 提示 + 返回失败，而不是继续空转 |
| 0.5 | 窗口无焦点时也要能操作 | 在控制台也接受输入：`waitKey` 之外同时给出"在控制台按 l/r/n/m/s/q 回车"的 `input()` 分支，并明确提示**窗口需要点一下才有焦点** |
| 0.6 | 每次进入某台相机时**清屏式**打印一行醒目提示 | 避免提示被上面的 OpenCV WARN 淹没 |

## 三、我建议的执行顺序与理由

1. **P0.1~0.3（打开过程可见）** —— 一处改动同时治好 `setup`/`run`/`calibrate`/`diag`
   四个模式的"卡死"观感，**性价比最高**。
2. **P0.4~0.6（`setup` 失败路径）** —— 它是最容易真卡死的一个（无限空转）。
3. **P1.4~1.5（`diag` 口径）** —— 不修的话，`#1` 那台会被永久误判成"带宽不足"，
   而它其实只是**打开慢**。这条会直接影响你选相机/换 USB 口的判断。
4. **P1.1~1.3、P2.x** —— 观感与文档，最后做。

**验证方式**：每一批改完，
- 跑 `启动程序.bat check`（.bat 改动的硬要求）；
- 跑 `apps\run_tests.py fast`（19 个测试里必须仍全绿）；
- **用计时的探针重跑一遍本节的模式表**，对照"卡死 → 正常/有反馈"。

**我不会在没批准前动手改。** 另外 `calib/` 与 `stereo/` 是标定主路径，
P0.1~0.3 会碰 `sphere_tracker/sources.py`（库层），**动它必须跑全套测试**。

## 四、一条方法论记录（我自己的坑）

第一版探针用 `subprocess.run(..., capture_output=True)`，
结果 **9 个模式全部"0.1 s / exit=1 / 无输出"**，看起来像"`.bat` 全坏了"。

**那是测量方式的假象**：cmd 的输出被重定向到管道后行为不同。
改成**写文件再读**，才拿到真实结果（`check` 其实 1.9 s 正常完成）。

→ 教训同本轮其它几条：**"零/无"这类结论，先用第二种方法复核**；
而且**测量工具本身要先被证明有效**，否则会拿着假数据去定位。
