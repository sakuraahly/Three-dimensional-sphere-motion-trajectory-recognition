## 1. 要解决什么（先定性，再动手）

「双目标定异常」有四种完全不同的病，说法与下一步截然不同，**必须先分开**：

| 病                                       | 症状                                                                           | 今天是否命中                                                                       |
| ---------------------------------------- | ------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------- |
| A 配置撞车（左右同台）                   | 开相机**之前**就报「左右解析到同一台相机」                                     | 否 —— `config/cameras.json` 现已 left/right 端口不同（`6&31324e2c` / `6&4489382`） |
| B 取帧失败（相机拿不到成对帧）           | 日志 `取帧源装配失败` / `启动阶段取不到成对帧，退出（camera）`，**没走到算法** | **是（命中两次）**                                                                 |
| C 标定算法拒收（角点 / 姿态覆盖 / 门限） | 走到了"收图"甚至"求解"，报对数不足 / RMS 超限 / 板太小                         | 否                                                                                 |
| D 精度不达标（RMS / 极线偏大）           | 求解成功但判定"勉强可用"或"不可用"                                             | 否                                                                                 |

**结论：本轮命中的是 B（取帧），不是算法。** 修算法一行都不该动。

## 3. 范式审计（AGENTS §11.7 强制，Leader 亲自做）

被审计的方案 = 现状：**"标定/录制默认请求 2560x1440，失败就按固定梯子降档"**。
逐条列隐含前提，并判它在**今天的条件下**是否成立：

| #   | 隐含前提                                                               | 今天是否成立                                                                                   | 不成立时换成什么                                                                          |
| --- | ---------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| P1  | 两台外接相机**恒给 2560x1440**（请求被无视），所以默认请求 1440 最省事 | **不成立** —— 今天 1920x1080 请求得到 1920x1080 实际值                                         | 默认档必须来自**相机实际能力**，而不是一条 2026-10-24 的观测；至少不能把"请求 1440"当无害 |
| P2  | 降档梯子 `[(申请),(720p),(480p),(原生)]` 覆盖了所有**可能可用**的档    | **不成立** —— 本机唯一稳定的 1920x1080 不在梯子里                                              | 梯子必须**包含 1080**，且其成员不能凭手写；应由 `video_profiles` 生成（同一份档位表）     |

| P6  | `video_profiles` 是分辨率档位的**唯一来源**                            | **不成立** —— `sources.py:397` 另有一份硬编码梯子，与其不一致                                  | 梯子改为从 `video_profiles` 取值（这正是该模块存在的理由）                                |
| P7  | 标定失败 = 标定算法问题                                                | **不成立（本轮）** —— 失败在取帧，算法未执行                                                   | 报错必须把「取帧失败」与「算法拒收」分开；本轮只修前者                                    |

**结论（实验后有修正）**：

- **P1 已被实验否证**：本机 aoni **不支持 2560x1440**，请求它被静默降级为 1920x1080。
  所以 `video_profiles.DEFAULT = 2560x1440` 是**名义档、不是实际采集档**；
  那条"真机恒给 1440"的依据（2026-10-24 复测）与今天的事实**相反**。
  → 该默认值与 `selftest_launcher_params.py` 里"1080 请求必失败"的判据**都需要重新裁决**，
  但这**不是**本轮标定失败的原因（见 §4）。
- **P2 / P3 / P6 仍成立**（梯子不含 1080、一步跳到 480、与 `video_profiles` 两份来源）——
  它们是**真实缺陷**，但属"本机已经打不开的相机救不回来"之外的第二层问题：
  它们让诊断信息更差，不该被当作本轮故障的根因。
- **P4 已定论（否证）**：对照 C（全新进程只开 `#1`）**照样失败** →
  "同型号两台**同时**打开导致协商失败"**不成立**；失败方是**右机本身**，
  与并发无关。带宽预算**不是**本轮故障原因。
- **P5 未验证**（原生档 `(0,0)` 语义）。
- **P7 成立**：本轮确实死在校验期（取帧），算法未执行。

**因此本轮的性质变了**：不是"修分辨率档就能好"，而是
**先把"右机间歇性失效"这条真因定死（对照 C/D/E）**，
再修"诊断与梯子"这两条放大了故障、误导了排查的缺陷。

## 4. 决定性实验（已跑，**主假设被推翻**）

**目的**：把"分辨率请求"与"设备 / 并发"分开。

| 组     | 请求                 | 做法                     | 结果                                                                    |
| ------ | -------------------- | ------------------------ | ----------------------------------------------------------------------- |
| A 基线 | 两台都 **1920x1080** | 两台同时打开，各读 30 帧 | `#0` **30/30**（实际 1920x1080）；`#1` **构造即失败**                   |
| B 可疑 | 两台都 **2560x1440** | 同上                     | `#0` **30/30**（实际仍 1920x1080，**被静默降级**）；`#1` **构造即失败** |

**判读（据数据）**：

- **分辨率不是决定因素。** 右机在两种请求下表现**逐字相同**：同一错误码
  `-2147483638`、同样"12 次 read 全空（含 640x480 档）"、耗时 61.3 s vs 61.4 s。
  → **"请求 2560x1440 导致右机拿不到帧"这一假设不成立，作废。**
- **aoni 不支持 2560x1440**：左机请求它被 MSMF **静默降级为 1920x1080**。
  → `video_profiles.DEFAULT = 2560x1440` 在本机**永远拿不到 1440**；它是"名义档"。
- **右机 `#1` 当前处于设备失效态**（`MF_E_VIDEO_RECORDING_DEVICE_INVALIDATED`），
  而**同日 21:35:07 的 `identify` 里它是好的**（MSMF@1920x1080，5.0 s 出图）。
  → 右机是**间歇性**失效，不是恒定坏。

**该实验未能分开的混淆（Verifier 主动指出，值钱）**：
设计里 `#1` 永远是"在 `#0` 已打开之后打开的第二台同型号 MSMF 相机"，因此数据**同时兼容**两说：
(a) 右机设备链路已失效；(b) 同进程内第二台同型号 MSMF 相机不被接受。
→ 已派**对照 C/D/E**：C 单独打开 `#1`；D 换打开顺序（`#1` 先）；E 打开→释放→重开 3 轮（判粘性）。

### 4.1 对照 C/D/E（已跑，**混淆排除**）

| 组     | 做法                                                 | 结果                                                                   | 排除了什么                                           |
| ------ | ---------------------------------------------------- | ---------------------------------------------------------------------- | ---------------------------------------------------- |
| C 单独 | **全新进程**里只打开 `#1`，请求 1920x1080 与 640x480 | 两次运行**都失败**：`-2147483638`，两个档都读不到帧（61.5 s / 61.6 s） | **(b) 被排除**：没有第二台相机在竞争，右机照样不给帧 |
| D 换序 | **先开 `#1`** 再开 `#0`                              | 失败方**恒为右机**；**后开的左机 30/30 帧全好**                        | **(a) 坐实**，且与打开顺序无关                       |
| E 粘性 | `#1` 开 → release → sleep 3 s → 重开，共 3 轮        | **3 轮全废**（1 轮 open 成功但 0/5 帧，2 轮连 open 都失败）            | 软件层"重开/释放"**救不回来**                        |

**真因（定死）**：右机 `#1`（`aoni webcam A25 right`，端口 `6&4489382&0&0000`）
当前处于**设备级失效态**（`MF_E_VIDEO_RECORDING_DEVICE_INVALIDATED`）。
它与分辨率、与打开顺序、与"是否第二台"**都无关**，且**软件重开无效**。

→ **用户唯一必须做的一步：物理拔插右机**（仍不行就换一个**直接插在机身上**的 USB 口，
别经 HUB / 扩展坞）。这一步**不能被任何软件替代**。

> 补充：右机并非恒定坏 —— 同日 **21:35:07** 的 `identify` 里它是好的
> （MSMF@1920x1080，5.0 s 出图）。所以这是**间歇性**设备失效，
> 拔插后可能立刻就恢复；恢复后再复跑标定即可。

**旁证（静态可证，不需开相机）**：21:35:07 的 `identify` 对每台相机是
**开一台、用完就在 `finally` 里 `release()`**（`apps/tools/cameras.py:630-631`），
**同一时刻只有一台开着** —— 所以那次「两台都好」是**逐台串行**测的，
跟双目要求的"两台**同时**打开"**不是同一个条件**。

> 🔴 **由此暴露一条真实缺陷（本轮要记）**：`identify` 报「两台都 ✔」与双目报
> 「取不到成对帧」**可以同时成立**，用户看到就是"程序自相矛盾"。
> 排查工具测的工况必须与它要支撑的工况一致 —— 否则它给的是**假的安心**。

> ⚠️ 教训（与本项目既有的"弱证据撑强结论"同型）：我最初的判断
> "请求 1440 → 右机拿不到帧"看起来有日志支持（两次标定都死在 1440 上），
> 但**对照实验一跑就否掉了**。**同一份日志有两种解释时，必须做能分开它们的实验**，
> 不能挑那个"解释得通"的。

## 6. 明确不做（范围护栏）

- **不改左右角色/身份绑定**（`config/cameras.json` 的 identity/port）——已知会静默错位。

## 8. 第二个主题：分辨率请求改为「自适应」（用户裁定）

用户原话：「**为什么不能改成自适应选择清晰度呢?不能被限制死了**」
——我给的三条"写死默认档"的选项**全部被否**。要求：按相机实际能力自适应，
不许被一个固定值限制住。

### 8.1 现状：一件"档位"的事被写在四处（P2 / P6 的量化）

| #   | 位置                               | 内容                                     | 问题                                             |
| --- | ---------------------------------- | ---------------------------------------- | ------------------------------------------------ |
| 1   | `sphere_tracker/video_profiles.py` | `PROFILES` 6 档；`DEFAULT = 2560x1440`   | **名义**默认，本机恒拿不到 1440（实测降级 1080） |
| 2   | `sphere_tracker/sources.py:397`    | `[(请求), (1280,720), (640,480), (0,0)]` | **不含 1920x1080**；一帧没有就跳到 480           |
| 3   | `sphere_tracker/sources.py:196`    | `CANDIDATE_MODES` 6 档                   | **第三份**手写清单（只服务 `optimize_mode`）     |
| 4   | `sphere_tracker/sources.py:206`    | `LOWRES_RETRY_MODE = (640,480)`          | 补试的那一档恰是本机**已知无效**档               |

### 8.2 两条不能违反的硬约束（既有决策）

1. **成对一致**：双目两路必须同档。`stereo/pair_source.py:323-338` 已记录
   `optimize=False` **是必须的** —— `optimize_mode` 是**逐台**优化，会把两路拉开，
   标定直接失败。所以"自适应"**不能**做成"每台各选最舒服的档"。
2. **不自动换后端**（2026-10-14 撤回，同进程混用 DSHOW+MSMF 会亲手制造坏状态）。

### 8.3 方案（Leader 定稿的接口契约）

**S1 单一来源**：`video_profiles` 新增

```python
NATIVE = (0, 0)                       # 原生档哨兵

def probe_order(start: VideoProfile | None = None) -> list[tuple[int, int]]:
    """自适应候选档，**按像素降序**，末尾是原生档 NATIVE。

    start=None  → 不设上限，从 PROFILES 最高档开始（"不被限制死"）；
    start=某档  → 从该档开始往下（显式档不越级往上，保持可控）。
    """
```

要实现的效果（**判据**）：

- `probe_order(None)` == `[(3840,2160),(2560,1440),(1920,1080),(1280,720),(960,540),(640,480),(0,0)]`
- `probe_order(parse("1920x1080"))` == `[(1920,1080),(1280,720),(960,540),(640,480),(0,0)]`
- **含 1920x1080**（P2 的修复点）。

**S2 请求默认改为 auto**：`apps/_common.add_stereo_source_args` 的
`--width/--height` 默认由 `video_profiles.DEFAULT` 改为 **`0`**；help 写明
`0 = 自适应（逐档探测，清晰度优先 + 帧率下限）`。显式给数则**跳过协商**，行为与今天一致。
（GUI 侧 `_gui_stereo.calibrate_args/record_args` 本就**不传**这两个参数，故无需改 GUI 即可生效。）

**S3 `CameraSource` 吃 auto**：`width<=0 or height<=0` 时
`res_candidates = video_profiles.probe_order(None)`；否则 `probe_order(get(width,height))`。
`CANDIDATE_MODES` 改为 `tuple(p for p in probe_order(None) if p != NATIVE)`（原生语义未验证，不进模式搜索）。
**不加帧率逻辑** —— 帧率属于成对协商（S4），单目仍走既有 `optimize_mode`。

**S4 成对协商（`stereo/pair_source.py` 的 `CameraPairReader`）**：auto 时
1. 按 `probe_order(None)` 逐档，用**同一后端**同时开两路；
2. 两路都出非黑帧 → 比对**两路实际分辨率**，不等则降档；
3. 相等 → 短测**成对帧率**（~0.3 s，且沿用 `optimize_mode` 里
   "测到 <0.1 fps 先等首帧再测"的既有做法）；≥ 下限（`DEFAULT_FPS*0.6 ≈ 14`）→ **定案**；
4. 全部档都不行 → 报错，**逐档**列出 `(左实际, 右实际, 成对帧率)`，
   让"右机全档无帧"一眼可见；
5. 定案写日志 + 标定 meta（`requested="auto"`, `resolved="WxH"`, `actual_left/right`）。

**S5 诊断修正**：`apps/tools/cameras.py` 的 `doctor` / `identify` 增加一段
**"两台同时取帧"**（与双目同工况）；`calibrate_stereo` 取帧失败时的
"请先跑 cameras.py doctor" 指引**删掉**（doctor 逐台串行会说"两台都好"→ 死循环）。
本轮已实测到这个死循环（§4）。

**S6 成本控制**：**不做探测缓存**（第一版）。正常相机从顶档往下"第一个能出帧的档就停"，
只开 1–2 次，代价与今天相当；坏相机吃满既有总预算后如实报错。
缓存留作后续待办（避免本轮把范围撑大）。
