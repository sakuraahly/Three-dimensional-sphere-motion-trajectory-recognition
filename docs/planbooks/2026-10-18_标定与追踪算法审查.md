## 0. 为什么要做这一轮

用户要求"详细审查张正友标定法有没有问题，还有后续的小球实时追踪算法"。
在此之前的一周里，项目反复在**同一个根因**上翻车：**用弱证据支撑强结论**
（`s²` 被合成场景盖住、枚举顺序被外推、标签被当事实）。所以这一轮的方法论是：

1. **先列清单**（本文档）——每项写清"查什么 / 怎么判 / 证据形态"；
2. **逐项取证**，能合成真值的就用真值（真值已知才谈得上对错）；
3. **区分"精度问题"与"可信度问题"** —— 后者更危险（假警报会让人忽略真警报）；
4. 发现的问题按严重度分级，**先记录、后修**，修之前要能写出失败判据。

### 2.1 A2/A3：`T` 的符号语义 —— **已用合成真值定案**

**方法**：造一个真值已知的双目（右相机在左相机 **+X**，即物理右侧，B=65mm，
R=I，无畸变），用项目自己的 `calibrate_stereo()` 反解。

**结果**（`outputs/_handoff_read/audit_T_sign.py`）：

```
真值：右相机在 +X（物理右侧），平均视差 x_left-x_right = +125.368 px  -> 符号 +
解出：rms=0.0000px  极线=0.0000px  对=14/14  判定=优秀
解出 T = [-6.50000040e-02 ...]              ← 负
baseline_side()  = 'left'                    ← 说是"右相机在左边"
disparity_sign() = +1                        ← 但这是对的
真值视差符号     = +1
describe(): [警告] T[0] < 0：标定时 --left/--right 可能接反了
```

**定案**：OpenCV 的约定是 `X_right = R·X_left + T`，所以
**右相机在物理右侧 ⟹ `T[0] < 0`**。
即 `baseline_side()` 的语义**写反了**。

**后果分级**：

| 影响面 | 结论 |
| ------ | ---- |
| 三角测量精度 | **无影响**（P1/P2 自洽） |
| `disparity_sign()` | **数值正确**（两次反号抵消），但注释里的推理是错的 |
| `StereoRig.describe()` | **每台正常装置都会打印"[警告] 可能接反了"** —— 假警报 |
| 用户 | 假警报会训练用户忽略真警报；而"真接反"时反而看起来"正常" |

**本次真机标定**：`T[0] = -0.0678663` → **属正常**，不是接反。
所以 `verify_stereo.py` 会给这台机器报假警报。

### 2.4 A5：板太小 → **RMS 完全看不出来，但深度精度差 4 倍**
**这是本轮最重要的一条。** 合成真值 + 真实量级亚像素噪声（0.30 px，8 次试验）：

| 姿态 | 板占画面 | **RMS** | cx 误差 σ | fx 误差 σ | **Z 误差 σ** | Z 误差最大 |
| ---- | -------- | ------- | --------- | --------- | ------------ | ---------- |
| 只在中央小块 | **1.9%** | **0.414 px** | 3.44 px | **8.87 px** | **5.76 mm** | **13.69 mm（2.28%）** |
| 铺满画面 | 7.9% | **0.413 px** | 2.08 px | 3.52 px | **1.40 mm** | 2.79 mm（0.46%） |

**结论**：两种标定的 **RMS 一模一样（0.414 vs 0.413）**，判定都会给"优秀"，
但 **Z 误差标准差相差 4 倍、最大值相差 5 倍**。

**机制**：板只占画面中央时，畸变项与主点/焦距在数据上**强耦合** ——
换个噪声样本，`fx` 能漂 ±9 px、`cx` 漂 ±3.4 px，而重投影残差**照样很小**。
深度对焦距是**一阶**敏感（`Z = f·B/d`），所以 fx 的漂移直接变成深度系统误差。

**这解释了当前项目的一个真实风险**：
本机这次标定板占画面 **7.7%**，落在这张表的"中央小块"一侧；
RMS 0.939 只是"噪声大"，而**深度不确定性可能比 RMS 暗示的大得多**。

**根因不在算法，在"质量口径"**：

1. `calibrateCameraExtended` 会返回 `stdDeviationsIntrinsics` / `stdDeviationsExtrinsics`，
   而 `_calibrate_one()` **把它们丢掉了**：
   ```python
   _ret, K, D, _rv, _tv, _sdi, _sde, per_view = out     # ← _sdi/_sde 被丢掉
   ```
   这两个量**正是"参数有多可信"**，能直接换算成焦距/主点的置信区间，
   再传播成**深度不确定度（mm）** —— 那就把"RMS 看起来还行"换成可判读的数字。
2. `board_area` 已经算出来了、也打印了，但**不参与分级**：
   板占 1.9% 的标定照样能判"优秀"。
3. 因此当前的四级判定**对"板太小"这类退化完全不敏感**。

**建议修法（待实施，先写测试）**：

- 用 `stdDeviationsIntrinsics` 算 `fx`、`cx` 相对不确定度；
- 由 `σ_Z/Z ≈ (Z/(f·B))·σ_d` 与 fx/cx 的不确定度，给出**深度不确定度估计（mm）**，
  写进报告；
- 分级里加一条：**板占画面 < 8% 时最高只能判"可用"**（不得判"优秀"），
  并在报告里点名"这一条是深度精度的主要限制"。

**⚠️ 可行性验证的结论要打折看**（`outputs/_handoff_read/audit_A5_stddev.py`）：

| 姿态 | RMS | fx 实测漂移 σ | fx **报**的不确定度 σ | 排序对不对 |
| ---- | --- | ------------- | --------------------- | ---------- |
| 中央小块 | 0.403 | 12.03 px | **18.70 px** | ✅ 更差 |
| 铺满画面 | 0.416 | **42.64 px** | 6.66 px | ✅ 更好 |

- **排序方向是对的**（3× 差异，与 RMS 完全无法区分形成对比）；
- **但绝对值对不上**：铺满那档实测漂 42.6 px，而 OpenCV 报 6.66 px
  —— 说明实测漂移里有一部分**不是**参数条件数，而是**某些次收敛到更差的局部解**
  （6 次样本也偏少）。
- 所以：**可以拿它当"相对风险指示"，不能当严格置信区间往外报**。
  真要报 mm 级深度不确定度，得再做一轮"已知真值 + 多噪声样本"的校准，
  或者干脆用**重采样（bootstrap）**来估 —— 那是另一个工作项。

**注意**：这条**不能**用"RMS 已经 0.939 所以差"来解释 —— 上表证明
RMS 对这个问题**几乎免疫**。要按"参数不确定度 + 深度传播"来判。

**深度不确定度的公式与边界**（写进 `depth_sigma_mm()` 文档串）：

```
(σ_Z/Z)² = (σ_f/f)² + (σ_d/d)²        d = f·B/Z,  σ_d ≈ √2·rms
```

**不含基线项**（`stereoCalibrate` 不返回 `T` 的方差），所以是**数量级估计**，
不是严格置信区间。我在文档串里同时写明了已验证的偏差
（排序正确、绝对值不一定吻合），避免下一个人把它当验收门限用。

**判据**：`selftest_stereo_calib.py` 新增 `test_board_area_caps_grade()`（12 项）：

- 小板 + 指标完美 → **不得判"优秀"**，且给出「最高只判可用」的原因；
- 大板 + 指标完美 → **仍判"优秀"**（防止把这一档废掉）；
- `std1` 被保留、`fx_sigma()` 有限、`depth_sigma_mm()` 随距离单调增；
- **零噪声时不确定度趋于 0**（不虚报）；
- 报告里确实出现这两行。

**实跑数字**（合成，0.3 px 噪声，板占 1.6% / 11.1%）：


**实测**（outputs/_handoff_read/audit_C3_coast.py，同一段抛物轨迹）：

`
遮挡时长相同（0.3 s），只改帧率：
  30 fps：遮挡  9 帧（max_coast_frames=12）→ id 1->1 延续
  60 fps：遮挡 18 帧（max_coast_frames=12）→ id 1->2 **断开（新轨迹）**
`

**根因**：Track.dead 只数**帧**（misses > max_coast_frames），
而 max_coast_frames = 12 是帧不是秒。本项目两路常跑 30/60 fps
（取决于后端与分辨率）→ **帧率翻倍、遮挡容忍度减半**。

后果不是"少了条线"：轨迹断开会让**拖尾与预测历史清零**，
TrajectoryPredictor 拿不到跨遮挡的连续轨迹，跟踪连续性**静默变差**。

**修法**：TrackerConfig.max_coast_s = 0.4（秒）优先，
max_coast_frames 作兜底（max_coast_s <= 0 时才用）。
Track 增加 last_hit_t，dead 改判 (t - last_hit_t) > max_coast_s。

**判据**：selftest_config_wiring.py 新增
	est_coast_window_is_frame_rate_independent()：
30/60 fps 下 **id 都延续**、两者行为一致、max_coast_s=0 时退回按帧数（老配置可用）。

修后实测：30 fps id 1->1、60 fps id 1->1、兜底 60 fps id 1->2。
