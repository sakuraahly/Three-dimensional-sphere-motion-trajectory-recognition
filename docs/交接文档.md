## 0. 一句话说清项目

用**两个摄像头**实时看一个球形物体（任意球形物体，不限于特定颜色/材质），
检测位置、跟踪运动、算出**三维坐标**，并**预测未来轨迹**。

技术路线（已确定，不要改）：

    边缘检测/颜色分割  →  感知前端（不是低级步骤，输入质量决定整条链路）
    双目/RGB-D 重建    →  空间位置 (X,Y,Z)
    卡尔曼/EKF        →  状态估计与短时预测
    PID 云台（可选）   →  执行器，不是预测算法

### 4.4 双目整条链路（真渲染 + 真检测，`selftest_stereo_branch.py`）

（检测 + 跟踪）→ `StereoReconstructor` 配对 + 三角测量 → 比真值。

| 指标                                         | clean                     | realistic                 |
| -------------------------------------------- | ------------------------- | ------------------------- |
| 两路检出率                                   | 100% / 100%               | 100% / 100%               |
| 两路检测 RMSE                                | 0.54 / 0.55 px            | 0.87 / 0.86 px            |
| **配对率**                                   | **100%**                  | **99.4%**                 |
| 交会残差（中位）                             | 0.025 px                  | 0.091 px                  |
| 三维误差 均值 / RMSE / 最大                  | 13.0 / **15.6** / 48.1 mm | 25.1 / **31.6** / 86.6 mm |
| 其中横向 / 深度                              | 7.8 / 10.4 mm             | 11.2 / 22.8 mm            |
| **折算到 1 m 处**                            | **1.13 mm**               | **2.27 mm**               |
| 单目对照（只靠像素半径推深度，深度相对误差） | 0.30% / 0.48%             | 0.67% / 0.79%             |
| 右路人为滞后 1 帧 → 三维误差                 | 440 mm（**34 倍**）       | 440 mm（**17.5 倍**）     |

**怎么读这张表（很重要，别把 15.6 mm 当成"精度差"）**：

双目深度误差服从 `εZ = Z² / (f · B)` —— 本装置 1 px 视差误差 = **7.5 mm**
深度误差 @ 3.73 m。所以 4 m 处的三维 RMSE 落在 15–35 mm 是**这条定律的必然
结果**，不是实现问题；两路检测残差 0.5–0.9 px 与之完全自洽。

**验收口径是"1 m 处 ≤ 10 mm"**，折算过去是 1.13 / 2.27 mm，比验收线宽 4–9 倍。
要真正比较，必须折算到同一距离（测试会自己打印这一行）。

**同步的价值是量化的**：右路只滞后 1 帧（17 ms），三维误差就涨到 34 倍
（13 mm → 440 mm）。这就是"拍运动物体必须同步"的硬证据。

## 5. 踩过的坑（最值钱的一节，别重复踩）

1. **相位相关做相机运动估计会被运动物体带偏**。完全静止的场景里报出 6–16 px 位移 ——
   背景不变时帧间唯一变化就是那颗球。正确顺序：特征点+RANSAC（多数派）→
   网格点+LK+中位数 → 相位相关（只兜底）。

2. **帧间差分得到的是"月牙"，不是圆**。球移动时差分图含旧+新两个位置，
   叠起来是被切过的月牙，圆度全不合格（补偿后检出率反而掉到 0%）。
   正确做法：有符号差分拆正/负 → 用"当前帧内部与周围的反差"剔除残影 →
   在提议区域内做**局部 Otsu** 重新分割出球。

3. **`findChessboardCornersSB` 开 `EXHAUSTIVE` 时，找不到板会穷举，302 ms/帧**。
   绝不能每帧开。两级检测：粗检（640 宽 + 不开 EXHAUSTIVE，12 ms）判断值不值得收；
   真要收的那帧才在棋盘附近裁剪做全分辨率精确检测（40 ms）。
   **裁剪不损失分辨率**，只是缩小搜索范围。

4. **摄像头"请求分辨率"≠"实际分辨率"≠"实际帧率"**。实测 aoni A25：
   请求 1280x720 → 10 fps；请求 1024x768 → 实际给 1280x720 @ **30 fps**（DSHOW 选了不同内部模式）。
   **探测必须记住"请求值"用于重开，且重开后必须复测**，否则就是"报告 29fps、实际 10fps"。

5. **`CAP_PROP_FPS` 返回的是"你请求的值"**，不是真实帧率（请求 60 实际 29.8）。
   拿它写录像会让播放速度错一倍。要用实测值。

6. **DSHOW vs MSMF 差异巨大**：DSHOW 打开 0.7s / 1080p 只有 4.3 fps；
   MSMF 打开 6.8s / 1080p 有 32.5 fps。但 MSMF 每次 `set()` 都重协商，
   逐个分辨率探测要 30–60 秒，得不偿失。

7. **两路输出分辨率可能不同**，按"统一宽度"缩放并排预览会崩
   （实测外置 1280x720、内置实际给 1280x1080）。要**各自独立缩放 + 补齐到同一高度**。

8. **`cv2.triangulatePoints` 的结果在"校正后"的左相机坐标系**，与原始左相机系差
   立体校正旋转 `R1`。**校正量必须一路配套**：三维点用 `R1` 换算真值，
   交会残差要用 `P1/P2` 投影到**校正后**像素 —— 混用原始 `K1/K2` 和原始像素，
   会得到一个几十像素的假残差（本项目的交会残差一开始就是错的，34 px）。

9. **渲染合成测试图时两台相机的贴图比例必须一致**。曾因 px/m 不一致让板大了 2.3%，
   导致焦距和基线系统性偏 3% —— 看起来像标定算法有问题，实际是测试脚本的 bug。

10. **背景差分（MOG2）在相机移动时整体崩掉**（整幅画面都变成前景）。
    现在检测到相机在动会自动切成"对齐后再差分"。

11. **USB 带宽**：1080p YUY2 未压缩 = 124 MB/s，超过 USB 2.0 实用上限（~20 MB/s），
    只够 4–5 fps。USB 3.0（蓝口）实际 400+ MB/s，够用。

12. **YOLO 零样本能给框但给不了精确半径**（conf 0.32，半径 24.2 vs 真值 23.8），
    还会把橙色圆判成 `frisbee` 0.797。**亚像素半径必须靠几何方法**。

13. 编辑文件偶发 `ReplaceFileW EIO (Win32 1175)`（文件被占用），重试即可。

14. **"视差必须为正"这个假设会静默杀掉整条配对链路**。原来的 `match_epipolar`
    把 `min_disparity_px <= disparity <= max_disparity_px` 写在范围检查里，
    等于把"左相机在左"藏了进去。**左右装反时（同型号相机插拔后索引互换，
    画面完全正常、标定指标也好看）每个点都被静默拒绝，配对率 0%**，
    而报错只有"配不上" —— 三角测量本身没错（P1/P2 自洽），所以根本查不出来。
    现在范围检查用 `|视差|`，符号单独判，并由 `StereoRig.disparity_sign()`
    按装置实际朝向自动定；`describe()` 会在 `T[0] < 0` 时打警告。

15. **`cv2.stereoRectify` 的 `P2` 第 4 列 = `-f · T[0]`，符号与 `T[0]` 相反**。
    凭直觉按 `+f · T[0]` 推会得到相反的结论（本项目第一版 `baseline_side()`
    就是这么写反的）。这个反号是"右相机在右边 → 校正后视差为负"的来源，
    已有数值断言钉在 `selftest_stereo_branch.py::test_baseline_sign` 里。

16. **写像素级测试时别自己手算"校正后投影"**。踩坑 8 的变体：第一版用
    `P[0,0]*x/z + P[0,2]` 算校正后像素，视差算成 343 px（真值 43 px）；
    改用 `projectPoints` 后，又把**已经校正过**的像素喂给 `rectify_point_left`
    （它内部会再校正一次），dy 变成 6.1 px、配不上。**校正量必须一路配套**，
    最省事的做法是让测试走"真值场景 + 真值投影 + 完整链路"，
    而不是自己拼中间量。

17. **合成视频素材别用 `mp4v` / `XVID` 存"每帧都变"的标记**。它们有帧间预测，
    会把逐帧变化的图案当残差压掉（实测解出来前几帧全变成同一个值），
    于是测试误报成"取错了帧"。用 **MJPG / FFV1**（AVI 容器），
    并在写完素材后**自己先验一遍**再拿去断言。

18. **在 DSH/AI 沙箱进程里查不到 USB 和相机，这不是你的机器有问题**。三个表现：
    - `Get-PnpDevice` / `Get-CimInstance Win32_USBController` → **"拒绝访问"**
      （USB 枚举属特权查询，被沙箱合规拦截）；
    - `OpenCV` 的 `VideoCapture(idx)` 全部打不开，报
      `VIDEOIO(DSHOW): backend is generally available but can't be used to capture by index`。
      但 `cv2.getBuildInformation()` 里 `DirectShow: YES`、`Media Foundation: YES`，
      `cv2.pyd` 与 ffmpeg 后端 dll 都完好 —— **后端是好的，是会话隔离**：
      DSHOW/MSMF 按**交互式桌面会话**枚举相机，沙箱进程不在那个会话里；
    - 所以**相机相关的实测必须在用户自己的终端里跑**，不要在沙箱里反复试。

    **能用的替代路径**（避开特权查询，实测有效）：
    - 设备清单与位置路径 → `pnputil /enum-devices /connected /location`
      （输出 2900+ 行。加 `/location` 才有 `Location Paths`，那里面才有
      `HSxx`/`SSxx` 这种能判 USB 速率的段）；
    - 注册表 → `HKLM:\SYSTEM\CurrentControlSet\Enum\USB` **可以直接读**，
      用 `ParentIdPrefix` 能拼出设备树（`Device Parameters` 子键里**没有**速率字段）。

19. **`HSxx` ≠ "插在 USB 2.0 口"，但 `SSxx` 一定意味着 3.0**。位置路径里的
    `HS` 是 High Speed（USB 2.0 速率），`SS`/`SSP` 才是 SuperSpeed。
    所以"看到 HS"只能说明**协商结果是 2.0**，不能反推物理口是蓝的还是黑的 ——
    设备本身只支持 2.0 时，插 3.0 口也一样是 HS。
    判"换口有没有用"要看**设备规格**（A25 规格明确写 USB 2.0），
    而不是看口子颜色。§7.1 与 §7.2 有完整推导。

20. **"先缩放、再在缩放图上算、最后换算回原尺度"——换算方向写反了不会报错，
    只会让数值小一个 `s²`**。`camera_motion._estimate_features()` 就是这么错的：
    把相似变换从小图换回全分辨率时写成 `S @ M @ Si`，正确方向是 `Si @ M @ S`
    （全分辨率 → 小图 → 应用 → 回全分辨率）。
    **只影响平移项，旋转/缩放项两种夹法结果相同** —— 所以肉眼看代码很容易滑过去。
    实测（640 宽、真值平移 16 px，只改 `work_width`）：

    | work_width | s | 报出位移 | 报出/真值 | s² |
    | ---------- | - | -------- | --------- | -- |
    | 160 | 0.25 | 1.002 px | 0.0626 | 0.0625 |
    | 320 | 0.50 | 4.000 px | 0.2500 | 0.2500 |
    | 640 | 1.00 | 15.993 px | 0.9996 | 1.0000 |

    默认 `work_width=320` 配 1920 宽画面 = **36 倍**，直接导致
    `is_moving()` 几乎永不判"在动"、MOG2 的相机补偿（坑 10）永不启用。
    **判据（已钉进 `tests/selftest_camera_motion.py`）：真值不变时，
    报出的位移就不许随 `work_width` 变化。**
    这类 bug 的一般形态：**凡是"缩放到小图算完再换算回去"的地方，
    都要有一个"结果与缩放比例无关"的断言**，否则错了也看不出来。

### 7.1 USB 链路实测拓扑（2026-10 排查）

用 `pnputil /enum-devices /connected /location` 读设备位置路径得到
（`Get-PnpDevice` / `CIM Win32_USBController` 会"拒绝访问"，原因见 §5 坑 18）：

    相机 A  PCIROOT(0)#PCI(1400)#USBROOT(0)#USB(3)
            ACPI(_SB_)#ACPI(PC00)#ACPI(XHCI)#ACPI(RHUB)#ACPI(HS03)
            → 直接挂在 Intel xHCI 根集线器上

    相机 B  PCIROOT(0)#PCI(1400)#USBROOT(0)#USB(2)#USB(2)
            ACPI(_SB_)#ACPI(PC00)#ACPI(XHCI)#ACPI(RHUB)#ACPI(HS02)#USB(2)
            → 多过一级集线器（扩展坞内部）

**三个要点：**

1. **两台都是 USB 2.0 设备，协商在 High Speed。** 路径里的 `HSxx`
   就是 High Speed；若按 3.0 超速连接，这一段会是 `SSxx` / `SSP`。
   而且 **aoni A25 本身只支持 USB 2.0**（规格标 `接口类型: USB 2.0`），
   所以**插到蓝色 USB 3.0 口也只能协商到 High Speed**，拿不到超速带宽。
2. **两台共用同一条 USB 2.0 总线** —— 同一颗 Intel xHCI（`PCI(1400)`）
   下的同一个根集线器（`RHUB`）。相机 B 还额外挂在扩展坞的一级 USB 2.0
   集线器后面，与坞上其他设备抢带宽。
3. 扩展坞本身是 3.0 的（`VID_35D6&PID_3510 Generic SuperSpeed USB Hub`），
   但相机是 2.0 设备，只能以 2.0 接入。

### 7.2 带宽够不够：算得过来，不是瓶颈

代码里 `CameraSource` 默认 `fourcc="MJPG"`（`sphere_tracker/sources.py:150`），
拿到的是**压缩流**。按 MJPEG 的实际码率算：

| 格式                         | 1080p30 单路  | 两路合计    | USB 2.0 实用上限（~35–40 MB/s） |
| ---------------------------- | ------------- | ----------- | ------------------------------- |
| **MJPEG（当前用法）**        | 约 1.5–3 MB/s | 约 3–6 MB/s | ✅ **余量 6–12 倍**              |
| YUY2 未压缩（假如没设 MJPG） | 约 124 MB/s   | —           | ❌ 只够 4–5 fps                  |

**结论：只要确实在用 MJPEG，USB 2.0 带宽对 1080p30 双路是够的。**

> ⚠️ **这里更正一条旧说法。** 本节以前写着"索引 0 插在 USB 2.0 口，
> 带宽受限，换到 3.0 口白白损失分辨率"。按上面的实测与计算，
> **这个因果不成立**：
> - A25 是 2.0 设备，换口也拿不到超速带宽；
> - 用 MJPEG 时 2.0 总线本来就有 6–12 倍余量。
>
> 所以"索引 0 分辨率偏低"如果确实存在，**原因不在这里**，
> 应往别处查（见 §7.3）。

- 相机**抖动**移动时停用"像素重力"约束退回自由二次拟合；匀速平移时保留

4. **`sphere_tracker/camera_motion.py` `_estimate_features()` 位移换算方向写反** ——
   把"小图上解出的相似变换"换回全分辨率时写成 `M_full = S @ M_small @ Si`，
   正确方向是 `Si @ M_small @ S`。旋转/缩放项不受影响，**只有平移项差一个 `s²`**：

   | work_width | s | 报出位移（真值 16 px） | 报出/真值 | s² |
   | ---------- | - | ---------------------- | --------- | -- |

   | 320 | 0.50 | 4.000 px | 0.2500 | 0.2500 |
   | 640 | 1.00 | 15.993 px | 0.9996 | 1.0000 |

   `matrix` 平移同比例偏小 → `warp_to_current()` 对不齐，差分退化成坑 2 的"月牙"。

   **为什么一直没被发现**：同一文件里三个估计方法的换算，另两个（`_estimate_grid`
   的 `med / s`、`_estimate_phase` 的 `sx / s`）都是对的，**只有主力方法错**；
   而合成 panning 场景恰好走 grid 分支，把 bug 完整盖住了 ——
   这正是坑 20 说的"合成真值漂亮 ≠ 真机可用"。已修 + 补测试。

### 10.10 真机标定第一次尝试暴露的问题（2026-10-10）

用户第一次真机标定，卡在 `collected 0/25`、`x122 两路未同时检测到棋盘`，
并反馈"左摄像头清晰度远远小于右摄像头"。截图显示：左路整幅蒙了一层奶白雾 +
左上角大面积过曝，右路通透锐利；同时 `detect 19 ms/frame (52 fps)` ——
**帧率是健康的**，这一点很关键（见下）。

**(1) 先纠正一个容易查错方向的判断：这不是 USB 带宽问题**

带宽不足的指纹是"**卡**"：帧率掉、残帧（下半幅常量）、驱动降分辨率。
它**不会**让画面变"糊"或蒙雾 —— 图像质量是光学与曝光的事，与传输速率无关。
**判断依据主要是"症状类型"，不是那个 52 fps**（这一点要写清楚，别被它误导）：
界面上的 `detect 19 ms/frame (52 fps)` 量的是**检测计算耗时**（`calibrate_stereo.py`
里 `perf_counter` 只夹在检测那一段），**不是相机采集帧率** —— 它只能说明
"帧在源源不断地进来、处理不是瓶颈"，**证明不了链路速率**。
真正站得住的依据是：**带宽不足不会让画面变糊**（它只会掉帧/降档/下半幅发灰），
而左路那种"整幅蒙雾 + 大面积过曝"是光学与曝光的现象。
§7.2 另有一笔独立账：MJPEG 双路 1080p30 在 USB 2.0 上还有 6–12 倍余量。

不过**结论仍然要实测才能定**，所以下面第 (3) 条加了工具 ——
它直接量"实测采集帧率"与"残帧数"，那才是能定性的指标。

**但它仍然值得"测一次再下结论"**，所以新增了工具（见 (3)），
把"带宽 vs 光学"变成可测量的判据，而不是靠嘴说。

**(2) 标定卡住的真正原因是画面质量，不是门限太严**

用户以为"手抖都不容忍"，但 `x122` 全部落在**第 1 道门限**（两路未同时检测到棋盘），
**根本没走到"停稳"那一道**。所以当务之急是修左路画面，不是放松门限。

不过原实现有个真实缺陷：第 1 道门限只说"两路未同时检测到棋盘"，
**不说是哪一路**。两路质量差很多时，人在窗口前挪半天板子也查不出方向。已修：

- 门限 1 现在会说 `左路未检测到棋盘（右路正常）`；
- 并顺带调用新增的 `diagnose_frame()` 给出画面会诊；
- 标定窗口**右上角新增逐路状态**（`左: 清晰度 210 面积 4.2% 曝光 118`），
  实时就能看出是哪一路、差在哪。

**(3) 新增 `apps/tools/camera_quality.py`：把"糊"和"卡"分开**

逐台量：请求/实际分辨率、实测帧率、**残帧数**、清晰度（Laplacian 方差）、
亮度/过曝/死黑、反差；两路对比后给结论。判据表：

| 现象 | 带宽/链路不足 | 光学/曝光问题 |
| ---- | ------------- | ------------- |
| 实测帧率 | 偏低；两路同开骤降 | 正常 |
| 残帧（下半幅常量） | **会出现** | 不会 |
| 实际分辨率 | 被降档 | 正常 |
| 清晰度 | 正常 | **明显偏低** |
| 过曝 / 动态范围 | 正常 | 可能异常 |

`--together` 额外测"两路同开"，用来暴露共用总线的争抢（单开正常、同开掉速）。
**唯一能定性归因的是交换测试**：把两台的口/线对调，问题跟着相机走 = 相机问题，
留在原口 = 链路问题。工具会把这段说明打出来。

`diagnose_frame()` 的蒙雾判据用的是**动态范围**（p95−p5 < 70）而**不是整幅标准差** ——
画面里有大块纯色（白墙、木桌）会把标准差抬高，用标准差会漏判。
这条在写测试时被当场抓到：第一版用 `std < 6`，合成蒙雾图给的是"无异常"。

**(4) 手持标定：给了"有代价"的放宽，而不是偷偷放水**

`apps/calibrate_stereo.py` 新增 `--stationary-px`（默认仍 3）与 `--relaxed` 预设
（停稳 10px、清晰度 28、更小的板、更贴边），并**明确打印"这是用精度换成功率"**。

**没有把默认值改松**，原因是那条门限承担着真实职责：两台 USB 相机**没有硬件同步**，
"板静止"是用"静态目标在任意时刻看起来都一样"来**替代时间同步**。
放太松 = 两路拍到不同位姿 → R/T 系统性偏，而且**不报错、事后查不出来**。
所以推荐顺序是：① 让板靠住（椅背/纸箱/书立）→ ② 加光提高快门 → ③ 才动门限。

**(5) 新增第 9 个回归测试**

`tests/selftest_camera_quality.py`：用已知答案的合成图钉住
① 会诊判据（正常图不误报、蒙雾/过曝/过暗/全黑各自指对方向）、
② 残帧判定（下半幅常量 → 识别；正常图、纯色图、带噪声暗背景 → **不误判**）、
③ 逐路状态在无观测时不崩。**全合成图，不开任何相机**，几秒跑完。
