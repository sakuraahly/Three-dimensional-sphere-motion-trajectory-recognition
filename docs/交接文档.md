## 0. 一句话说清项目

用**两个摄像头**实时看一个球形物体（任意球形物体，不限于特定颜色/材质），
检测位置、跟踪运动、算出**三维坐标**，并**预测未来轨迹**。

技术路线（已确定，不要改）：

    边缘检测/颜色分割  →  感知前端（不是低级步骤，输入质量决定整条链路）
    双目/RGB-D 重建    →  空间位置 (X,Y,Z)
    卡尔曼/EKF        →  状态估计与短时预测
    PID 云台（可选）   →  执行器，不是预测算法

| 单目对照（只靠像素半径推深度，深度相对误差） | 0.30% / 0.48%             | 0.67% / 0.79%             |
| 右路人为滞后 1 帧 → 三维误差                 | 440 mm（**34 倍**）       | 440 mm（**17.5 倍**）     |

**怎么读这张表（很重要，别把 15.6 mm 当成"精度差"）**：

双目深度误差服从 `εZ = Z² / (f · B)` —— 本装置 1 px 视差误差 = **7.5 mm**
深度误差 @ 3.73 m。所以 4 m 处的三维 RMSE 落在 15–35 mm 是**这条定律的必然
结果**，不是实现问题；两路检测残差 0.5–0.9 px 与之完全自洽。

**验收口径是"1 m 处 ≤ 10 mm"**，折算过去是 1.13 / 2.27 mm，比验收线宽 4–9 倍。
要真正比较，必须折算到同一距离（测试会自己打印这一行）。

**同步的价值是量化的**：右路只滞后 1 帧（17 ms），三维误差就涨到 34 倍
（13 mm → 440 mm）。这就是"拍运动物体必须同步"的硬证据。

## 5. 踩过的坑（最值钱的一节，别重复踩）

1. **相位相关做相机运动估计会被运动物体带偏**。完全静止的场景里报出 6–16 px 位移 ——
   背景不变时帧间唯一变化就是那颗球。正确顺序：特征点+RANSAC（多数派）→
   网格点+LK+中位数 → 相位相关（只兜底）。

2. **帧间差分得到的是"月牙"，不是圆**。球移动时差分图含旧+新两个位置，
   叠起来是被切过的月牙，圆度全不合格（补偿后检出率反而掉到 0%）。
   正确做法：有符号差分拆正/负 → 用"当前帧内部与周围的反差"剔除残影 →
   在提议区域内做**局部 Otsu** 重新分割出球。

3. **`findChessboardCornersSB` 开 `EXHAUSTIVE` 时，找不到板会穷举，302 ms/帧**。
   绝不能每帧开。两级检测：粗检（640 宽 + 不开 EXHAUSTIVE，12 ms）判断值不值得收；
   真要收的那帧才在棋盘附近裁剪做全分辨率精确检测（40 ms）。
   **裁剪不损失分辨率**，只是缩小搜索范围。

4. **摄像头"请求分辨率"≠"实际分辨率"≠"实际帧率"**。实测 aoni A25：
   请求 1280x720 → 10 fps；请求 1024x768 → 实际给 1280x720 @ **30 fps**（DSHOW 选了不同内部模式）。
   **探测必须记住"请求值"用于重开，且重开后必须复测**，否则就是"报告 29fps、实际 10fps"。

5. **`CAP_PROP_FPS` 返回的是"你请求的值"**，不是真实帧率（请求 60 实际 29.8）。
   拿它写录像会让播放速度错一倍。要用实测值。

6. **DSHOW vs MSMF 差异巨大**：DSHOW 打开 0.7s / 1080p 只有 4.3 fps；
   MSMF 打开 6.8s / 1080p 有 32.5 fps。但 MSMF 每次 `set()` 都重协商，
   逐个分辨率探测要 30–60 秒，得不偿失。

7. **两路输出分辨率可能不同**，按"统一宽度"缩放并排预览会崩
   （实测外置 1280x720、内置实际给 1280x1080）。要**各自独立缩放 + 补齐到同一高度**。

8. **`cv2.triangulatePoints` 的结果在"校正后"的左相机坐标系**，与原始左相机系差
   立体校正旋转 `R1`。**校正量必须一路配套**：三维点用 `R1` 换算真值，
   交会残差要用 `P1/P2` 投影到**校正后**像素 —— 混用原始 `K1/K2` 和原始像素，
   会得到一个几十像素的假残差（本项目的交会残差一开始就是错的，34 px）。

9. **渲染合成测试图时两台相机的贴图比例必须一致**。曾因 px/m 不一致让板大了 2.3%，
   导致焦距和基线系统性偏 3% —— 看起来像标定算法有问题，实际是测试脚本的 bug。

10. **背景差分（MOG2）在相机移动时整体崩掉**（整幅画面都变成前景）。
    现在检测到相机在动会自动切成"对齐后再差分"。

11. **USB 带宽**：1080p YUY2 未压缩 = 124 MB/s，超过 USB 2.0 实用上限（~20 MB/s），
    只够 4–5 fps。USB 3.0（蓝口）实际 400+ MB/s，够用。

12. **YOLO 零样本能给框但给不了精确半径**（conf 0.32，半径 24.2 vs 真值 23.8），
    还会把橙色圆判成 `frisbee` 0.797。**亚像素半径必须靠几何方法**。

13. 编辑文件偶发 `ReplaceFileW EIO (Win32 1175)`（文件被占用），重试即可。

14. **"视差必须为正"这个假设会静默杀掉整条配对链路**。原来的 `match_epipolar`
    把 `min_disparity_px <= disparity <= max_disparity_px` 写在范围检查里，
    等于把"左相机在左"藏了进去。**左右装反时（同型号相机插拔后索引互换，
    画面完全正常、标定指标也好看）每个点都被静默拒绝，配对率 0%**，
    而报错只有"配不上" —— 三角测量本身没错（P1/P2 自洽），所以根本查不出来。
    现在范围检查用 `|视差|`，符号单独判，并由 `StereoRig.disparity_sign()`
    按装置实际朝向自动定；`describe()` 会在 `T[0] < 0` 时打警告。

15. **`cv2.stereoRectify` 的 `P2` 第 4 列 = `-f · T[0]`，符号与 `T[0]` 相反**。
    凭直觉按 `+f · T[0]` 推会得到相反的结论（本项目第一版 `baseline_side()`
    就是这么写反的）。这个反号是"右相机在右边 → 校正后视差为负"的来源，
    已有数值断言钉在 `selftest_stereo_branch.py::test_baseline_sign` 里。

16. **写像素级测试时别自己手算"校正后投影"**。踩坑 8 的变体：第一版用
    `P[0,0]*x/z + P[0,2]` 算校正后像素，视差算成 343 px（真值 43 px）；
    改用 `projectPoints` 后，又把**已经校正过**的像素喂给 `rectify_point_left`
    （它内部会再校正一次），dy 变成 6.1 px、配不上。**校正量必须一路配套**，
    最省事的做法是让测试走"真值场景 + 真值投影 + 完整链路"，
    而不是自己拼中间量。

17. **合成视频素材别用 `mp4v` / `XVID` 存"每帧都变"的标记**。它们有帧间预测，
    会把逐帧变化的图案当残差压掉（实测解出来前几帧全变成同一个值），
    于是测试误报成"取错了帧"。用 **MJPG / FFV1**（AVI 容器），
    并在写完素材后**自己先验一遍**再拿去断言。

18. **在 DSH/AI 沙箱进程里查不到 USB 和相机，这不是你的机器有问题**。三个表现：
    - `Get-PnpDevice` / `Get-CimInstance Win32_USBController` → **"拒绝访问"**
      （USB 枚举属特权查询，被沙箱合规拦截）；
    - `OpenCV` 的 `VideoCapture(idx)` 全部打不开，报
      `VIDEOIO(DSHOW): backend is generally available but can't be used to capture by index`。
      但 `cv2.getBuildInformation()` 里 `DirectShow: YES`、`Media Foundation: YES`，
      `cv2.pyd` 与 ffmpeg 后端 dll 都完好 —— **后端是好的，是会话隔离**：
      DSHOW/MSMF 按**交互式桌面会话**枚举相机，沙箱进程不在那个会话里；
    - 所以**相机相关的实测必须在用户自己的终端里跑**，不要在沙箱里反复试。

    **能用的替代路径**（避开特权查询，实测有效）：
    - 设备清单与位置路径 → `pnputil /enum-devices /connected /location`
      （输出 2900+ 行。加 `/location` 才有 `Location Paths`，那里面才有
      `HSxx`/`SSxx` 这种能判 USB 速率的段）；
    - 注册表 → `HKLM:\SYSTEM\CurrentControlSet\Enum\USB` **可以直接读**，
      用 `ParentIdPrefix` 能拼出设备树（`Device Parameters` 子键里**没有**速率字段）。

19. **`HSxx` ≠ "插在 USB 2.0 口"，但 `SSxx` 一定意味着 3.0**。位置路径里的
    `HS` 是 High Speed（USB 2.0 速率），`SS`/`SSP` 才是 SuperSpeed。
    所以"看到 HS"只能说明**协商结果是 2.0**，不能反推物理口是蓝的还是黑的 ——
    设备本身只支持 2.0 时，插 3.0 口也一样是 HS。
    判"换口有没有用"要看**设备规格**（A25 规格明确写 USB 2.0），
    而不是看口子颜色。§7.1 与 §7.2 有完整推导。

20. **"先缩放、再在缩放图上算、最后换算回原尺度"——换算方向写反了不会报错，
    只会让数值小一个 `s²`**。`camera_motion._estimate_features()` 就是这么错的：
    把相似变换从小图换回全分辨率时写成 `S @ M @ Si`，正确方向是 `Si @ M @ S`
    （全分辨率 → 小图 → 应用 → 回全分辨率）。
    **只影响平移项，旋转/缩放项两种夹法结果相同** —— 所以肉眼看代码很容易滑过去。
    实测（640 宽、真值平移 16 px，只改 `work_width`）：

    | work_width | s | 报出位移 | 报出/真值 | s² |
    | ---------- | - | -------- | --------- | -- |
    | 160 | 0.25 | 1.002 px | 0.0626 | 0.0625 |
    | 320 | 0.50 | 4.000 px | 0.2500 | 0.2500 |
    | 640 | 1.00 | 15.993 px | 0.9996 | 1.0000 |

    默认 `work_width=320` 配 1920 宽画面 = **36 倍**，直接导致
    `is_moving()` 几乎永不判"在动"、MOG2 的相机补偿（坑 10）永不启用。
    **判据（已钉进 `tests/selftest_camera_motion.py`）：真值不变时，
    报出的位移就不许随 `work_width` 变化。**
    这类 bug 的一般形态：**凡是"缩放到小图算完再换算回去"的地方，
    都要有一个"结果与缩放比例无关"的断言**，否则错了也看不出来。

21. **SB 与经典检测器返回的角点顺序恰好整体反序**（RMS 323.112 px ↔ 0.020 px，
    分类正是 8x5 点阵的 `rot180`）。**单目标定对它免疫、双目标定不免疫**，
    而且**不报错** —— 一路 SB、一路经典会让双目标定静默产出垃圾 R/T
    （合成复现：整体 RMS 21~42 px、基线被吹到真值的 8~15 倍）。
    判据钉在 `tests/selftest_board_corner_order.py`；
    守卫在 `calib/capture.py`（两道：粗检后、精确复核后）。详见 §12.1。

22. **"看起来在检查"与"真的在检查"是两件事**（本轮在反向自证里踩到）：
    写了个"临时造一处失效引用，检查器应当报红"的自证 —— **它没红**。
    根因是 `check_standards.py` 把 `outputs/` 也当事实来源扫，
    于是**我自己写在那里的调试代码让那个假路径变成了"合法字面量"**。
    → 一般形态：**临时产物不能当事实来源**；而且
    **反向自证本身也需要被验证**（"跑了一遍没报错" ≠ "它真的在检查"）。

23. **`cv2.setRNGSeed()` 管不住 `cv2.stereoCalibrate` 内部的 RANSAC**：
    同一份输入，基线估计能在 2000~13000 mm 之间跳。
    → 涉及它的断言**只能钉数量级**（>5 倍、>10 倍、>30°），钉具体数值必然变成噪声。

24. **用替身（stub）构造场景的测试，必须断言"替身真的走到了那一步"**。
    本轮一个"精确复核才混用"的场景因为替身的调用计数器写成 `i % 2`（超过 2 次就错位）
    **根本没被构造出来**，测试却报"通过" —— 是它自己那条
    "替身必须被调用 ≥4 次"的断言抓出来的。
    → **"测试通过"里最危险的一种，是它其实没测到东西。**

25. **改 `.bat` 之后必须复跑**（不是形式主义）：本轮给 `test` 加了 `full` 参数、
    加了 `standards` 分支，编码仍是 UTF-8 无 BOM + 纯 CRLF，实跑 `启动程序.bat test`
    与 `standards` 各通过。**改完不复跑，行尾或码页一坏，报错信息完全指不到真正的原因**（见 §10.9）。

26. **界面能设的东西，不许是一份与真实取值无关的装饰。**
    `启动程序.py` 硬编码 `--cols 8 --rows 5 --square 25` 且**完全没传 `--target`**，
    于是从界面走**永远**用脚本默认的试标定档 —— 而界面上**没有任何迹象**。
    **"文档里写的正式档，从界面根本到不了"** 比没有默认值更糟：用户以为做对了。
    核对办法：把界面拼出的命令行打出来，与文档承诺的档位**逐字对一遍**。（§13.1）

27. **"合成图上测得挺快"对性能没有参考价值。**
    `hough` 在纯色底 + 一个圆上 **132 ms**，在真实房间（书架/床/杂物）上 **4384.9 ms** ——
    **33 倍**。`HoughCircles` 先做 Canny，纹理一多边缘就爆炸。
    这与坑 20 的 `s²` 是**同一类错误**：合成场景恰好绕开了真实输入的关键性质。
    → **性能基准必须用真实纹理**，或者至少两种输入都测。（§13.5）

28. **手算 grid 行号 = 迟早重叠。** 参数辅助函数内部占 `row*2` 与 `row*2+1` 两行，
    调用方传 1、2、3… 并**另手工放**复选框 —— 手算的行号正好落在被占的行上。
    **Tk 不报"两个控件在同一格"，它直接画在一起**，用户看到的是"文字被遮挡"。
    根因不是那几个错行号，是**这种做法**。改成每个容器一个游标。（§13.3）

29. **写死的换行宽度是对窗口尺寸的猜测，窗口一改就错。**
    写死 820（按"窗口 900"估的），窗口改成 980 之后卡片自宽 873 而视口 966 ——
    文字在卡片那一列里被切掉，右边还空一片。必须**按视口动态算**。（§13.3）

30. **叠加层必须在"最终画布"上画；先画后缩 = 所有文字被重采样糊掉。**
    把 `display_width` 折进同一个 `scale`，于是先在 1920 画布上用原字号写 HUD，
    再把整张图压到 960。量化：纯白笔画占比 **0.1% → 3.0%**、最亮像素 **245 → 255**。
    **顺序错了，字就糊了** —— 而这看起来像"字体问题"。（§13.5）

31. **"自动恢复"可能是在制造那个已知的坏状态。**
    我加了"MSMF 拿不到帧就自动改用 DSHOW"，实测**更糟**：
    换完后 `optimize_mode` 在**混合后端的进程**里测到 0.0 fps → 触发几十秒模式搜索
    → 把分辨率降到 1280x720 写进缓存。而**单独测同一台相机的 MSMF 是 10/10 帧全好的**。
    根因代码里早写着：**同一进程混用 DSHOW + MSMF，MSMF 那路会"打开成功但抓不到帧"**。
    → **宁可口头说清让人显式选，也不要静默补救。**（§13.8）

32. **任何循环都要有预算 —— 单次 `cap.read()` 可能要 10 秒。**
    设备不响应时 MF 的抓帧超时是 10 秒；12 次读 × 4 档分辨率 × 3 个后端 = **8 分钟以上**，
    而全程一个字都不打印。用户看到的就是"点了运行，然后什么都没有"。
    现在：一帧都读不到 = 设备层面问题 → 跳过其余分辨率；每次读上限 3 秒；总预算 60 秒。
    **8 分钟 → 10.6 秒**。（§13.8）

33. **`cv2.WINDOW_FULLSCREEN == cv2.WINDOW_AUTOSIZE == 1`**（本构建实测）。
    所以 `namedWindow(name, WINDOW_FULLSCREEN)` **得不到全屏窗口**，它等价于 AUTOSIZE。
    全屏**只能**走 `setWindowProperty`。**不要相信看起来语义正确的那条路，实测它。**（§13.7）

34. **`cv2.contourArea` 对"行序网格点"恒为 0。**
    它按多边形顶点顺序算，而角点是行序网格 —— 路径自己折回去。必须先用 `convexHull`。
    （这个数字本来是要用来回答"板占画面多少"，恒 0 会让结论完全反过来。）（§13.2）

35. **缓存没有"过期"概念。** `config/camera_modes.json` 里相机 1 一度被钉在 **640x480** ——
    是相机坏掉那段时间模式搜索写进去的，之后**一直用**，没有任何机制发现它已经不对。
    → 加缓存时要想清楚**什么时候作废**。（§13.8）

36. **"变异没红"必须先分清是"判据弱"还是"注入没生效"。**
    本轮三次遇到：一次是注入的字符串根本没匹配上（源码没变），
    一次是**断言写成了重言式**（改了个副本的字段却断言原对象，恒真），
    一次是**判据本来就不可测**（那道守卫在另一个函数里，测试走不到）。
    三者要采取的行动完全不同。→ 变异脚本必须**报出"注入后源码没变"**。（§13.10）
37. **"这台相机打不开 / 恒为纯黑"先问"它是哪台"，再问"它怎么坏了"。**
    本机的**笔记本内置相机被用户有意遮住**（不参与双目），所以它必然表现为
    `MSMF 能打开但一帧都拿不到` / `DSHOW 出帧但恒为纯黑`（`mean=0.0`）——
    **这是预期行为，不是故障**：没有光进来就没有画面。

    ⚠️ **我在这上面误判了**（用户当场纠正）：看到某个索引恒为纯黑，
    我先断言"那是 `aoni` 外接相机坏了，建议换相机/换线"，
    而它其实是**被遮住的内置相机**。教训有两条：

    - **枚举位次 ≠ 物理身份**。`cameras.py list` 的 `#N` 是 PnP 枚举位次，
      而"哪台是内置"只能靠**名字**（`Integrated*`）或**盖住镜头看哪台变黑**来认。
      **不能靠"我测到 `#N` 是黑的"反推它是哪台** —— 见 §11.1：
      PnP / DSHOW / MSMF **三套枚举互相错位**，而且实测还会随时间浮动。
    - **排查黑屏的第一问是"这台是哪台"，不是"它怎么坏了"**。顺序反了，
      就会给出"换相机"这种让人白跑的建议。

    处置：在 `identify` 里给内置相机按 `n` 标成「无关」（本机 `Integrated Camera`
    与 `Integrated IR Camera` 都已在「无关」清单里），之后自动挑相机会跳过它。
    已写进 `用户手册.md` §3.3（含"怎么一眼认出内置相机"）与故障排查表。
38. **"变异脚本"必须进版本库，不能躺在 `outputs/` 里。**

    全放在 `outputs/_handoff_read/` —— 而 `outputs/` **被整个 gitignore**。
    后果：证据**不受版本管理、删了就没了**，而且"该跑哪些变异"只活在对话里。

    已全部收进 `tests/selftest_mutation_guards.py`（13 条变异 + 统一运行器）。

    - **安全契约**：改源码前备份原文 + SHA256，`finally` 里写回并**校验哈希**；
      不等就**中止**（别在污染的工作区上继续叠加变异）。锚点不唯一（命中 ≠ 1）

    - **必须登记进 `NEVER_FAST`**（`apps/run_tests.py`）：它运行期会把源码改成

      把安全性交给"千万别改成并行"来维持太脆。

39. **修"错"时别把"能看见"也一起修掉 —— 回退要分层，不能一刀切。**
    2026-10-18 我为了修"识别界面把 aoni 标成 Integrated"（§10.13 / §10.14），
    把 `identify` 的**后端回退整个删掉**（`33b7164`）。结果：MSMF 打不开的那台
    在识别界面里**直接消失** —— 用户的原话是"aoni 摄像头又是只能检测到一个了"，
    而 `cameras.py list --probe`（**带回退**）明明两台都能出图。

    **教训**：一个动作同时承担了两件事，而它们该分层：

    | 用途 | 能不能换后端 | 理由 |
    | ---- | ------------ | ---- |
    | **看见画面**（判断"这台活着吗"） | ✅ 可以 | 不换就完全没信息 |
    | **绑定身份**（哪台是 left） | ❌ 不行 | 换过后 `#N` 不再对应 PnP 名字 |

    现在的实现：`_open_preview()` 会回退，并把**实际后端**一起返回；
    只要不是 `INDEX_BACKEND`，标签改成 `#N ？？未知（经 DSHOW 打开…）`，
    且**按任何键都不写配置**，只提示改用 `pin <role> name:"..."`。

    **推论**：以后遇到"某个功能既用于诊断又用于决策"，**先把两种用途拆开**，
    再决定各自允许多大的自由度。一刀切地收紧，会把诊断能力一起砍掉 ——
    而"看不见"比"标错"更难排查：标错至少还能靠画面纠正。

    > 同一轮里还有两个**我自己引入又自己修**的小坑，记下以免重犯：
    > ① 把 `_open_preview` 拆成 `_open_preview` + `_try_open` 时，
    > 旧的 `except` 尾巴被留在了新函数里，引用了未定义的 `used_name`
    > （`NameError`）—— **拆分函数后必须整段重读，不能只替换上半截**。

40. **"按索引回退后端"在**显示**这一层也站不住 —— 会让同一台相机出现两次。**
    2026-10-18 同一件事我改了三次，三次都被用户当场抓到：

    | 改法 | 用户看到 | 原因 |
    | ---- | -------- | ---- |
    | `af8bb30` 按索引回退 | **aoni 被标成 Integrated** | DSHOW 编号与 PnP 错位 |
    | `33b7164` 删掉回退 | **只剩一台** | 打不开的那台直接从界面消失 |
    | "回退只为显示、不许绑定" | **同一台 aoni left 出现两次，right 不见** | `DSHOW #2` 与 `MSMF #0` 可能是同一台 |

    **根因**：PnP 与各后端的编号是**互不相容的三套命名空间**。
    任何"混着用"的方案都必然三选一：**贴错、重复、遗漏**。

    **最终定案（`_open_preview`）**：只做一件事 ——
    **在同一个后端内开一个编号，绝不换**。
    - 打不开就如实报"打不开"，并在 `identify` 结束时**列出哪些编号没能打开**；
    - 想确认"另一台在别的后端下能不能出图"，用 `cameras.py probe`
      （它**逐后端分别列出**，本来就不下"哪台是哪台"的结论）；
    - 要换后端，用**显式** `--backend dshow`（整场都换，标签会说明不可信）。

    **教训**：诊断与决策必须分层，但**分层不等于可以混用命名空间**。
    我第三次的"折中"看起来兼顾了两边，实际是把两边的缺陷都引进来 ——
    折中方案也要先问"它在最坏情况下会输出什么"，而不是只看它能否满足两个目标。
    详见 `docs/交接文档.md` §10.15。

41. **"这台机器上没有那台设备"不该让逻辑判据假红。**
    2026-10-19 复跑 fast 档是 **19/20**，红的是
    `selftest_pair_source` 里"角色名 + `--backend dshow` 必须被拒绝"那一条。
    它直接调 `from_args`，而 `from_args` 先用 `resolve_camera_arg` 解析角色 ——
    相机一拔，解析先抛"没有为「left」选定相机"，**后面的后端守卫
    （`pnp_derived` 且 `api != INDEX_BACKEND`）根本没被走到**，
    判据要的"不能一起用 / PnP"自然对不上。**逻辑项被真机状态绑住了。**

    修法：只替身**输入**（`resolve_camera_arg` 返回 0/1），守卫仍走产品代码；
    两条"非空转"判据 —— `Counter(resolved)` 各一次（解析没被绕过）、
    `built == []`（守卫在构造 `PairSource` **之前**就拒绝）。后者防的是
    "守卫被挪到构造之后"：真机会先开相机，而异常照样让测试变绿。
    **产品行为不变**：无相机时 `from_args` 仍先报角色解析失败；改的是判据，不是报错顺序。

    **判据**：`tests/selftest_pair_source.py` 在无相机机器上必须
    `判定结果：全部通过` 且退出码 0；**把替身去掉**（回到真实解析）或
    **绕过守卫**（`INDEX_BACKEND` 临时改成 DSHOW）都必须变红（反向自证）。
    **"没相机"只该让真机项 `[跳过]`，不该让逻辑项假红** ——
    假警报会训练人忽略真警报（§10.16 第 6 条）。

### 7.1 USB 链路实测拓扑（2026-10 排查）

用 `pnputil /enum-devices /connected /location` 读设备位置路径得到
（`Get-PnpDevice` / `CIM Win32_USBController` 会"拒绝访问"，原因见 §5 坑 18）：

    相机 A  PCIROOT(0)#PCI(1400)#USBROOT(0)#USB(3)
            ACPI(_SB_)#ACPI(PC00)#ACPI(XHCI)#ACPI(RHUB)#ACPI(HS03)
            → 直接挂在 Intel xHCI 根集线器上

    相机 B  PCIROOT(0)#PCI(1400)#USBROOT(0)#USB(2)#USB(2)
            ACPI(_SB_)#ACPI(PC00)#ACPI(XHCI)#ACPI(RHUB)#ACPI(HS02)#USB(2)
            → 多过一级集线器（扩展坞内部）

**三个要点：**

1. **两台都是 USB 2.0 设备，协商在 High Speed。** 路径里的 `HSxx`
   就是 High Speed；若按 3.0 超速连接，这一段会是 `SSxx` / `SSP`。
   而且 **aoni A25 本身只支持 USB 2.0**（规格标 `接口类型: USB 2.0`），
   所以**插到蓝色 USB 3.0 口也只能协商到 High Speed**，拿不到超速带宽。
2. **两台共用同一条 USB 2.0 总线** —— 同一颗 Intel xHCI（`PCI(1400)`）
   下的同一个根集线器（`RHUB`）。相机 B 还额外挂在扩展坞的一级 USB 2.0
   集线器后面，与坞上其他设备抢带宽。
3. 扩展坞本身是 3.0 的（`VID_35D6&PID_3510 Generic SuperSpeed USB Hub`），
   但相机是 2.0 设备，只能以 2.0 接入。

### 7.2 带宽够不够：算得过来，不是瓶颈

代码里 `CameraSource` 默认 `fourcc="MJPG"`（`sphere_tracker/sources.py:150`），
拿到的是**压缩流**。按 MJPEG 的实际码率算：

| 格式                         | 1080p30 单路  | 两路合计    | USB 2.0 实用上限（~35–40 MB/s） |
| ---------------------------- | ------------- | ----------- | ------------------------------- |
| **MJPEG（当前用法）**        | 约 1.5–3 MB/s | 约 3–6 MB/s | ✅ **余量 6–12 倍**              |
| YUY2 未压缩（假如没设 MJPG） | 约 124 MB/s   | —           | ❌ 只够 4–5 fps                  |

**结论：只要确实在用 MJPEG，USB 2.0 带宽对 1080p30 双路是够的。**

> ⚠️ **这里更正一条旧说法。** 本节以前写着"索引 0 插在 USB 2.0 口，
> 带宽受限，换到 3.0 口白白损失分辨率"。按上面的实测与计算，
> **这个因果不成立**：
> - A25 是 2.0 设备，换口也拿不到超速带宽；
> - 用 MJPEG 时 2.0 总线本来就有 6–12 倍余量。
>
> 所以"索引 0 分辨率偏低"如果确实存在，**原因不在这里**，
> 应往别处查（见 §7.3）。

> 同理 `Get-PnpDevice`、`Get-CimInstance Win32_USBController` 会"拒绝访问"。
> **能用的替代**：`pnputil /enum-devices /connected /location`
> 与读注册表 `HKLM:\SYSTEM\CurrentControlSet\Enum\USB`（§7.1 就是这么查的）。
> 帧率这类必须真采一帧的指标，**只能让用户在本地跑**。

### 两个硬约束

1. **双目要求两台相机相对位姿固定**。整体移动没关系（R,T 是常数），
   但**两台各自移动完全不行** —— 相对位姿每帧变，三角测量失效。
2. **两台同型号，索引顺序在重新插拔/重启后可能互换**。左右一换，标定的 R,T 就失效，
   而画面看起来完全正常。→ 贴 L/R 标签；每次拍摄前跑 `verify_stereo.py`
   （未动 0.08px vs 碰动 27.9px，差 250 倍）。

**(2) 踩到一个很难查的坑：LF 行尾的 .bat + 中文 = cmd 行同步错乱**

纯 ASCII 的 LF 文件侥幸能跑（cmd 不关心），一旦正文含多字节字符，
cmd 按字节偏移读文件就会错位。

`启动程序.bat` 因此是「**UTF-8 无 BOM + `chcp 65001` + CRLF**」三件套。

### 10.10 真机标定第一次尝试暴露的问题（2026-10-10）

用户第一次真机标定，卡在 `collected 0/25`、`x122 两路未同时检测到棋盘`，
并反馈"左摄像头清晰度远远小于右摄像头"。截图显示：左路整幅蒙了一层奶白雾 +
左上角大面积过曝，右路通透锐利；同时 `detect 19 ms/frame (52 fps)` ——
**帧率是健康的**，这一点很关键（见下）。

**(1) 先纠正一个容易查错方向的判断：这不是 USB 带宽问题**

带宽不足的指纹是"**卡**"：帧率掉、残帧（下半幅常量）、驱动降分辨率。
它**不会**让画面变"糊"或蒙雾 —— 图像质量是光学与曝光的事，与传输速率无关。
**判断依据主要是"症状类型"，不是那个 52 fps**（这一点要写清楚，别被它误导）：
界面上的 `detect 19 ms/frame (52 fps)` 量的是**检测计算耗时**（`calibrate_stereo.py`
里 `perf_counter` 只夹在检测那一段），**不是相机采集帧率** —— 它只能说明
"帧在源源不断地进来、处理不是瓶颈"，**证明不了链路速率**。
真正站得住的依据是：**带宽不足不会让画面变糊**（它只会掉帧/降档/下半幅发灰），
而左路那种"整幅蒙雾 + 大面积过曝"是光学与曝光的现象。
§7.2 另有一笔独立账：MJPEG 双路 1080p30 在 USB 2.0 上还有 6–12 倍余量。

不过**结论仍然要实测才能定**，所以下面第 (3) 条加了工具 ——
它直接量"实测采集帧率"与"残帧数"，那才是能定性的指标。

**但它仍然值得"测一次再下结论"**，所以新增了工具（见 (3)），
把"带宽 vs 光学"变成可测量的判据，而不是靠嘴说。

**(2) 标定卡住的真正原因是画面质量，不是门限太严**

用户以为"手抖都不容忍"，但 `x122` 全部落在**第 1 道门限**（两路未同时检测到棋盘），
**根本没走到"停稳"那一道**。所以当务之急是修左路画面，不是放松门限。

不过原实现有个真实缺陷：第 1 道门限只说"两路未同时检测到棋盘"，
**不说是哪一路**。两路质量差很多时，人在窗口前挪半天板子也查不出方向。已修：

- 门限 1 现在会说 `左路未检测到棋盘（右路正常）`；
- 并顺带调用新增的 `diagnose_frame()` 给出画面会诊；
- 标定窗口**右上角新增逐路状态**（`左: 清晰度 210 面积 4.2% 曝光 118`），
  实时就能看出是哪一路、差在哪。

**(3) 新增 `apps/tools/camera_quality.py`：把"糊"和"卡"分开**

逐台量：请求/实际分辨率、实测帧率、**残帧数**、清晰度（Laplacian 方差）、
亮度/过曝/死黑、反差；两路对比后给结论。判据表：

| 现象 | 带宽/链路不足 | 光学/曝光问题 |
| ---- | ------------- | ------------- |
| 实测帧率 | 偏低；两路同开骤降 | 正常 |
| 残帧（下半幅常量） | **会出现** | 不会 |
| 实际分辨率 | 被降档 | 正常 |
| 清晰度 | 正常 | **明显偏低** |
| 过曝 / 动态范围 | 正常 | 可能异常 |

`--together` 额外测"两路同开"，用来暴露共用总线的争抢（单开正常、同开掉速）。
**唯一能定性归因的是交换测试**：把两台的口/线对调，问题跟着相机走 = 相机问题，
留在原口 = 链路问题。工具会把这段说明打出来。

`diagnose_frame()` 的蒙雾判据用的是**动态范围**（p95−p5 < 70）而**不是整幅标准差** ——
画面里有大块纯色（白墙、木桌）会把标准差抬高，用标准差会漏判。
这条在写测试时被当场抓到：第一版用 `std < 6`，合成蒙雾图给的是"无异常"。

**(4) 手持标定：给了"有代价"的放宽，而不是偷偷放水**

`apps/calibrate_stereo.py` 新增 `--stationary-px`（默认仍 3）与 `--relaxed` 预设
（停稳 10px、清晰度 28、更小的板、更贴边），并**明确打印"这是用精度换成功率"**。

**没有把默认值改松**，原因是那条门限承担着真实职责：两台 USB 相机**没有硬件同步**，
"板静止"是用"静态目标在任意时刻看起来都一样"来**替代时间同步**。
放太松 = 两路拍到不同位姿 → R/T 系统性偏，而且**不报错、事后查不出来**。
所以推荐顺序是：① 让板靠住（椅背/纸箱/书立）→ ② 加光提高快门 → ③ 才动门限。

**(5) 新增第 9 个回归测试**

`tests/selftest_camera_quality.py`：用已知答案的合成图钉住
① 会诊判据（正常图不误报、蒙雾/过曝/过暗/全黑各自指对方向）、
② 残帧判定（下半幅常量 → 识别；正常图、纯色图、带噪声暗背景 → **不误判**）、
③ 逐路状态在无观测时不崩。**全合成图，不开任何相机**，几秒跑完。

> 必须先把模块登记进 `sys.modules`，否则 `@dataclass` 解析注解会报

### 10.12 相机改名：两台不再重名（2026-10-18）

**做了什么（用户操作，不是代码改动）**：两台 aoni 相机在系统里改了 FriendlyName，
**名字唯一且自带左右标识**：

| 系统里的名字 | 端口（`InstanceId` 尾段） |
| ------------ | ------------------------- |
| `aoni webcam A25 left`  | `6&31324e2c&0&0000` |
| `aoni webcam A25 right` | `6&4489382&0&0000` |

配套的 `config/cameras.json` 已确认：`left` → `#0`、`right` → `#1`，两条都 `verified=true`。

**这改变了什么（重要）**：

- **`_match_entry()` 硬规则 2 的前提消失了。** 那条规则是"绑定过身份的角色，
  身份/端口对不上时**不许**退回按名字匹配"，理由正是**名字会撞**。
  现在名字唯一 ⇒ 按名字兜底**技术上安全了**。但代码**没改**（本轮只改文档），
  所以现状是：**换 USB 口之后，`check` 仍会报"解析失败"，而不会自动按名字找回**。
- **兜底能力仍在**（`identity → port → name` 的第三级没删），
  只是 `bound=True` 时被跳过。

**✅ 已决定（2026-10-18，用户拍板）：选 A —— 保持现状。**

用户原话：**"还是先保持现状吧，让人来选择很安全"**。
即：**身份/端口对不上就报错，由人跑一次 `identify` 确认，不做自动按名字找回。**

记住这个决定的**理由**（否则下一个人会觉得"名字唯一了还不是能自动？"）：

- 自动兜底省下的是**几十秒的 `identify`**，赌上的是**静默用错相机** ——
  而"用错左右"的后果是**标定的 R/T 全废且画面看不出异常**（§13.8 那条真缺陷）。
  **代价不对称**：省几十秒 vs 废掉整轮标定。
- 名字是**用户可改的自由文本**。今天唯一，不代表明天唯一；
  而程序的正确性不该建立在"用户不会去改那个字段"上。
- **报错本身是有价值的产物**：它明确告诉你"这台不在线了"，并给出下一步。
  静默自动恢复会把这条信息吞掉。

**所以：`settings.name_fallback` 这个配置项不要加。** 将来若有人提这个需求，
先回到本节读一遍代价不对称那一条。

| 选项 | 好处 | 代价 / 风险 | 结论 |
| ---- | ---- | ----------- | ---- |
| **A. 保持现状（身份优先，不按名字兜底）** | 换口必报错，**绝不静默用错相机** | 换口后要跑一次 `identify`（几十秒） | **✅ 已采用** |
| B. 名字唯一时允许按名字兜底 | 换口后自动恢复，不用人工确认 | 用户**再改名**（或换一台同名相机）后，兜底会**静默绑错** | ❌ 不做 |
| C. 名字里解析左右（`…left` / `…right` → 角色） | 连 `identify` 都省了 | 把**人的命名习惯**变成**程序契约**；名字打错就是静默错绑 | ❌ 明确不推荐 |

> 我原来的倾向是 B（带"名字唯一"守卫）。用户选 A **比我的建议更稳** ——
> 我当时按"省不省事"权衡，而 A 是按"错了要付什么代价"权衡。
> **这个选择更好，记录在此，不是妥协。**

**另一个必须一起看的事实**：`right` 那台的**端口变了、索引也变了**：

| | 早期实测 | 2026-10-15 | 2026-10-18（现在） |
| --- | --- | --- | --- |
| `left` | `#1` / `6&31324e2c` | `#1` / `6&31324e2c` | **`#0`** / `6&31324e2c` |
| `right` | `#0` / `6&212acdc8` | `#1` / `7&24e47704` | **`#1`** / `6&4489382` |

即：**同一台外接相机，光换 USB 口就能换出三个不同的端口串**（`6&212acdc8` →
`7&24e47704` → `6&4489382`），索引也跟着跳。**再次印证"索引与端口都会漂，
只有名字与 VID/PID 稳定"。**（`left` 的端口一直没变，是那台一直插在同一个口上。）

- `camera_quality.py` 里"本机两台 aoni 就在同一条 2.0 总线上"、"注意 A25 是 USB 2.0" → 泛称；
- `cameras.py` 的 `pin` 示例**从实际设备列表动态生成**（`_pin_example_lines()`），
  不再写死型号名；
- `--help` 里的 `name:aoni` → `name:<名字片段>`。

**仍未做的两处（有意）**：`camera_registry.py` 的 `DEFAULT_SETTINGS.avoid_names`
里的 `Integrated Camera` / `Integrated IR Camera` 仍是默认值 —— 那是"**默认判据**"，
本来就该有出厂值，且用户可覆盖；注释里举 `aoni webcam A25` 属**历史记录**，不改。

### 10.13 🔴 我引入的生产级 bug："aoni 被认成 Integrated"（2026-10-18）

**用户报告**：

> 运行相机管理选择的时候，把我的 aoni 相机识别为了 aoni 相机和 integrated 相机，
> 也就是识别了两次

**这确实是我改坏的，不是环境问题。** 完整归因：

```
表象：identify 里同一台/两台相机被贴上错名字（aoni 显示成 Integrated）
  ↑
直接原因：_open_preview 给**每个索引单独挑后端**（先 MSMF，不成换 DSHOW）
  ↑
机制原因：#N 的**标签来自 PnP 枚举**，而 cv2.VideoCapture(N, backend) 用的是
          **后端自己的枚举**。只要有一个索引回退到 DSHOW，标签就与画面脱钩
  ↑
根因：我删掉了"必须固定 MSMF"这条不变量，并给出了一个**错误的理由**
      ——「画面就在用户眼前，标签与画面是同一路流，真要错位人一眼能看出来」。
      **这条理由是错的**：两台 aoni **长得一模一样**，人看画面根本分不出哪台是哪台；
      而 DSHOW 错位后，标签指向的那台**根本没出现在画面上**，无从目视核对。
```

**实测证据**（`outputs/_handoff_read/probe_index_map.py`，2026-10-18）：

| 索引 | PnP 标签 | MSMF | DSHOW |
| ---- | -------- | ---- | ----- |
| #0 | aoni **left** | 有图 std 65 | 有图 std 57 |
| #1 | aoni **right** | 有图 std 56 | **纯黑 std 0**（= 被遮住的内置） |
| #2 | Integrated Camera | 纯黑 std 1（内置被遮住） | **有图 std 64**（= aoni） |
| #3 | Integrated IR | 打不开 | 打不开 |

**MSMF 与 PnP 一致；DSHOW 整体错位。** 所以回退一次，用户就会看到
"aoni 被显示成 Integrated Camera"、同一台被认成两台。

**修法（三条）**：

1. **`identify` 整场只用一个后端**（`_open_preview(index, backend)` 不再自己挑）。
   打不开就如实说"打不开"并跳过，**绝不换后端**。默认 `INDEX_BACKEND`（MSMF）；
   `--backend dshow` 仍可用，但会打**醒目警告**并建议改用 `pin`。
2. **`doctor` 同样锁一个后端**。它原来也用 `pick_backend_for_device` 逐索引挑 ——
   那意味着"实测 left 那台"其实测的是**另一台相机**，结论整个失真。
3. **双目路径加守卫**（更危险的一处，见下）：`PairSource.from_args` 里，
   只要索引是**按角色名/auto 解析**出来的（= PnP 位次），
   `--backend dshow/auto` 会被**拒绝**或**强制锁成 MSMF**：
   ```
   `--backend dshow` 与「按角色名解析索引」**不能一起用**。
   原因：角色名解析出的是 PnP 位次，而各后端的编号空间不同。
   ```
   想用 DSHOW 必须**显式给数字编号**（`--left 0 --right 2 --backend dshow`），
   索引就落在 DSHOW 自己的编号空间里，由用户自己确认。

**为什么双目路径那条更危险**：`identify` 至少**看得见画面**；而标定是
`right` 角色静默拿到被遮住的内置相机，**两路都报 1920x1080、界面上毫无异常**，
等收不到棋盘才会发现 —— 而更坏的情况是**把笔记本内置相机当成右目标定成功**，
得到一份"看起来正常但完全错"的外参。

**防回归**：

- `selftest_camera_registry.py` **第 16 节**：AST 查"没有 `pick_backend_for_device` 调用"、
  行为级断言"传什么后端就用什么后端"、"打不开时**只尝试 1 次**"、
  `identify --backend` 默认 `None`。
- `selftest_pair_source.py`：角色名 + `dshow` → **必须拒绝**；角色名 + auto → **锁 MSMF**。
- `selftest_mutation_guards.py`：`backend-guard`（关掉守卫 → 报红）、
  `open-preview-shape`（形状不一致 → 报红）。
  **旧的 `auto-backend` 变异已删除** —— 它的语义被这次修复**反转**了
  （现在"锁死 MSMF"才是对的）。

### 10.14 🔴 "命名为 right 的相机，画面上是 left"（2026-10-18 第二次纠正）

**用户提问**：

> 你的相机管理的视频画面的内容是不是根本不是通过相机的名字来设置的?
> 为什么我的命名为 right 的相机却在画面上是 left?

**答案是：对，画面只按编号打开，名字根本不参与。** 而这条比 §10.13 更根本 ——
§10.13 修的是"后端之间的错位"，这一条是"**编号与设备列表的对应关系本身无法证明**"。

**证据链的缺口（这是我第二次犯同一类错）**：

| 我实际验证过的 | 结论 |
| -------------- | ---- |
| aoni vs Integrated（MSMF `#2` 黑 = PnP `#2` 内置） | 成立 |
| **两台一模一样的 aoni，谁在 `#0`、谁在 `#1`** | **从未验证** |

我拿"`#2` 是内置"外推到"整个顺序都对"——**用一条弱证据支撑了一个强结论**。
而两台 aoni **同 VID/PID、同分辨率、同画面特征**，在软件层面**不可区分**，
所以这个顺序**原理上无法由 `cv2` 证明**。

**后果**：`identify` 窗口上 `#N <名字>` 这行标签**永远是猜测**，
但原来写法像是事实。用户按它按键，就会把角色绑到反的那台。

**修法（诚实优先，不假装能证明）**：

1. **标签自认是推测**：`_preview_label()` 输出
   `#0  推测:aoni webcam A25 left  端口 6&31324e2c&0&0000`，
   `identify` 开头也明说"名字是猜的，请以画面为准"。
2. **给出真正可靠的路径**：`pin` 按**名字**绑身份 ——
   **完全不开相机、不碰编号**，因此不可能左右颠倒：
   ```powershell
   python apps/tools/cameras.py pin left  name:"aoni webcam A25 left"
   python apps/tools/cameras.py pin right name:"aoni webcam A25 right"
   ```
   实测支持**带空格的全名**，也支持 `name:left` 这种唯一子串。
3. **判据**：`selftest_camera_registry.py` 第 17 节断言标签必须含「推测」。

**这一节要记住的两件事**：

- **"名字"不是选择器，是标签。** 用户给相机改名，改的是**系统里那台设备的
  FriendlyName**，不会改变 `cv2.VideoCapture(index)` 的行为。名字能帮我们
  **认设备身份**（`pin name:`），但不能帮我们**决定打开哪一台**。
- **"能从现象推出顺序"是幻觉。** 一个可区分点（内置相机是黑的）只能证明
  "那一台"对齐，**不能证明其余同型号之间的相对顺序**。
  这类"用弱证据外推强结论"正是本项目最贵的教训（§9：`s²` 被合成场景盖住）。
  以后遇到"同型号设备排序"，**要么承认不可知，要么让用户目视/按名字指定**。

### 10.15 相机管理：同一件事改了三次，最终定案（2026-10-18）

这一天围绕"设备管理/识别"改了 **6 次**，其中**三次是修 A 引出 B**，
每次都被用户当场抓到。完整记录如下 —— 比结论更值钱的是**为什么每次都错**。

| 次序 | 我的改动 | 用户看到 | 机制 |
| ---- | -------- | -------- | ---- |
| 1 | `af8bb30` 按索引**回退**后端（"真能出图就用"） | **aoni 被标成 Integrated** | DSHOW 编号与 PnP 错位（DSHOW #1=内置、#2=aoni） |
| 2 | `33b7164` **删掉**回退（"标签必须可信"） | **只剩一台** | MSMF 打不开的那台直接消失 |
| 3 | `e802a8f` 回退**只为显示、禁止绑定** | **同一台出现两次，另一台不见** | `DSHOW #2` 与 `MSMF #0` 可能是同一台 |
| 4 | `266af26` 定案：**同一后端内开一个编号，绝不换** | 正常 | 打不开就点名报出，不隐藏 |

**最终设计（不要再改回去）**：

```
_open_preview(index, backend)  # 只试这一个后端；失败返回 (None, None)
```

**为什么"折中"也不行**：PnP 与各后端的编号是**互不相容的三套命名空间**。

诊断（看见了什么）与决策（这是哪台）必须分层，但**分层不等于可以混用编号**。

**同一轮里另外两个真修**（都不是"相机坏"）：

| 现象 | 根因 | 修法 |
| ---- | ---- | ---- |
| 某台"打开成功但一帧都不给" | 我们**请求 640×480**，而这台只认 **1920×1080** | 预览/探测改请求**原生**分辨率 |
| 首帧等 3 s 就判死 | 该台**首帧要 ~23 s** | 新增 `first_frame_timeout_s`；预览/探测给 30 s |
| 预览明显卡顿 | 每帧 `imshow` 一张 **1080p（6 MB）** | 显示前降到 **960 宽**（采集实测 27.6 fps、降采样 0.59 ms/帧） |

- `probe` —— 逐**后端** × 逐**编号**真开一次，报「✅ 有图 / ⚠ 近乎纯黑 / ✘ 打不开」，

- `doctor` —— 回答一句话："现在能不能跑双目"（枚举 → 角色解析 → 逐台实测 → 两路一致性）。

并删除冗余的『检查相机映射』按钮（它在每次标定/复检前已**自动执行并拦截**）。

### 10.16 反复出现的错误模式（跨事件归纳，**这一节最重要**）

以下七条都是**本轮真实发生过的**，不是假设。每条给出证据与之后的规矩。

| # | 模式 | 本轮实例 | 规矩 |
| - | ---- | -------- | ---- |
| 1 | **用弱证据撑强结论** | ①`位移换算 s²` 被合成场景盖住；②从"内置相机是黑的"外推出"整个枚举顺序都对"；③从 `CameraConfig.fx=0` 外推 `CameraModel` 会返回 0 米（实测是 hfov 估算，**已撤回**） | 一个可区分点只能证明**那一个点**。补证据或降结论强度，**不许外推** |
| 2 | **修 A 引出 B** | 相机回退三连（贴错→消失→重复） | 改前先写"这个动作还承担了什么"；**一个动作只承担一件事** |
| 3 | **"打开成功"≠"能用"** | 640×480 下"能打开但一帧不给"；3 s 首帧判死 | 判据必须是**真出图**（非全黑 + 有帧），并且**先怀疑请求参数，再怀疑设备** |
| 4 | **判据跟不上契约** | 改了行为但 `selftest_camera_registry` 第 16 节仍断言旧语义；`selftest_mutation_guards` 锚点在重构后失效 | 改行为**必须同时改判据**；变异"锚点命中 0 处"要当成**测试红**处理 |
| 5 | **拆函数留下旧尾巴** | 拆 `_open_preview`/`_try_open` 时旧 `except` 留在新函数里 → `NameError: used_name` | 拆函数**整段重读**，不能只替换上半截 |
| 6 | **假警报训练人忽略真警报** | `baseline_side()` 写反 → 每台正常装置都报"左右可能接反"（§10.13） | 诊断的**误报率**和漏报率同等重要；报警必须可信 |
| 7 | **文档抄数值会过期** | `AGENTS.md`/`用户手册` 抄了 65.81/0.743；磁盘实际 67.98/0.939 | 数字**只写在有权威出口的地方**（`config/*.json`）；正文引用要注明"以文件为准" |

**改完必答三问**（建议写进每次提交说明）：

1. **证据是什么？** —— 命令 + 输出 + 退出码；没有就不算验证过。
2. **最坏情况它会输出什么？** —— 不是"能不能满足目标"，而是"错的时候错成什么样"。
3. **判据在哪？** —— 能不能让它在**下次**变红？红不了就等于没修。

## 11. 真机标定攻坚（2026-10-10 第二轮）

本节记录**第一次真机标定之后**的排查与修复。核心成果：
把三处**静默失败**变成可见/可测/可拦截，并**证伪了一个原本以为的根因**。

### 11.1 相机编号与后端的错配（**踩了三次，根因同一个**）

**现象**：笔记本内置相机被反复绑成左/右目。

**根因**（实测坐实）：

```
camera_registry.list_devices() 的编号  ← Windows PnP 枚举
cv2.VideoCapture(index, backend)       ← 各后端自己的枚举
```

**两者不是同一套。** 本机同一时刻实测（用户盖住内置相机 → 它在哪一路全黑就是哪一路）：

| | 0 | 1 | 2 | 3 |
| --- | --- | --- | --- | --- |
| **PnP** | aoni | aoni | **内置(黑)** | 内置红外 |
| **DSHOW** | aoni | **内置(黑)** | aoni | 打不开 |
| **MSMF** | aoni | aoni | **内置(黑)** | 打不开 |

**MSMF 与 PnP 一致，DSHOW 错位。** 所以拿 PnP 编号去让 DSHOW 开，就开到别的相机。

> ⚠️ **上表是"某一时刻的样本"，不要当常量用。** 2026-10-15 实测同机：
> 同一批设备里 **DSHOW 下 `#0` 也变成纯黑**（而上表那次 `#0` 是正常的 aoni）。
> 也就是说**三套枚举的错位关系本身还会浮动** —— 又一次印证
> **位次不可作依据**（坑 37 就是在这个背景下误判的）。
> 判"哪台是哪台"唯一可靠的办法仍是：**名字 + 盖住镜头看哪台变黑**。

**三次踩坑的不同入口**：
1. 双目标定：`right`(PnP #1) 用 DSHOW 开 → 开到内置 → 画面全黑，**看起来像相机坏了**；
2. `cameras.py identify`：预览用 auto 后端、标签写 PnP 名字 → **用户看着 A 按 r，配置记到 B**；
3. 自动挑相机 / 画质会诊：`probe_index()` 同样错配 → **评的是另一台相机**。

**修复**：答案收敛到 `sphere_tracker/sources.py` 的 `INDEX_BACKEND`（一处，带完整实测表），
**六处引用它**：`camera_registry._default_opener`、`cameras.py`、`camera_quality.py`、
`list_cameras.py`、`run_realtime.py`、`stereo/pair_source.py`。

**防复发**：`tests/selftest_config_wiring.py` 新增**静态检查** ——
任何 `CameraSource(index=...)` 必须显式给 `backend=`（只有 `**kwargs` 透传豁免）。
**已反向自证**：去掉一处 → 报红并指到具体行；还原 → 通过。

> **教训**：同一个假设写在两处，就会漂移成两种行为。**不变量要留在拥有数据的模块里。**

### 11.2 标定通路第一次跑通（日志 + 布局 + 建议）

| 项 | 内容 |
| -- | ---- |
| **日志** | `apps/_common.setup_logging()` → `outputs/logs/<tag>_<时间戳>.log`；文件 DEBUG、终端 INFO、毫秒时间戳。库层只 `getLogger`，装 handler 是 app 的事 |
| **布局** | 所有状态文字移进画面**下方独立条带**（原来逐路状态压在右画面上、拒绝统计被窗口下沿**截断** —— 被截掉的恰是"为什么收不满"） |
| **自适应** | 先算文字高度、图像用剩余空间；屏幕尺寸用 `GetSystemMetrics` 取 |
| **建议** | `next_step_hint()` 按占比最高的门槛给可执行动作 |

**顺带修的真 bug**：`self.rejected` 用**完整原因字符串**当 key，而原因里嵌着每帧不同的数字
（`左图模糊(清晰度 42)` 与 `(清晰度 51)` 是两个 key）→ **统计被打散成几百个一次性条目**，
"最常见原因"和百分比全是错的。新增 `reject_category()` 归一化。

### 11.3 标定结果不可用 —— 已排除"8 对太少"

真机 8 对（`outputs/logs/calibrate_*.log`）：

```
整体重投影 RMS: 46.4040 px
左目重投影 RMS: 1.3784 px      ← 单目正常
右目重投影 RMS: 0.9386 px      ← 单目正常
极线误差 RMS  : 15978.5150 px  ← 比图像对角线(2203px)大 7 倍
判定          : 不可用
```

**用项目自带合成装置做对照**（`make_poses` / `render_view`）：

| 合成场景 | 整体 RMS | 极线 RMS | 基线误差 | 判定 |
| -------- | -------- | -------- | -------- | ---- |
| 8 个覆盖良好的姿态 | **0.4154 px** | 0.3209 px | 1.5% | 可用 |
| 8 个姿态挤在一起 | **0.1334 px** | 0.2738 px | 12.3% | 可用 |

**结论（已证）**：**8 对本身够用**，甚至优于 `ok_rms=0.80` 门槛；姿态退化只让基线偏 12%。

**所以 46 px / 15978 px 另有原因。** "单目各自正常、双目爆炸"这个签名
指向**左右角点顺序不一致**：每个相机内部自洽（单目标定正常），
但两路数组同名下标不是同一个物理角点 → 错配点对 → R/T 垃圾 → P1/P2 垃圾
→ `undistortPoints` 把点映射到图像外。

> ⚠️ **这是最高嫌疑，不是结论。** 验证方案见
> `planbooks/2026-10-10_标定可视化与失败诊断.md` §2：
> 跑一次 `--save-pairs`，比对两路单应隐含的相对旋转（真实双目应只有几度）。

### 11.4 单目实时 1.1 fps —— 瓶颈已实测定位

| 检测器 | 合成图 1080p | **真机图 1080p** | 倍率 |
| ------ | ------------ | ---------------- | ---- |
| `color` | 18.3 ms | 9.3 ms | — |
| **`hough`** | 81.3 ms | **1751.6 ms** | **21×** |
| `motion` | 15.9 ms | 16.3 ms | — |
| `fusion` | 121.3 ms | **3372.4 ms** | **28×** |
| 整条 pipeline | **135.0 ms** | **2675.4 ms** | **20×** |

**边缘密度**决定；合成图背景干净、实验室画面杂乱，1080p 下边缘数量差几个量级。
**相机自运动估计不是瓶颈**（1080p 实测 2.0 ms）。

| 分辨率 | hough | pipeline |
| ------ | ----- | -------- |
| 1920×1080 | 1706 ms | 2020 ms |
| 1280×720 | 814 ms | 533 ms |
| 960×540 | 216 ms | 215 ms |
| 640×360 | 64 ms | 68 ms |

**即使 640×360，hough 的 64 ms 仍是主要开销** —— 光降分辨率治不彻底，计划见

### 12.0 ⚠️ 当前约束：**外接摄像头没有接上**（用户 2026-10-10 明确说明）

这条**影响你该怎么做**，不只是"进度慢一点"：

### 12.1 已经落地的三项基础设施

| 项 | 落点 | 一句话 |
| -- | ---- | ------ |
| **角点出身** | `calib/board.py`、`calib/capture.py` | `BoardObservation.detector` 记 `"sb"`/`"classic"`；回退**必须显式**（`allow_classic_fallback`，默认 False）；**禁止一对之内混用**（两道守卫） |
| **运行健康度** | `sphere_tracker/stats.py` | `Health`：`capture_fps` / `loop_fps` / `detect_ms` 三个口径分得开，另有 `frame_age_ms` / `dropped` / `skew_ms`。**纯数据**（无 IO、无本项目依赖）。**目前还没有调用方** |
| **测试运行器与落差自查** | `apps/run_tests.py`、`apps/tools/` | 见 §12.3 |

**为什么"角点出身"是硬门禁而不是提醒**（这是本轮最值钱的一条）：

`findChessboardCornersSB` 与经典 `findChessboardCorners` 返回的**角点顺序恰好整体反序**
（实测：直接对应 RMS **323.112 px**，整份反序 **0.020 px**；分类正是 8x5 点阵的 `rot180`）。

- **单目标定对它免疫**（反序仍是一组自洽对应，RMS -0.0066 vs 0.0704 px）→ **每一路各自看起来都正常**；
- **双目标定不免疫**：一路 SB、一路经典 → 同名下标不是同一物理角点 → 合成复现整体 RMS 21~42 px、
  极线误差上万像素、**基线被吹到真值的 8~15 倍**；
- **它不会报错**。真机上只能靠事后猜 —— 所以才要在收帧时当场拦住。

**另一条同样重要的事实**：`calib/stereo_calib.py:272` 的**基线核对逻辑本来就有**
（`expected_baseline_mm` + `baseline_tolerance=20%`），但该参数**默认 `None`**，
所以真机那次的警告只有 2 条、**没有基线那条**。给个锚就立刻报出偏差（实测）。
→ **护栏一直在，只是从没被启用。**

### 12.2 真机标定的证据比原先以为的多（原判断已更正）

**原说法"数据已不可复现"不准确。** `outputs/logs/` 里两份日志**完整还在**
（`calibrate_20261010_162029.log` 与 `..._160739.log`）：

- `162029`：`共处理 1362 帧：收下 8 对，拒收 1354 帧`；六类拒收分布
  （**58.3% 是「棋盘还在移动」**、21.8% 两路未检测到）；全套标定指标**含基线 199.67 mm**；判定不可用、**未保存**。
- `160739`：更早一次**未跑完的 25 对档**（1905 帧、收到 8/25 被中止），拒收同样由「棋盘还在移动」主导（652 次）。

**真正缺的只有两样**：图像（当时没跑 `--save-pairs`）与逐帧的检测器出身。
→ 所以紧接着该做的是 **`planbooks/...架构接缝...` 的 P0-4**（会话落盘），
而不是"再举一次板"。

**为什么"板还在移动"占 58% 值得单独记一笔**：这两台相机**没有硬件同步**，
"板静止"是**用静态目标替代时间同步**的唯一手段（§10.10(4)）。
若 46 px 的根因不在检测器混用，这里就是第一嫌疑 —— 它指向**时间层**，不是标定身份层。

**实测：两台相机的镜头中心间距 = 65 mm（下 60 / 上 70）**，而标定算出 199.67 mm。
→ 基线**确实被吹飞**（方向支持"对应错配"），但只有 **3.07 倍**，
而纯错配在同样尺度上应给 **8~15 倍**（合成实测）——
**混合检测器单独解释不了这个幅度**，另有叠加因素。**这条仍是开放问题。**

**踩到的真缺陷（都是"先写测试、测试崩了，才发现是库层的锅"）**

1. **`select_cameras` 不接 probe 异常** —— 驱动抽风会让**整次挑选崩掉**，
   用户看到 traceback 而不是"这台不行，试下一台"。
2. **失败的试开被当成"挑到了"** —— 我加异常处理后，把 `_failed_probe()` 的结果
   `append` 进了 `picked`，于是 `ok=False` 的 probe 也算一台相机：

3. **`Selection.ok` 只算"有没有"、不算"够不够"** —— `need=2` 只挑到 1 台时返回 True，

4. **两套判定对同一台机器结论相反** —— `camera_availability` 自己重实现了"合格"判据，

   已改成**委托**：**同一个事实只留一个实现**。

> 第 4 条特别值得记：**我自己犯了正在修的那个毛病**（同一个量两处各算一遍）。
> 修法：`camera_availability` 只负责"把失败翻译成人话 + 给出下一步"，
> "合不合格"完全交给 `select_cameras`。

| 页签 | 放什么 | 判据 |
| ---- | ------ | ---- |
| **基本设置** | 目标/最少对数、板参数（内角点列·行、方格边长）、分辨率、帧率 | **改错就白做**的那几项 |
| **高级设置** | 停稳上限、清晰度下限、放宽模式、**预期基线**、存图像对、验证图 | **拿精度换成功率**的开关 |

### 13.2 标定判定改成四级 + 报告里给出板占画面比例

**用户的反馈**：「程序报告我说数据不可用，我不是很能接受」——**他不接受是对的**。

`outputs/logs/calibrate_20261013_225549.log`（那次 25 对的真机标定）：

| 指标 | 这次 | 门限 | 上一次（10-10） |

| **基线** | **67.28 mm** | 实测 ~65（**只差 3.5%**） | ~~199.67 mm~~（3.07 倍） |

| 极线 RMS | 0.8071 px | good≤0.25 / ok≤0.60 | 15978 |
| 使用/输入 | 22/25（剔 3 对） | — | 8 对 |

**基线核对是通过的**，说明方格尺寸与内外参都对；只是精度指标刚过 ok 线。
而 `ok_rms` 本来就是"**够用**"的意思，不是"超过就废"。

> ⚠️ **证据挂错了版本（2026-10-14 二次复核更正）** —— 上面那份日志**不是四级判定的证据**。
>
> | 事实 | 证据 |
> | ---- | ---- |
> | `calibrate_20261013_225549.log` 的末行是 `判定: 不可用 —— 请重拍标定图像（换更多角度、保证清晰、铺满画面）` + `WARNING 标定未通过质量判定，未保存` | 日志文件本身 |
> | 那句**逐字**是**旧的三分支**文案 | `git show 43a5957:calib/stereo_calib.py`（10-13 23:06）里还是 `res.ok = False` 的二值判定，**没有** `grade` 字段 |
> | 四级判定是**晚 10 小时 26 分**才进来的 | `bfa95ca`（10-14 09:21:49）`feat(calib): grade results in four tiers…` |
>
> 结论：那次标定**当时确实被判不可用、也确实没保存**（`config/` 下至今**没有任何 `stereo_calibration.*`**，已实测）——**程序没错，文档把因果讲反了**。
> 这条反馈的真正价值是"**用一次真实数据说明二值判定不合理**"，而四级判定的**判据**落在
> `tests/selftest_calib_facts.py::test_board_area_and_tiered_verdict`（把噪声抬到 0.60 px 造出
> RMS 0.825 / 极线 0.882，**正是真机那次的形状** 0.91 / 0.81，断言判为「勉强可用」且 `ok=True`）。
> **教训**：`bfa95ca` 之后**从未在真机上重跑过标定**，所以这一节当时只能借旧日志讲故事 ——
> 而"借"的时候没有核对**那份日志是哪个版本的代码产出的**。日志带时间戳，提交也带时间戳，**两边一比就能发现**。

**改法**：

1. **四级判定** —— 只有**物理上错了**才判不可用：

   | 分级 | 条件 | 保存 |
   | ---- | ---- | ---- |
   | 优秀 | RMS≤0.35 且 极线≤0.25 | ✓ |
   | 可用 | RMS≤0.80 且 极线≤0.60 | ✓ |
   | **勉强可用** | 精度过线但**基线没错** | **✓ 保存** |
   | 不可用 | 基线对不上 / 有效对<8 / 求解发散 | ✗ |

2. **板占画面比例进报告**（`板占画面 : 1.1%（左 1.1% / 右 1.2%；建议 10%~30%）`）
   —— 这个数字**一直是算得出来的**（每次拒收都在算"棋盘太小(1.2%)"），
   只是**没有出口**。又一个"没有出口的字段"。

3. **采集时实时显示**（窗口底栏：`板只占画面 1.2% —— 太远了，请靠近到 10% 以上`）
   —— 答案在**板还在手里**的时候给出，而不是收完 25 对才说。

4. **建议可执行**：把"换更多角度、保证清晰、铺满画面"换成
   `板离得太远：只占画面 1.1%，建议靠近到 10%~30%`。

**那次标定的真实原因**（拒收分布 3902 条）：

```
45.5%  棋盘还在移动          ← 最大头
11.8%  两路都未检测到棋盘
11.2%  右路未检测到棋盘
 7.9%  与已收位姿太接近
 7.6%  该区域已收够
 6.8%  左图棋盘太小(1.2%)     ← ★ 精度偏高的机制原因
 0.1%  两路角点出身不同（左 sb / 右 classic）  ← 硬门禁拦下 4 帧（守卫生效）
```

**注意**：那次的两路分辨率是**错配**的（1280x720 vs 1920x1080，见 §13.8），
所以那份 R/T **不能用** —— 不仅仅是精度不够。
而且**它也没有被保存**（当时还是二值判定，见本节开头的"证据挂错了版本"）——
所以本节的"应当保存"是**事后按新规则重判**的说法，**不要读成"config 里有一份能用"**：
`config/` 下至今没有任何 `stereo_calibration.*`（已实测）。

### 13.3 GUI 可滚动 + 换行宽度动态计算

**两个真缺陷**：

1. **提示文字不换行** → 第 1 步那张卡片的自然宽度 **1941 px**（整窗 1973 px），
   而屏幕只有 1600 —— 新加的参数区**把原有控件全挤到窗口外**。
2. **换行宽度写死 820** → 按"窗口 900"估的；窗口改成 980 之后卡片自宽 873
   而视口 966，**文字在卡片那一列里被切掉**，右边空一大片。

**现在**：换行宽度由 `_reflow()` **按视口宽度动态算**（每次 `<Configure>` 重设）。
实测默认窗口下**页面宽 964 / 视口 966**（差 2 px）。

**另外发现并修掉的**：**手算 grid 行号**。参数辅助函数内部占 `row*2` 与 `row*2+1`
**两行**，而调用方传 1、2、3… 并**另手工放**复选框/分组标题 —— 手算的行号正好落在
已被占用的行上，**文字与输入框互相盖住**（用户看到的"高级设置里都是被遮挡的文字"）。
**Tk 不会报"两个控件在同一格"**，它就直接画在一起。

根因不是那几个写错的行号，是**"手算行号"这种做法**。现在每个容器一个游标，
辅助函数自己取下一行，调用方不传行号。

### 13.4 实时检测终于有日志了

**改之前**：`apps/run_realtime.py` **一份日志都不落盘**（其它 app 都调了 `setup_logging`），
只有终端输出，**进程一退全没了**。而"卡顿 / 丢帧 / 相机掉线"恰恰是**过后才想查**的问题。

**现在** `outputs/logs/realtime_*.log` 里有：

| 内容 | 级别 | 为什么 |
| ---- | ---- | ------ |
| 环境（Python / OpenCV / 平台） | INFO | 同一问题在不同 OpenCV 版本上原因可能不同 |
| 相机模式 / 检测方法 / 显示宽度 | INFO | 这次到底用什么参数跑的 |
| **每 5 秒一行健康度** | INFO | 定位卡顿的核心证据 |
| **逐帧检测与追踪明细** | DEBUG | 「球在第几帧丢的」「丢那一下耗时是不是飙了」 |
| **用户按的每个键** | INFO | 复现操作序列 |
| 结束时的完整快照（JSON） | INFO | 事后画曲线 / 比对两次运行 |

健康度那一行长这样：

```
健康度 cap 31.6  loop 85.1  detect 7.9 ms  age 1.4 ms  drop 2
```

**`cap` 与 `loop` 分开是"能诊断"和"只感觉到卡"的分界线**：旧版只有一个裸 `FPS`，
"相机慢"和"我们慢"长得一模一样。掉帧超 25% 还会**额外写一条 warning 指出可能原因**。

**每个任务也单独落盘**：`outputs/logs/task<NN>_<时间>_<标题>.log`
（命令行 + PID + 全部输出 + 退出码 + 耗时），任务管理器里有"打开日志文件"按钮。

### 13.5 帧率：三个独立的瓶颈，都是实测出来的

**① 显示**：`cv2.imshow` 把 1920x1080 缩进窗口要 **17.74 ms/帧**，
而先把图缩到 960x540 再显示只要 **1.84 ms**（便宜 9.6 倍）——
**每秒最多 56 帧是花在缩放上**的，而这件事我们自己做只要 0.55 ms。

现在 `render(display_width=960)`：**先缩图、再在最终画布上画叠加**。
实测 20 秒对照：`loop 65.2 fps`（全尺寸）→ **78.5 fps**（960）。

**② 检测方法**：实测（1920x1080）

| 方法 | 简单合成图 | **真实纹理（书架那样）** |
| ---- | ---------- | ------------------------ |
| `color` | 17.7 ms → 56 fps | **17.8 ms → 56 fps** |
| `motion` | 18.5 ms | 15.5 ms |
| `hough` | 132 ms | **4384.9 ms → 0.2 fps** |
| `fusion` | 181 ms | **3740.5 ms → 0.3 fps** |

**默认已从 `fusion` 改为 `color`**。代价写进了代码注释：`color` 更容易被**同色干扰物**骗到，
三条补救按代价排序（换回 fusion / 调门限 / 换颜色预设）。

> ⚠️ **"合成图上测得挺快"完全没有参考价值** —— `hough` 在同样的帧上，
> 纯色底只要 132 ms、真实纹理要 4384 ms（33 倍）。`HoughCircles` 先做 Canny，
> **纹理一多边缘就爆炸**。这是本项目的老教训（见 §9 的 `s²`），这次又踩一次。

**③ hough 的搜索半径**：原来用 `max_radius=200`（= 直径 400px 的球）搜索 **192 种半径**。
给 hough 一个**独立**上限 80（不动物理约束 `max_radius`，color 与几何校验还要用）：

```
hough   8557.8 ms → 480.6 ms   （18 倍）
fusion  7524.6 ms → 418.6 ms   （18 倍）
```

**④ `--detect-width`**：让检测跑在缩小的图上，坐标自动换算回原图。
实测误差 **1~2 px**（960 / 640 两种宽度，位置与半径都对）。

> **坐标换算必须有测试**：半径差一个倍率，**三维深度就差一个倍率**
> （`camera.depth_from_radius` 直接吃半径）。

**⑤ 我引入又修掉的回归：文字变糊。**
第一版把 `display_width` 折进同一个 `scale`，于是**先 resize、再用原尺寸字号画 HUD** ——
`cv2.putText` 在 1920 的画布上写完字，整张图（连字一起）被压到 960，**字就糊了**。

量化证据（HUD 笔画像素）：

| | 纯白笔画占比 | 最亮像素 |
| -- | ------------ | -------- |
| **先缩图再画字（修好后）** | **3.0%** | **255** |
| 先画字再缩图（糊的那版） | 0.1% | 245 |

旧路径**一个纯白像素都没有** —— 每个笔画都被重采样糊成灰边。

### 13.6 任务管理器（能中断跑飞的程序）

**改之前**：只有 `self.proc` 一个句柄 ——
**一次只能跑一个**程序，而且**没有任何中断手段**。程序卡住时用户只能关启动器窗口，
**而关窗口不杀子进程**：相机仍被占着，下一次运行打不开相机，**而用户不知道为什么**。

**现在**：`Task` 对象（id / pid / 启动时刻 / 退出码 / 停止原因），**允许多个同时跑**；
卡片里有中断 / 强制结束 / 全部中断 / 查看输出 / 打开日志 / 清理已结束。

**两个设计取舍**：

1. **先优雅、3 秒不退再强杀** —— `CREATE_NEW_PROCESS_GROUP` + `CTRL_BREAK_EVENT`
   让程序自己走退出流程（正在写标定结果的程序来得及收尾）。
   实测退出码 `3221225786` = `0xC000013A`，**证明这条路真的生效**。
2. **停任务要杀整棵进程树** —— `terminate()` **只杀直接子进程**；
   我们的子进程是 python，它自己还有子进程。父进程死了子进程活着，**相机就还占着**。
   停完补一刀 `taskkill /T /F` 并报出杀了几个。

### 13.7 所有视频窗口都有全屏

**改之前**：`run_realtime` / `run_video` / `calibrate_stereo` / `check_stereo_setup`
**根本没建窗口** —— `cv2.imshow` 自动建的是 `WINDOW_AUTOSIZE`（尺寸等于图片、
**用户拖不动**）。显示宽度降到 960 之后窗口就只有 960x540，在 3200x2000 的屏上只占一小块。

**现在** 7 个窗口统一走 `apps/_window.py`：

| 键 | 作用 |
| -- | ---- |
| `f` / F11 | 切换全屏 |
| **`Esc`** | **全屏时 = 退出全屏**；不在全屏时才轮到程序自己处理 |

> `Esc` 这条优先级是**必须的**：好几个程序把 Esc 当"退出程序"，
> 不这样安排的话**全屏之后一按 Esc 就把程序关了**。

**两个坑**：

1. **`cv2.WINDOW_FULLSCREEN == cv2.WINDOW_AUTOSIZE == 1`**（本构建实测）——
   所以 `namedWindow(name, WINDOW_FULLSCREEN)` **得不到全屏窗口**，
   它等价于 AUTOSIZE。全屏**只能**走 `setWindowProperty`。
   （实测图像区 304x281 → **1600x1000** → 退回来。）
   测试**断言了这个常量关系**：哪天换了 OpenCV 两者真分开了，测试会红并提示"实现可简化"。
2. **`calibrate_color` 里 `f` 已经是"冻结画面"** —— 全屏若抢走它就会把一个既有功能弄坏。
   那个程序**保留 `f`、全屏只用 F11**。**抢掉别人的键比没有全屏更糟**，测试逐个核对了这件事。

**初始窗口**取"图片的 1.5 倍"与"屏幕的 90%"里较小的那个 ——
图小就放大到看得清，图大也不超出屏幕。

### 13.8 相机：三个不同的失败模式，逐个查清

**① 同名相机 + 名字兜底任意猜（真缺陷）**

两台同型号同名（**当时**都叫 `aoni webcam A25`），其中一台换过 USB 口：

```
left  -> #1 via 'identity'   ✓ 它绑定的那台正好在线
right -> #0 via 'name'       ✗ 名字同名，**任意抓了第一个**
```

**危害第二条最阴**：`#0` 当时只有 1280x720 而 `#1` 是 1920x1080 →
**两路分辨率不一致，双目标定失去意义，而界面上看不出任何异常**。

**现在**：绑定过身份的角色，身份/端口对不上就**拒绝并报错**（说清缺哪台 + 当前清单 + 下一步）；
同名多台报歧义；`resolve_roles()` 保证两个角色不撞车；界面**拦住**标定操作并弹窗。

> **2026-10-18 现状更新**：用户已把两台相机**改名**为 `aoni webcam A25 left` /
> `aoni webcam A25 right`，**名字唯一**。所以上面"任意抓了第一个"的**触发条件已消失**，
> 但**代码里的这些守卫不删** —— 它们防的是"名字不唯一"这个**状态**，而不是这台机器。
> 换了设备 / 用户又改回同名，守卫仍然必要。见 §10.12。

**② "打开了但一帧都拿不到"（硬件状态）**

`-2147483638` = `MF_E_VIDEO_RECORDING_DEVICE_INVALIDATED`。实测：

| 后端 | 打开 | 帧 |
| ---- | ---- | -- |
| MSMF | True（**61 秒**） | **0** |
| DSHOW | True（7 秒） | 有帧但 `mean=0.00 std=0.000`（纯黑） |

**处置只有物理拔插**。

**代码侧的缺陷是"等它的方式"** —— 三个等待叠在一起，把"失败"拖成"卡死"：

| 环节 | 实测代价 |
| ---- | -------- |
| 单次 `cap.read()` 对不响应的设备 | **10 秒**（MF 内部抓帧超时） |
| 逐个试 4 个分辨率 | 40 秒 |
| 不指定后端时再试 3 个后端 | **8 分钟以上** |

现在：**一帧都读不到 = 设备层面问题 → 不再试其它分辨率**；每次读上限 3 秒；
整个搜索上限 60 秒。**8 分钟 → 10.6 秒**，并报出每一档为什么失败。

**③ ⚠️ 我加过"自动换后端"，实测证明更糟，已撤回**

第一版让它"MSMF 拿不到帧就自动改用 DSHOW"。**结果**：

```
MSMF 打开相机1 → 无帧 → 自动切 DSHOW
  → optimize_mode 在【混合后端的进程】里测到 0.0 fps
  → 触发几十秒的模式搜索（150 秒）
  → 把分辨率降到 1280x720 写进缓存
```

而**单独测同一台相机的 MSMF 是 10/10 帧全好的**（1920x1080，清晰度 996）——
**是这次"回退"把它弄坏的**。

根因代码里**早就写着**（`stereo/pair_source.py`）：
**同一进程里混用 DSHOW + MSMF，MSMF 那路会"打开成功但抓不到帧"**。
**自动换后端 = 亲手制造那个已知的坏状态。**

`_try_other_backend` 已**整个删除**（留着就是给下一个读代码的人再踩一次的陷阱）。
现在**抛错并给出按顺序的恢复步骤**，第一条就是**拔插相机**。

**④ 缓存会被坏状态污染**

`config/camera_modes.json` 里相机 1 一度被钉在 **640x480** —— 是相机坏掉那段时间
模式搜索写进去的。**这类缓存没有"过期"概念**，坏了会一直用。
（本轮已手工改回 1920x1080。）

### 13.10 本轮踩的坑（补进 §5 的清单）

| 坑 | 教训 |
| -- | ---- |
| **界面硬编码 + 不传参数** | 界面能设的东西，不许是一份与真实取值无关的装饰。`--target` 没传下去 → 永远用试标定档，而界面上看不出来 |
| **"合成图上测得挺快"** | `hough` 纯色底 132 ms、真实纹理 **4384 ms**（33 倍）。**合成基准对性能没有参考价值**，和 `s²` 是同一类错误 |
| **手算 grid 行号** | 加一行就要重排全部编号，迟早撞。**Tk 不报"两个控件在同一格"**，直接画在一起 |
| **写死的换行宽度** | 是对窗口尺寸的猜测，窗口一改就错。必须按视口动态算 |
| **先画字再缩图** | 叠加层必须在**最终画布**上画；先画后缩 = 所有文字被重采样糊掉 |
| **自动换后端** | 在一个**已被证明有害**的组合（混用 DSHOW+MSMF）上"自动恢复" = 制造那个坏状态。**宁可口头说清，不要静默补救** |
| **单次 `read()` 10 秒** | 设备不响应时 MF 的抓帧超时要 10 秒；12 次 × 4 档 × 3 后端 = 8 分钟。**任何循环都要有预算** |
| **`WINDOW_FULLSCREEN == AUTOSIZE`** | 本构建里两者同值，那个常量**不能**用来建全屏窗口 |
| **`cv2.contourArea` 对网格点恒为 0** | 它按多边形顶点顺序算，而角点是行序网格。必须 `convexHull` |
| **缓存没有过期概念** | 相机坏掉时写进去的 `640x480` 会被一直用，而没有任何机制发现它已经不对 |
| **我写的断言是重言式** | 改了个副本的字段却断言**原对象**，恒真 —— 把判定退回二值的变异照样通过。**"变异没红"要先分清是判据弱还是注入没生效** |

### 14.4 标准数据契约（摘要）

- `derived/seeds.json`：`schema=sphere-stereo-seeds`，原图像素坐标，`seed_frame` 对应左右；
- `derived/traj3d.json`：`schema=sphere-stereo-trajectory`，`unit=m`，
  `coordinate_system=rectified_left_camera`，含 sync/calibration/seeds/samples；
- `derived/visualization.json`：`schema=sphere-stereo-visualization`，
  `trajectory` + `bounds` + `style`，可视化程序只读这个；
- 完整定义：`docs/数据标准.md`。改字段可保持 v1；改坐标/单位/语义必须升 version。

### 14.5 已知限制

- **`--detect-width` + `ctx.gray` 尺寸 bug**：pipeline 把原分辨率灰度图传给缩小后的
  detector；specular 已 shape-guard，color 亚像素分支待修（单独提交 + 测试）。
- **specular 只支持离线双目**；实时入口会明确拒绝。自动初始化不可靠，
  必须点选/给 seed。
- **没有独立三维真值**：221550 的 Z 范围只能说明"在动、量级合理"，
  不能证明绝对精度。
- **标定"勉强可用"**：极线 1.182 px，仍限制绝对精度。
