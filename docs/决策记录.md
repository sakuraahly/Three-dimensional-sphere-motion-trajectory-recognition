## 2026-10-23 · 多 Agent 团队角色与高清摄像头策略

- **批准人：** 用户（Human-in-the-loop）。
- **决策 1：** 主 agent 为 Leader / Orchestrator；默认不亲自承担大批量实现，
  负责拆解、派发、集成、验收与提交。规则写入全局 `~/.dsh/AGENTS.md` §十五，
  项目 `AGENTS.md` §11.6 落地。
- **决策 2：** 代码/契约/高风险变更默认必须有独立 Critic；Executor 不得自评；
  高风险/不可逆事项必须由用户批准。
- **决策 3：** 高清摄像头接入先做能力确认（`cameras.py doctor`）。
  **2026-10-24 更新：真机已验证两台外接相机恒给 2560x1440，默认据此改为
  2560x1440@24（见决策 8），不再默认 1080p@30；4K 仍不默认。**
- **决策 4：** 分辨率/帧率/编码改为单一 profile 来源，禁止在 GUI、录制、标定、
  检测各处各写一份 `1920/1080/720/960`；支持能力由探测决定，失败明确回退。
- **决策 5：** 标定、录制、离线分析的分辨率必须一致；不一致必须报错，不静默混用。
- **决策 6（2026-10-23 记录，已被决策 8 取代）：** 两台相机确认支持
  2560x1440@30。裸采集短测：两路 `CameraSource + HFYU` 在 10.022s 内写
  302/301 帧（30.13/30.03fps），零读错，合计约 **2.23GB ≈ 223MB/s**。
  但 **`record_stereo` 1440p@30 主循环实测只有约 24.07fps（242/300 帧/路，
  10 秒，HFYU，两路一致）**——裸采集 30 ≠ 主循环 30，按 30 录会丢帧。
  当时据此仍默认 1080p；2026-10-24 真机确认相机**根本不接受 1080 请求**，
  该默认会让录制校验必然失败，故改为 1440@24（见决策 8）。
- **决策 7：** 录制前必须校验“标定 `image_size` == 录制请求分辨率”；
  1080 标定 + 1440 录制直接报错（return 2），不能等到离线才失败。
  录制默认用独立命名的 `RECORD_DEFAULT`，避免以后改 `DEFAULT` 时录制静默跟过去。
- **决策 8（2026-10-24，真机验证后改默认）：** 两台外接相机**无视 1920/1280
  请求，恒给 2560x1440** —— 旧默认 1920/1080 会让 `record_stereo` 的
  “实际分辨率 == 请求”校验必然失败（默认值根本跑不起来）。因此：
  `video_profiles.DEFAULT` 与 `RECORD_DEFAULT` 均改为 2560x1440；
  GUI / `_common` / `run_realtime` / `record_stereo` / `cameras.py doctor`
  的帧率默认统一为 **24**；`record_stereo` 2560x1440@30 主循环实测
  **24.07fps**（242/300 帧/路，HFYU 10 秒，两路一致）——**30 会丢帧，
  24 是稳定目标**，只在显式请求 >24fps 时告警。
  1920x1080 / 1280x720 仍是合法可选档；旧 1080 标定、旧 1080 会话照常可读，
  但录制/标定必须同分辨率（混用仍 return 2）。4K 仍不默认。

## 2026-11-18 · 高帧率/高分辨率档位扩容

- **批准人：** 用户（Human-in-the-loop）。
- **决策 1：** `video_profiles.PROFILES` 由 6 档扩到 8 档，顶部新增 8K（7680x4320）
  与 5K（5120x2880）。两者**只在用户显式选择时生效，不进自动协商**：
  `PROBE_CEILING = P4K` 保证 `probe_order(None)` 与扩容前**逐项相同**（仍是 4K 起、
  共 7 项、末尾原生档）。理由：自动协商每多试一档就多一次相机打开尝试，个别后端
  单次 20 s+，从 8K 起试会让所有现有相机变慢。显式档（`probe_order(P8K)`）
  不受 `ceiling` 限制：以该档自身开头，再逐档往下。
- **决策 2：** 默认档改为**对象引用**（`DEFAULT = RECORD_DEFAULT = P1440`），
  不再用 `PROFILES[1]` 下标。原因：在顶部加两档会让 `PROFILES[1]` 从 2560x1440
  静默漂成 5120x2880，而**默认档漂移不会报错**，只会让所有录制/标定静默换分辨率。
  以后加档只改 `PROFILES` 那张表，别碰对象引用。`tests/selftest_highspeed.py`
  用正则扫 `sphere_tracker/` 与 `apps/` 下的**代码**（注释与 docstring 不算），
  出现 `PROFILES[数字]` 即报不达标并打印文件名与行号。
- **决策 3：** 帧率全链改为浮点。5 个 CLI 入口（`record_stereo` / `_common` /
  `run_realtime` / `tools/capture_board` / `tools/list_cameras`）的 `--fps`
  由 `type=int` 改为 `fps_type`，`pair_source` 的 `int(fps)` 改 `float(fps)`。
  理由：29.97 被截成 29，录 1 分钟少 1.8 帧。`FPS_TIERS =
  (24, 30, 60, 120, 240, 500, 1000)` 只是 GUI/CLI 下拉的**建议值，不限制输入**；
  合法区间 `(0, 1000]`，非法输入抛 `argparse.ArgumentTypeError` 且文本里带收到的原文。
- **决策 4：** 三个"按帧说话"的门限改为**从 fps 派生**，但 **24/30 fps 下必须逐项
  等于旧常量**（否则就是拿现有相机的行为去换一个还没接上的能力）：
  - 实时两路时间差：`run_realtime_stereo.default_max_skew_ms(fps)`，
    `fps <= 30` 恒 60 ms（= `DEFAULT_MAX_SKEW_MS`），更高按 `60*30/fps` 收紧、
    下限 2 ms（500 fps → 3.6 ms）。`--max-skew-ms` 的 parser 默认值是 `None`，
    在 `parse_args()` 之后立刻填成实际数字 —— `None` 在 `should_drop()` 里的语义是
    "不设门限"，绝不能漏进主循环（比门限偏松危险得多）。
  - 闪光同步搜索窗：`sync.config_for_fps(fps)`，
    `max_offset = max(180, 6s*fps)`、`min_overlap = max(30, 1s*fps)`
    （24/30 fps 都得到 180/30，与旧硬编码一致；500 fps → 3000/500）。
  - 理由：这三个数字原本是按 30 fps 调的。500 fps 下 60 ms 等于 30 帧
    （形同不设防），180 帧只有 0.36 秒（搜索窗窄到必然失配）。
- **决策 5（明确写了不做什么）：** `PairSource.timestamp_tolerance_s`
  **保持固定 0.033，不按帧率派生**。这条容差只用于**视频文件**的时间戳 sidecar
  配对，帧周期来自**容器**，而构造函数的 `fps=` 是**相机请求帧率**（视频路径下
  默认 60，与视频真实帧率无关）；按 `1/fps` 派生会得到 0.0167，比原值紧一倍，
  属于对 `--left-video/--right-video` 老入口的行为变更，且对高帧率相机零收益
  （相机路径根本不走这条）。顺带把 `from_args` 视频分支兜底的 `0.020`
  与类默认 `0.033` 不一致这个真 bug 统一为 `0.033`。
- **决策 6：** 录制启动期加裸流带宽提示（`record_stereo.stream_bandwidth`，
  BGR24 未压缩估算），阈值按**单路** `USB3_EFFECTIVE_GBPS = 0.5` GB/s 判，
  **不是**两路合计 —— 两台相机通常各占一个 USB3 口、各吃自己的链路；按合计判会
  把本机**已实测可用**的 2560x1440@24（单路 0.265 GB/s）也报成告警。
  **只 `log.warning`，不拦截、不改退出码。**
- **决策 7（真正天花板，写清楚免得以后当成程序 bug）：**
  ① `cv2.VideoCapture` 只走 UVC，不存在 4K@500 的 UVC 模式，需要厂商 SDK +
  硬件触发；② 双路 4K@500 BGR24 裸流 24.9 GB/s，远超任何单机 I/O；
  ③ 本机 HFYU 实测 1080p30 约 34 fps/路，按像素线性外推 4K 约 8 fps/路、
  8K 约 2 fps/路 —— 所以"请求 24 fps、实际录到 8 fps"是**硬件吞吐**，
  不是程序丢帧。`session.*.fps_measured` 记的是**实测值**，
  `run_stereo_video` 下游取的也是 `fps_measured or fps_requested`（不是容器头），
  所以时间轴不会错。

## 2026-11-19 · 两种受限运动下的简化标定（轴向大板 / 中轴 90°）

- **批准人：** 用户（Human-in-the-loop，物理前提由用户逐条确认）。

背景：以后可能用**很大的棋盘格**，但受装置限制不能像现在这样多姿态移动。
用户明确要求把这两种方式和现有的多姿态标定**区分开、并存**：

1. **平行双目 + 轴向大板**：板正对相机、只能沿光轴前后小范围推，推进距离已知、方格尺寸已知；
2. **大角度 + 中轴 90°**：同一块板先正对相机 A，绕**板的中轴**旋转 90° 后正对相机 B；
   只保留 chain_dual 的 ①② 两步，用户原话"很妙"的是"装置保证两次板刚好垂直 90°"。

- **决策 1（为什么现有标定必须新写，不能只放宽门限）：** 三份只读审计一致确认，现有系统会
  **主动拒收**这类数据：`calib/capture.py` 的 `diversity_min=0.055` + 九宫格覆盖
  要求位姿变化；`calib/mono_calib.py` 的 fx 留一法判据专门防"姿态太相似"（报错原文就是
  "拍 ±20° 倾斜的，而不是只平移"）；大板还会撞 `max_area_ratio=0.90`。
  数学上板正对 + 纯 Z 推进是**退化观测**（切向畸变不可观测、f 与 Z 强耦合、主点漂移），
  所以必须靠用户给的物理先验换精度，而不是改几个阈值。
- **决策 2（轴向模式的数学）：** 已知方格边长 L 与每帧推进量 ΔZ_i 时，
  `1/p_i = Z0/(f·L) + ΔZ_i/(f·L)` 线性拟合 → `f=1/(b·L)`、`Z0=a/b`；
  主点用"逐角点跨帧拟合 `u=cx+slope/Z`、取截距中位数"同时分离 cx 与板横向平移。
  合成自验：0.3px 角点噪声下 fx/fy/Z0 误差 0.16%/0.017%，主点 0.4px。
- **决策 3（轴向不标畸变，诚实标注）：** 正对 + 纯 Z 推进下径向畸变与尺度/主点强耦合，
  无法可靠分离。求解器**锁定切向 p1=p2=0、D 恒 0**，并在产物里写
  `distortion_calibrated=False` + notes，**不硬凑**。镜头畸变明显时仍需一次常规多姿态标定。
- **决策 4（轴向的 R 弱可观测 → `assume_parallel`）：** 只沿光轴推进对两相机相对旋转几乎没有
  约束（合成真值下也可能差约 1°）。焦距/Z0/基线可靠，R 不能当精密量。对机械保证平行的
  装置提供 `--assume-parallel`：强制 `R=I`，E/F 由 `(I,T)` 重算，校正接近恒等、极线更稳。
  默认关（保持"观测 R"的旧语义），由用户按装置选择。
- **决策 5（中轴 90° 的链）：** 旋转轴是**板的中轴**（不是板边），两板几何中心重合 →
  `T_AB=[R_AB|0]` 纯旋转。但 `BoardSpec` 原点是**角点**不是中心：直接用角点原点会让
  `T_AB` 平移变成 `(I−R_AB)·c ≈ W/2`，所以求解器内部先把物点平移到板中心。
  相对位姿用严格链 `T=T_camB_B·T_AB·inv(T_camA_A)`（含两板 solvePnP 的 roll），
  不用"无 roll 版"简化式（实测 roll=20° 时简化式差 10.27 mm）。
- **决策 6（中轴 90° 不写死 90° 于产物判定，但用装置约束省步骤）：** 现有 chain 刻意从 R
  实测夹角、不写死 90°，因为它同时承担 A/B 指派校验与 180° 等价解纠错。新模式用装置
  90° 换掉 ③④（同框图/参考对），代价是这些防呆不再来自图像；改用**基线物理核对**兜底
  （见决策 7）。
- **决策 7（装反检测的真实边界，实测）：** 装错旋转轴时两板**仍正对**，残差照样很小，
  "板法向一致性 / 光轴夹角"都抓不住；唯一信号是**基线模长**：合成实测 axis 装错只偏
  **7.8%**、angle 反向偏 **16.9%**，而 `CalibConfig` 默认 `baseline_tolerance=0.20`
  漏判。所以：① 数据层在给了 `expected_baseline_mm` 且偏离超容差时**强制降级不可用**；
  ② 全局默认 0.20 **不改**（joint/chain 共用）；③ 两个新 CLI 入口显式用 **0.05**。
  不写"已自动识别装反"这种假安心，docstring 里写明灵敏度边界。
- **决策 8（内参来源与 sanity check）：** 中轴 90° 自己不求内参，吃轴向标定产物或既有标定。
  真实产物实测 `实验性质大角度1` 左右 fx 差 **33%**（2304 vs 1540），另两份平行装置仅
  0.26%/0.7%。所以读入后：K 非法/fx≤0/NaN → exit 2；fx 差 >30% 或 |D|>1 → 警告 +
  `intrinsics_suspect` 标记，**但不误杀几何判定**（内参可疑 ≠ 几何不成立）。
- **决策 9（角点顺序：SB 也可能整体反序）：** `findChessboardCornersSB` 的顺序取决于棋盘
  起始色，可能整体 rot180（实测正序 RMS 278px、反序 0.66px）。CLI 新增 `_canonical_order`
  按几何方向（行内 x 增、行间 y 增）规范化到 `BoardSpec.object_points()` 顺序。
  这与 `calib/board.py` 既有的"SB 是基准、经典回退整体反序"约定不冲突，且更鲁棒
  （能纠 SB 自身因起始色反序）。是否推广到现有 `calibrate_stereo.py` **本轮不动**，
  留待有真机数据时对比验证。
- **决策 10（接入形态）：** 新增两个**独立 CLI**（`apps/calibrate_axial.py`、
  `apps/calibrate_device90.py`），**不改** `calibrate_stereo.py` 的 joint/chain 分派、
  不注册新 `calib_method`（保持 CLI choices 与插件计数不变）。GUI 在双目窗的方法下拉里
  按窗口模式过滤：平行窗 `joint|axial`、大角度窗 `chain|chain_dual|device90`，
  避免选到几何前提不成立的算法。专属控件**懒建**（首次选中才创建），因此默认窗口的
  预算/高度判据一个都没动。

验收：`tests/selftest_stereo_calib.py`（轴向/中轴/内参 sanity/CLI 判据，含 mutation 反向自证）、
`tests/selftest_launcher_params.py`（11 条 GUI 接入判据）、`tests/selftest_gui_budget.py`、
`apps/run_tests.py fast` 26/26 全绿。合成图读图端到端 fx 有约 2.4% 偏差，已确认是
`fillPoly` 硬边的 detect 伪影（角点相对 ideal 仅 0.4px，但 p 有系统缩放趋势），
真实光学成像无此问题；ideal 角点端到端误差 0.000%。**真机精度仍未验证，需用户实测。**

## 2026-11-20 · 相机身份 / 采集索引分离 + 世界系契约

- **批准人：** 用户。用户给定物理事实：**真实左相机 = 床，真实右相机 = 阳台门**。
- **背景（相机）：** `#N` 来自 DSHOW 设备类顺序（过滤后重新编号），**不是**
  OpenCV/MSMF 采集索引；`capture_index` 从未写入，角色 `verified=true` 只表示
  身份确认。按角色启动时静默回退 `entry.order`，本机 left 身份对应 PnP #1
  而配置 `index=0`，`cameras.py check` 已报漂移 —— 这就是"显示的和真实的对不上"。
- **决策 1（相机）：** `role.capture_index` 是唯一采集索引；`None` 时
  `resolve_role` **拒绝猜**，报错指到 `cameras.py identify`；`identify` 写入实测值，
  `pin <role> capture-index:N` 可在已确认时落地。`role.location` 记录物理位置
  （床 / 阳台门），只用于人工核对；`settings.virtual_names`（vivo / 原子笔记 / OBS / …）
  命中的虚拟摄像机不参与绑定/预览，phantom 索引命中必须告警。

  这再次证明 PnP 位次只是快照、采集索引必须每次重测。
- **决策 2（世界系）：** 原点 = 板检测到的**左下内角点**；X=列向、Y=行向、

## 2026-11-21 · Media Foundation 按设备 symlink 采集（第二条路）

- **批准人：** 用户。原话：「用第二条路，然后先不要废止现有的方法。」
- **背景：** OpenCV `VideoCapture` 只收整数编号；PnP/编号/后端三套空间会漂移，
  名字又会重复/变化。MF 的 `MF_DEVSOURCE_ATTRIBUTE_SOURCE_TYPE_VIDCAP_SYMBOLIC_LINK`
  直接带 PnP 端口（本机 left `6&31324e2c`、right `6&212acdc8`），可按链路精确打开。
- **决策 1（新增，不废止）：** 新增 `sphere_tracker/mf_camera.py` 与
  `open_camera_source`；`capture_api=opencv` 原路径逐字保留，默认仍是 `opencv`。
  `--capture-api mf` 显式启用 MF；`auto` 先 MF、失败打印警告后回退 OpenCV。
- **决策 2（按 native type 选档）：** 不能只给 RGB32/宽高请求（会被接受却落到
  640×480）；必须枚举 `GetNativeMediaType`，分辨率优先、fps 其次、subtype 优先
  MJPG（双目 USB 带宽）。`MFCameraSource` 首次 `read()` 打开，`read/release/info`
  与现有 `VideoSource` 一致。
- **决策 3（不按名字猜）：** MF 匹配只认 symlink/端口/identity；FriendlyName 只
  显示。换 USB 口后 symlink 变化，仍需 `check`/重新绑定，不自动按名字找回。
- **实测：** right 单台 1920×1080 NV12 60 帧稳态 30.48 fps；MF 双路 1920×1080
  30 对约 15.1 fps（左相机当前 MF native 只有 NV12，右有 MJPG）；因此**默认
  不切 MF**，不把现有 OpenCV 双路 24–30 fps 降成 15。
- **判据：** `selftest_camera_registry` 第 24 节（symlink/选档/解码纯函数）、
  `selftest_pair_source`/`selftest_config_wiring`/`selftest_gui_budget`/
  `selftest_launcher_params` 全绿；真机单台/双路结果见 `docs/交接文档.md` §115。

## 2026-11-05 · 安装/卸载/无黑框启动器（分发版入口体系）

- **背景：** 分发版要给"只会双击"的终端用户一套入口，同时不能把开发仓库的约束带进纯净包。
  当日定下四个根目录入口：`run.bat`（主）、`install.bat`（安装）、`uninstall.bat`（卸载）、
  `launcher.exe`（可选无黑框壳）；另三个 worker 在 2026-11-22 同步修了参数转发与安全闸。
- **裁决 1（参数单一产地）：** `install.bat` 只是转发 `run.bat install` 的薄壳，
  `uninstall.bat` 是只认自身目录、不接受外部路径的卸载薄壳；参数路由的唯一产地是
  `run.bat`。**不在第二个 `.bat` 里复制一份安装/卸载逻辑**，避免两处漂移。
- **裁决 2（launcher 不入库、不进纯净包）：** `launcher.exe` 是 Go 编译产物、平台相关，
  既不入库也不进 `make_clean_bundle.py` 生成的纯净分发包；源码留在 `native/launcher/`
  （`main.go` / `go.mod` / `build.bat` / 图标），需要时由开发者用 Go 1.25（windres 可选）
  重建。终端用户不应把 `build.bat` 当安装步骤，完成提示也不承诺包内有该 exe。
- **裁决 3（卸载只走回收站）：** 卸载只允许在分发出去的纯净包副本上执行 —— 发现
  `.git` / `.workbuddy` / `AGENTS.md` 任一开发仓库标记立即拒绝（用户明确要求
  "绝不能在开发仓库里直接运行"）；列出将删内容并要求手输 `UNINSTALL` 二次确认；
  只走 Windows 回收站（可还原），回收站失败就停、绝不永久删除。安装后自采的
  `data/` / `config/` / `logs/` 会一起进回收站，卸载前需自行备份。
- **裁决 4（AI 组默认不装）：** `apps/setup_env.py --ai` 才额外装 YOLO / SAM 组，
  默认只装核心依赖。理由：AI 组需要 CUDA 且体积大，而核心功能
  （检测 → 跟踪 → 三维 → 预测）不依赖它；默认不装能让纯净包开箱即用，也不打断
  机器上已有的 AI 环境（`--verify` 只体检，`--isolate` 才强制新建项目内 `.venv`）。
- **自举前提：** 安装器需要一个"先能运行的 Python 3.10+"作引导解释器
  （已登记的 `config/python_env.txt` > PATH `python` > `py`），完全空白机器装不了；
  因此三份用户文档都把"先装 Python"列作第 0 步。
